## Phase 1 — 忌口为何 `commits=0`（最先）

### 已证实现象

| 探针 | 结果 |
| --- | --- |
| 「我绝对不能吃香菜」 | `appliedEvents=[]` `preferenceEpoch=0` `plan=[OUT_OF_SCOPE]` |
| facts / snapshot | 皆空 |
| metrics 前后 | `extractions` 33→34；**`commits` 仍 0**；**`writeFails` 仍 0** |

含义：

1. 异步抽取跑了（extractions+1）。
2. **没有任何一次成功 commit**（本进程累计 commits=0）。
3. **也没有记到写失败**（writeFails=0）→ 失败被静默吞掉，或根本没走到会抛错的路径。

### 问题归属

| 层 | 类型 | 说明 |
| --- | --- | --- |
| MySQL `diet_preference_*` 是否迁移/可写 | **数据/基建** | V44/V45 有 migration；需在测试库确认表存在且进程连的是该库 |
| `PreferenceStore.commit`：`!available()` 或 catch 后 `none()` | **业务** | 不打 `writeFails`、同步链无失败字段 → 指标与 UI 双假绿 |
| 规则能抽「香菜」 | 非根因 | 本地正则与单测可抽；旁路 extractions 在涨 |

最可能分叉（需二选一钉死）：

- **A. `DietPreferenceMapper` 不可用** → `available()==false` → 直接 `none()`，无异常。  
- **B. mapper 可用但 `persistCommit` 抛错** → Store catch 成 `none()`，Async 看不到异常 → **writeFails 仍不涨**（Store 吞了）。

### 如何验证（不改产品逻辑）

1. 查测试库：`SHOW TABLES LIKE 'diet_%'`；`flyway_schema_history` 是否含 V44/V45。  
2. 启动日志是否加载 `DietPreferenceMapper`。  
3. 临时在 `commitDurable` catch 打 warn + `metrics.markWriteFail()`（验证用），再打一枪忌口看 writeFails。  
4. 成功标准：一次忌口后 `commits≥1`、facts 含香菜、`epoch≥1`。

### 优化（本 Phase 交付）

1. 基建：补齐/迁移偏好表；确认 datasource 指向真实测试库（非占位密码连错库）。  
2. 业务：commit 失败必须 `markWriteFail` + 日志；响应增加可见态（如 `memoryWrite=FAILED|OK`）。  
3. 门禁：忌口轮 `applied` 空或 epoch 不涨 → 脚本 FAIL。

**本 Phase 未完成前，不要把「记忆问答无记录」当成答题 bug。**

## Phase 2 — 荐菜空（落库通了之后）

### 已证实现象

| 请求 | 结果 |
| --- | --- |
| 无川菜：番茄鸡蛋豆腐 | **有菜**：水煮蛋、番茄炒蛋 |
| 有川菜：同食材 | `NO_FEASIBLE_MAINS`，`degradeStep=0`，`guide=ADD_FOODS` |
| foods 含青椒/土豆 | `unrecognized:["青椒","土豆"]` |

### 问题归属

| 点 | 类型 | 说明 |
| --- | --- | --- |
| 菜系硬过滤 + degrade 默认 false | **业务/配置** | 有候选但主料验全失败后不降级去菜系 |
| `PublishedCatalogIndex.toDish`：非调味一律进 mains | **业务建模** | 表「辅料」也变硬主料；香菇/木耳等拖死家常菜 |
| 川菜语料偏肉+菌 | **数据** | 过滤后可行交集薄 |
| 青椒/土豆无别名 | **数据** | 缩小 owned 集合（次要；无它们仍应有番茄炒蛋） |

`NO_FEASIBLE_MAINS` 语义：narrow **非空**，verify 全灭——不是 ANN 没召回。

### 优化（本 Phase 交付）

1. 预发/生产：`nutritionist.recall.degrade.enabled=true`；`NO_FEASIBLE_MAINS` 允许去菜系（点名不存在菜系仍 fail-closed）。  
2. `toDish`：按菜谱主/辅列（或 role）拆 mains/aux；缺辅料走 bring 扣分，不硬拒。  
3. 数据：补 1～N 道「川菜 + 主料⊆番茄/蛋/豆腐」冒烟菜；补青椒/土豆 alias。  
4. 空引导：有菜系过滤时除 `ADD_FOODS` 外给 `DROP_CUISINE` 提示。  
5. 观测：`owned_ids` / `narrowed_count` / `degrade_step` / 首个缺失主料。

**成功标准：** 同 R2 文案 `dishes≥1` 或明确「先不限川菜」的可解释降级结果；`degradeStep` 可见。

## Phase 3 — OOS 话术与门禁假绿（体验与防回归）

### 已证实现象

- 纯忌口/改口/记忆问：`plan=[OUT_OF_SCOPE]`，explanation 为选菜自我介绍。  
- 设计上偏好是旁路，不在 `TaskType`；Understand 末桶 + Executor 仍播域外文案。  
- 前端 `RULES_MEMORY` 写死 PASS；有 `emptyReason` 的空荐也 PASS。

### 问题归属

| 点 | 类型 |
| --- | --- |
| TaskType 无偏好任务 + prompt/thinFallback 落 OOS | **业务（架构）** |
| 旁路成功仍执行 OOS 文案 | **业务** |
| SafetyNet 不覆盖偏好句 | **业务** |
| analyzeNodes 假绿 | **业务（验收）** |
| 金标绿 ≠ 真机红 | **业务（门禁体系）** |

与 Phase1 正交：即使旁路写成功，若不做门控，plan 仍可能唯一 OOS。

### 优化（本 Phase 交付）

1. Orchestrator：rules 已 commit 或 `memoryAnswer` 非空且 tasks 仅 OOS → 丢掉 OOS / 改为确认话术。  
2. Understand：偏好-only → 空 tasks + constraints/queries；prompt 补 `memoryQueries` 样例。  
3. SafetyNet：忌口/改口/记忆问误 OOS 时纠偏。  
4. 前端：R2 dishes≥1；R3 applied+epoch；R9 非「没有记录」；忌口句 applied 空 → FAIL。  
5. 真环境 Accept 升为首发门禁。

**成功标准：** 忌口轮 explanation 含「已记住…」且 plan 非sole OOS；脚本假绿消失。

## Phase1 结论（2026-11-18 已落地）

| 项 | 结论 |
| --- | --- |
| 表/Flyway | schema 已到 V45，表存在；本轮加 V46 加宽 `event_id` |
| 根因 | **数据列宽 + 业务键设计**：明细 `event_id = uuid:uuid`（73）> `VARCHAR(64)` → `Data truncation`；`PreferenceStore` 吞异常 → `commits=0`/`writeFails=0` |
