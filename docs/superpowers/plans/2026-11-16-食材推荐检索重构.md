# 食材推荐检索重构

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 用户报出现有食材后，系统只返回主料齐全的菜，最多 3 道，并附带匹配理由和做法。

**Architecture:** 食材先过同义词变成 `food_id`。倒排召回「主料被盖住」的已发布菜，硬过滤确认子集关系，再按主料覆盖和需自备辅料排序。Redis 只按 `dish:{id}` 缓存菜卡。向量、BM25、Reranker 在菜多到倒排扫不完、或用户用一句话描述口味时再接入。今天的克数和热量仍由已有求解器和 Java 复算决定，不进这条检索。

**Tech Stack:** JDK 21、Spring Boot 4.1.1、MySQL `consult_agent`、现有 Redis、小程序 `miniprogram/`。第一版不新增 Milvus。

## Global Constraints

- 能不能做只看必需主料是否都在用户食材里。模型、向量、Reranker 都不能放行缺主料的菜。
- 油、盐、生抽视为常备辅料，不参与硬过滤，也不写成「需自备」。
- 标签只允许内容类（当前已发布减重菜使用「减脂」）。不建糖尿病、高血压、低血糖、痛风、肾病标签，也不按这些标签召回。
- 热量展示用 Java 按配料复算的结果。不用菜谱上另写的一个千卡数做过滤。
- 没有克数的菜可以出现在「能做的三道」里，但不能进入 `/api/nutrition/catalog/day` 的额度求解。当前库里的已发布菜都有克数。
- 未知营养素保持空值，不写成 0。
- 个人小程序只给饮食建议，不按病种配餐。

## 接口

`GET /api/nutrition/catalog/matches?foods=138,580`

`foods` 为食材编号或中文名，逗号分隔。也接受 `番茄` 这类同义词。

成功时 `data` 为：

```json
{
  "dishes": [],
  "unrecognized": ["土豆"],
  "fallback": ""
}
```

`dishes` 最多 3 条，每条含 `score`。没有通过门槛时 `dishes` 为空，`fallback` 说明不会另编一道。`unrecognized` 是对不上食材字典的词。

## 排序

通过硬门槛的菜按规则分从高到低排：100 分减去每个需自备辅料 15 分，低于 40 分不返回。同分再比主料数量和菜名。模型不参与打分。

## 第二阶段（本轮不实现）

- Milvus 稠密向量加内置 BM25，只用于「清淡、快手」这类自然语言，以及倒排候选过多时的粗召回。
- 两路结果用 RRF 合成 Top 20～30，然后仍做主料硬过滤。
- Reranker 超时预算 500 毫秒，超时用上面的排序。
- 上架同时写 MySQL 与 Milvus；下架软删并删除 `dish:{id}`。每日对账：MySQL 已下架的菜不得再被向量召回。

## 对照法律检索

- 知识源只是已发布菜谱和食材字典。做法是附在菜上的正文，不单独拿去匹配。
- 切块粒度是一道菜的一个已发布版本。匹配粒度是一个必需主料，相当于法条按「条」切、按构成要件对齐，不按字数把做法切断。
- 核心规则：用户食材必须覆盖全部必需主料。油、盐、生抽是常备，不参与这条规则。
- 打分：硬门槛是主料覆盖率等于 1，否则 0 分并丢弃。通过之后每缺一种非常备辅料扣 15 分，低于 40 分不推荐。这是规则分，不是模型分。菜能不能上架仍由发布状态决定。
- 验证：返回前再用食材集合复核主料。Redis 只缓存已经通过复核的菜卡，不参与判断。
- 兜底：没有通过门槛的菜就返回空，并说明不会另编一道。对不上字典的词单独列出。
- 评测：`IngredientMatchEvaluationTest` 用固定菜谱和查询，检查精确率与应命中菜的召回率。

### Task 2：推荐服务与接口

**Files:** `DishRecommendService.java`，`CatalogController.java`

- 用目录里的已发布菜。非调味食材为主料，调味品为辅料。

- 接口返回 `Result`，成功码 200。
