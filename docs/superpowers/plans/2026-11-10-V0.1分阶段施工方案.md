# Nutritionist V0.1 分阶段施工方案

> **For agentic workers:** REQUIRED SUB-SKILL: Use `superpowers:subagent-driven-development`（推荐）或 `superpowers:executing-plans` 按任务逐步实施。步骤使用 `- [ ]` 跟踪。

**Goal:** 在 `nutritionist` 仓库交付可运行的 V0.1 模块化单体，完成无模型确定性配餐 MVP，并与 `registration-assistant` 共享账号、患者与网关。

**Architecture:** nutritionist 独立部署；账号/JWT/患者基础资料归挂号体系；nutritionist 只保存患者引用和营养业务事实。Controller 只转调，Service 编排事务，Domain 放规则与端口，Infrastructure 放 JDBC/Redis/模型适配。推荐创建异步化，求解与模型走有界虚拟线程队列。

**Tech Stack:** JDK 21、Spring Boot 4.1.1、Spring AI 2.0.1、MySQL 8.0.46、Redis 8.2.10、RocketMQ 5.5.1（V0.1 主链路不接）、ojAlgo、Flyway、JdbcTemplate、Testcontainers、k6。

## Global Constraints

- 产品基线唯一：`docs/superpowers/specs/2026-11-10-慢病与减重食材推荐系统设计.md`（V1.5）。本文件是唯一施工方案，不另建产品方案。
- 版本：`0.1.0-SNAPSHOT`；分支从 `feature-V0.1-20261110-foundation` 开始；`main` 只收发布合并。
- 包名：`com.moonligh.nutritionist`；文档中文文件名；Java/配置/迁移用英文。
- API 前缀：`/api/nutrition/v1`；统一返回 `Result{code,message,data,traceId}`；业务 HTTP 常为 200，网关限流可用 429/503。
- 对象化：接口与领域禁止 `Map<String,Object>`；使用 record `*Req/*Res`、`*Command/*Result/*Snapshot`；手工映射，无 BeanUtils/MapStruct/Lombok。
- 时间：`Instant`；业务日：`LocalDate` + `ZoneId`；重量与营养：`BigDecimal` + 单位枚举；枚举 JSON 用稳定数字 code。
- 写接口必须带 `Idempotency-Key`（≤64）；同键同请求哈希返回原结果，同键不同哈希返回 409。
- 模型不得修改食材 ID、克数、菜谱版本、油盐、步骤顺序、食品安全参数、目标或摄入事实。
- 容量：全站 API 合计峰值 1000 QPS；推荐创建单独限流并异步；日均约 10 万推荐任务。
- 默认 `mvn -B verify` 不依赖真实模型与外部服务；IT 用系统属性开关。
- 代码要求：小类小方法、显式分支、必要中文注释；优化用重构，不堆条件。

## 1. 跨仓边界与部署

### 1.1 责任划分

| 能力 | 仓库 | 说明 |
| --- | --- | --- |
| 登录、JWT、账号 | registration-assistant `consult-identity` | nutritionist 不自建登录 |
| 患者基础资料（姓名、性别、年龄、关系） | registration-assistant `consult-identity` | 生产入口 `/api/patients` |
| 网关路由、JWT 验签、分档限流、在途上限 | registration-assistant `consult-gateway` | 增加营养路由 |
| 营养画像、疾病/药物/过敏、测量、库存、目标、方案、烹饪、摄入 | nutritionist | 业务事实源 |
| 专业目标、规则审核、Kill Switch | nutritionist | 角色由 identity 签发，nutritionist 校验 |

### 1.2 患者引用合同

nutritionist 不复制患者主数据，只保存：

```text
PatientRef
  accountId: String
  patientId: String
  patientVersion: String
  boundAt: Instant
```

每次写业务前通过 `PatientGateway`（端口）校验：

1. 当前 `accountId` 拥有该 `patientId`；
2. 返回的 `patientVersion` 与请求一致，否则 `NEED_MORE_DATA` / 版本冲突；
3. 允许缓存短 TTL，但确认方案和推荐提交前必须二次校验。

挂号侧 V0.1 需补充（不破坏现有咨询）：

- 规范化 `consult-identity-api` 中 `PatientRes`，增加 `patientVersion`、`updatedAt`；
- 网关增加：
  - `/api/nutrition/v1/**` → nutritionist 服务；
- 限流档位：查询、普通写、推荐创建、库存识别、专业管理。

### 1.3 鉴权头

与挂号一致，网关校验后写入：

- `X-Account-Id`
- `X-Account-Role`：`patient` / `staff` / 后续 `nutritionist_pro`
- 可选 `X-Doctor-Id`

nutritionist 的 `AccountAuthFilter` 只信网关头；本地开发可用 `nutritionist.security.dev-principal` 开关注入测试账号，生产必须关闭。

## 3. 统一返回、错误码与幂等

### 3.1 Result

复用挂号形态，nutritionist 自有一份同结构类（不跨仓依赖 consult jar，避免强耦合；字段与语义对齐）：

```java
public class Result<T> {
    private int code;       // 200 成功
    private String message;
    private T data;
    private String traceId; // 与 X-Trace-Id / MDC 相同
}
```

### 3.2 错误码段

| 段 | 用途 |
| --- | --- |
| 1000–1099 | 通用（对齐挂号：1001 参数、1003 限流、1004 繁忙） |
| 1201–1299 | 登录/账号（由网关/identity 产生，nutritionist 透传语义） |
| 2100–2199 | 画像与患者引用 |
| 2200–2299 | 安全许可与药物 |
| 2300–2399 | 目标与额度 |
| 2400–2499 | 食材/菜谱/数据质量 |
| 2500–2599 | 库存 |
| 2600–2699 | 推荐任务与求解 |
| 2700–2799 | 方案与确认 |
| 2800–2899 | 烹饪执行 |
| 2900–2999 | 摄入与效果评价 |
| 3000–3099 | 治理 / Kill Switch |

首批必须实现的码：

| code | 常量 | 说明 |
| --- | --- | --- |
| 2101 | PATIENT_NOT_BOUND | 未绑定就诊人 |
| 2102 | PATIENT_VERSION_CONFLICT | 患者版本已变化 |
| 2103 | PROFILE_VERSION_CONFLICT | 画像版本冲突 |
| 2201 | SAFETY_NOT_ALLOWED | 当次安全许可不允许自动配餐 |
| 2202 | MEDICATION_RULE_NOT_COVERED | 药物场景无已发布规则 |
| 2301 | TARGET_RULE_MISSING | 无已发布目标规则 |
| 2302 | PROFESSIONAL_TARGET_REQUIRED | 需要专业目标 |
| 2401 | FOOD_DATA_REJECTED | 关键营养数据未达门槛 |
| 2402 | RECIPE_NOT_PUBLISHED | 菜谱未发布或已失效 |
| 2501 | PANTRY_VERSION_CONFLICT | 库存版本冲突 |
| 2502 | PANTRY_RESERVATION_FAILED | 预留失败 |
| 2601 | RECOMMENDATION_IN_PROGRESS | 同范围任务单飞中 |
| 2602 | RECOMMENDATION_EXPIRED | 提交前版本复核失败 |
| 2603 | SOLVER_INFEASIBLE | 硬约束无解 |
| 2604 | IDEMPOTENCY_CONFLICT | 同键不同请求体 |
| 2701 | PLAN_NOT_CONFIRMABLE | 方案状态不可确认 |
| 2801 | COOKING_DEVIATION_UNSUPPORTED | P3 不接受执行偏差 |
| 3001 | KILL_SWITCH_ACTIVE | 能力已紧急停止 |

### 3.3 幂等表

```sql
CREATE TABLE idempotency_record (
  id            BIGINT PRIMARY KEY AUTO_INCREMENT,
  account_id    VARCHAR(64)  NOT NULL,
  endpoint_scope VARCHAR(64) NOT NULL,
  idempotency_key VARCHAR(64) NOT NULL,
  request_hash  CHAR(64)     NOT NULL,
  response_code INT          NOT NULL,
  response_body JSON         NOT NULL,
  created_at    DATETIME(3)  NOT NULL,
  UNIQUE KEY uk_idem (account_id, endpoint_scope, idempotency_key)
);
```

规则：

1. 写接口读取请求头 `Idempotency-Key`；
2. 规范化请求体后算 SHA-256；
3. 插入成功则执行业务；唯一键冲突则比较哈希；
4. 领域事件（测量、摄入、库存变更）另有 `event_id` 唯一索引，不能只靠幂等表。

## 4. 字段级 API 合同

基础路径：`/api/nutrition/v1`
除特别说明外，成功 `Result.code=200`；推荐创建成功可用业务码 200 且 `data.status=PENDING`。

- 鉴权：patient

### 4.2 疾病 / 药物 / 过敏

`CreateConditionReq`：`patientId, patientVersion, conditionCode, onsetDate?, sourceCode, note?`

### 4.6 方案

`ConfirmPlanReq`：`planVersion, pantryVersion, profileVersion`

## 5. 状态机

### 5.1 RecommendationTaskStatus

`1 PENDING → 2 RUNNING → 3 SUCCEEDED | 4 FAILED | 5 CANCELLED | 6 TIMED_OUT`

### 5.2 PlanStatus

`1 DRAFT → 2 VALIDATED → 3 CONFIRMED → 4 COMPLETED`
旁路：`5 CANCELLED`、`6 EXPIRED`、`7 INTERRUPTED`

### 5.3 MealExecutionStatus

`1 GENERATED → 2 CONFIRMED → 3 PARTIALLY_CONSUMED → 4 CONSUMED`
旁路：`5 CANCELLED`、`6 INVALIDATED`

### 5.4 CookingExecutionStatus

`1 STARTED → 2 IN_PROGRESS → 3 FINISHED`
旁路：`4 ABORTED`、`5 WAITING_REVISION(P4)`

### 5.5 安全事件优先级（工程调度）

1. 急症 STOP
2. 药物/过敏/营养不良
3. 专业目标失效或数据质量
4. 普通偏好变化
5. 库存/口味优化

低优先级不得覆盖高优先级结论。

## 6. 关键事务时序

### 6.1 推荐创建

```text
校验鉴权与患者
 → 幂等插入
 → 单飞锁
 → 写 recommendation_task(PENDING)
 → 入队
 → 返回 recommendationId
```

### 6.2 求解提交前复核

```text
读取任务
 → 锁外：安全、目标、候选、求解、可执行性、Java 复算
 → 短事务：再次读取 profile/patient/rule/target/food/recipe/pantry/intake/killswitch 版本
 → 任一变化 → EXPIRED/FAILED(2602)
 → 原子预留库存
 → 写 plan_version(VALIDATED) + task SUCCEEDED
```

### 6.3 确认方案

```text
校验 plan VALIDATED
 → 检查预留有效
 → plan CONFIRMED / meal CONFIRMED
 → 审计
```

### 6.4 按计划投料（P3）

```text
complete step followPlanExactly=true
 → 写 cooking_actual_ingredient(计划量)
 → 条件更新预留→消耗
 → 步骤完成
 → 末步可 FINISHED
```

### 6.5 摄入

```text
SIMPLE_FOOD: 幂等写 intake + 消耗简单食物预留/库存
COOKED_BATCH: 幂等写 intake，不重复扣原料
 → 更新当日额度投影
```

锁顺序固定：`patient → pantry_lot → reservation → plan → task`，避免死锁。

## 9. 容量与限流（1000 QPS / 日 10 万任务）

### 9.1 目标换算

- 全站 API 合计峰值 **1000 QPS**
- 推荐创建：校验+落库，目标 p95 < 100ms；求解异步
- 日均 10 万推荐任务 ≈ 约 1.2 任务/秒，高峰按 10× 预留

### 9.2 分层保护

| 层 | 配置起点 | 超限 |
| --- | --- | --- |
| 网关在途 | 单实例 1500 | 503 / 1004 |
| 查询限流 | 20/s·账号 | 429 / 1003 |
| 普通写 | 5/s·账号 | 429 |
| 推荐创建 | 2/s·账号 | 429 |
| 库存识别 | 1/s·账号 | 429 |
| 任务在途 | 单实例 200 | 1004 |
| 求解并发 | 单实例 32 | 排队/拒绝 |
| 模型并发 | 单实例 16 / 全局可配 | BUSY 降级 |
| DB 池 | 单实例 30 | 超时失败 |

虚拟线程启用，但以上闸门必须配置；禁止无界队列。

### 9.3 压测验收

1. 混合 1000 QPS：读多写少，HTTP 失败 < 1%
2. 推荐突发：创建接口不阻塞，任务积压可控
3. 幂等重放：无双写
4. Redis 故障：限流降级本机，单飞旁路，行锁兜底
5. 模型变慢：任务超时，不拖垮 DB
6. SSE 慢客户端：有界缓冲 + 断开取消

## 13. 决策重放与拒绝原因

### DecisionReplayService

保存不可变快照或内容寻址数据，不只存版本号：

- 输入画像快照
- 规则/目标/食物/菜谱字节或内容哈希
- 约束集
- 求解器版本与目标层结果
- 最终 plan_version

支持问答：当时为何允许、约束是什么、为何选该菜、现在重算为何不同。

### CandidateRejectionReason

类型化字段，禁止自由 Map：

```text
CandidateRejectionReason
  candidateId
  candidateTypeCode          // recipe/food
  reasonCode                 // allergy/budget/dataQuality/equipment/...
  message
  constraintIds              // List<String>
  capabilityLevel
```

用于用户解释与排障。
