# 食材推荐 Agent 接口实现方案

> 依据 `docs/方案`。外层统一为 `{ "code": 200, "message": "...", "data": ... }`。`code` 不是 HTTP 状态，成功是 200。

**Goal:** 小程序一次调用完成食材标准化、三道菜检索、可选的额度求解和说明生成。模型只能走白名单工具。

**Architecture:** 新增一个回合接口。回合内部是最多 4 轮的循环。每一轮要么调用一个只读工具，要么提交说明。检索和求解的 HTTP 接口保持可单独调用，供页面和评测直接打。

## 1. 已有接口，保持不变

### `GET /api/nutrition/catalog`

已发布食材和菜。小程序启动时拉取。

`data.foods[]`：`id`、`name`、`image`、`seasoning`。

`data.recipes[]`：`id`、`name`、`category`、`cookware`、`step`、`ingredients[]`（`foodId`、`name`、`grams`、`image`）、`nutrition`（`energy`、`protein`、`carb`、`fat`、`fiber`、`sodium`，未知为 `null`）。

### `GET /api/nutrition/catalog/matches?foods=`

`foods` 为逗号分隔的食材编号或中文名。

`data`：

```json
{
  "dishes": [
    {
      "id": "wl-egg-tomato",
      "name": "番茄炒蛋",
      "energy": 250,
      "score": 100,
      "reason": "主料都有：鸡蛋、西红柿。",
      "bring": "",
      "step": "西红柿切块，鸡蛋打散。"
    }
  ],
  "unrecognized": ["火星菜"],
  "fallback": ""
}
```

没有通过门槛时 `dishes` 为空，`fallback` 为「没有主料齐全的已发布菜，不会另外编一道。」

### `GET /api/nutrition/catalog/day`

查询参数：`sex`（1 男，2 女）、`age`、`activity`（1 轻，2 中，3 高）、`mode`（`cut`、`keep`、`gain`）、`foods`（可选，逗号分隔编号）。

`data`：

```json
{
  "energyTarget": 1743,
  "breakfast": [{ "id": "wl-oat-milk", "portions": 1, "energy": 279, "ingredients": [{ "foodId": "54", "name": "燕麦片", "grams": 40 }] }],
  "lunch": [],
  "dinner": []
}
```

配不出时 `code` 非 200，`message` 为「按这个额度和食材配不出完整的一天」。未满 18 岁、或 65 岁以上且活动量为 3，同样失败，不返回菜。

### `GET /api/nutrition/catalog/foods/{id}/image`

`id` 为 1 到 6 位数字。返回 `image/jpeg`。否则 404。

### `GET /api/nutrition/recipes/{recipeId}/versions/{version}`

读取某一个已发布版本的配料和步骤。`read_recipe` 工具调用它，不新写一套查询。

## 2. 新增回合接口

### `POST /api/nutrition/agent/turns`

请求：

```json
{
  "foods": ["番茄", "鸡蛋"],
  "profile": { "sex": 2, "age": 30, "activity": 2, "mode": "cut" },
  "text": ""
}
```

`foods` 必填，至少一项。`profile` 可空；为空则不调用 `solve_day`。`text` 只用于最后的说明，不参与能不能做。

响应 `data`：

```json
{
  "dishes": [],
  "unrecognized": [],
  "fallback": "",
  "day": null,
  "explanation": "主料都有：鸡蛋、西红柿。",
  "toolCalls": ["normalize_ingredients", "search_dishes"]
}
```

`day` 在调用了 `solve_day` 时才有值，结构与 `/catalog/day` 的 `data` 相同。`explanation` 来自模型。模型超时或返回空时，有菜则以「模型超时，已按食材规则给出。」加上规则理由或锁定克数；没有菜则为「模型超时。没有主料齐全的已发布菜，不会另外编一道。」JSON 不合格且修复次数用完时，用已经拿到的检索理由或求解器锁定克数拼接。

失败：

- `foods` 为空：`code` 非 200，`message` 为「先给出至少一种食材」。
- 工具循环超过 4 轮仍无合格说明：仍返回 200，`explanation` 用兜底文案，`toolCalls` 保留已调用记录。
- 主模型和兜底模型都超时：仍返回 200，改走食材规则或只给上面的超时提示。

这个接口不要求 `Idempotency-Key`。它不写计划、不写摄入。

## 3. 工具接口

工具不单独暴露给小程序。循环按下面的 JSON 调用，参数和返回都是结构体。

### `normalize_ingredients`

请求：`{"tool":"normalize_ingredients","foods":["番茄","火星菜"]}`

返回：

```json
{ "ids": ["138"], "unrecognized": ["火星菜"] }
```

编号来自食材表的中文名，以及固定同义词：番茄、西红柿 → `138`；鸡蛋 → `580`；鸡胸、鸡胸肉 → `405`；北豆腐、豆腐 → `606`。对不上的词只出现在 `unrecognized`。

Java：`DishRecommendService.normalize(List<String> foods): Normalized`

```java
public record Normalized(List<String> ids, List<String> unrecognized) {}
```

### `search_dishes`

请求：`{"tool":"search_dishes","ids":["138","580"]}`

返回：与 `/catalog/matches` 的 `data` 相同。`ids` 为空时 `dishes` 为空，`fallback` 为拒绝文案。

Java：已有 `DishRecommendService.match`。回合里改为先 `normalize`，再把编号交给排序器，避免中文名再解析一次。

硬门槛和规则分不变：主料覆盖率必须为 1；起始 100，每个需自备辅料扣 15，低于 40 不返回；最多 3 道。油、盐、生抽编号 `654`、`668`、`672` 是常备。

### `read_recipe`

请求：`{"tool":"read_recipe","id":"wl-egg-tomato"}`

返回：

```json
{
  "id": "wl-egg-tomato",
  "name": "番茄炒蛋",
  "version": "1",
  "step": "西红柿切块，鸡蛋打散。",
  "ingredients": [{ "foodId": "138", "name": "西红柿", "grams": 200, "staple": false }],
  "energy": 250
}
```

菜不存在或未发布时返回 `{"found":false}`。不返回草稿。

Java：`DishRecommendService.recipeCard(String id)`，内部读 `CatalogBrowse.findRecipe`。只读当前已发布版本。未发布返回 `{"found":false}`。

### `solve_day`

请求：

```json
{
  "tool": "solve_day",
  "sex": 2,
  "age": 30,
  "activity": 2,
  "mode": "cut",
  "ids": ["138", "580"]
}
```

返回与 `/catalog/day` 的 `data` 相同。参数不合法或求解无解时返回 `{"solved":false,"message":"..."}`，循环把这句话写入兜底，不再重试求解。年龄、活动和目标以请求里的 `profile` 为准。模型在工具参数里改这些数字不会被采用。

Java：已有 `DayMenuService.plan(int sex, int age, int activity, String mode, List<String> ownedFoodIds)`。

### `read_meal_facts`

请求：`{"tool":"read_meal_facts"}`

返回当前回合已经锁定的食材和克数。没有调用过 `solve_day` 时返回空数组。

### `read_long_term_memory`

请求：`{"tool":"read_long_term_memory"}`

返回：

```json
{ "conditions": [], "medications": [], "measurementStopsPlanning": false }
```

没有患者上下文时三项皆空。病情和用药只供说明引用，不参与 `search_dishes` 的过滤。

## 4. 模型每一轮的协议

模型每一轮只能返回下面两种 JSON 之一。

调用工具：

```json
{ "tool": "search_dishes", "ids": ["138", "580"] }
```

提交说明：

```json
{
  "explanation": "主料都有：鸡蛋、西红柿。",
  "items": [{ "foodItemId": "138", "grams": "200" }]
}
```

`items` 必须与 `solve_day` 锁定的食材和克数逐项相同。没有求解时，`items` 必须为空数组。多一个、少一个或克数不同，算一次内容错误，克数保持锁定值。

工具名不在白名单时，返回「工具不在白名单，不能修改目标、方案、摄入或用药。」并记一次内容错误。禁止的名字是 `update_target`、`confirm_plan`、`record_intake`、`change_medication`、`relax_constraint`。

## 5. 循环顺序

系统先执行 `normalize_ingredients`。用户的 `text` 只放进说明提示，不参与能不能做。

测试里没有传入模型时，不进入循环，直接执行：

1. `search_dishes`
2. 有 `profile` 时调用 `solve_day`
3. `explanation` 使用每道菜的 `reason`；有求解结果时改用锁定克数原文

线上默认有模型。一次完成调用的顺序是：

1. 主模型 `deepseek-v4-pro`。读超时再叫一次。
2. 还超时，并且 `fallback-model-name` 有值，就调用兜底模型 `qwen4-max`。
3. 再超时或返回空：还没检索过就执行上面的规则顺序。有菜时说明以「模型超时，已按食材规则给出。」开头。没有菜时说明为「模型超时。没有主料齐全的已发布菜，不会另外编一道。」
4. 模型有返回时，系统把规范化结果放进短期记忆，再让模型选择后续工具。`search_dishes` 的 `dishes` 为空则停止。格式错误、内容错误各最多 1 次，模型调用最多 4 次。

调用实现是 `TwoModelChain` 加 Spring `RestClient`，不是 Spring AI 或 LangChain4j。`ModelCompletion` 是以后替换模型客户端的接口。

## 6. 小程序

`miniprogram/utils/api.js` 增加 `turn(foods, profile)`，请求 `POST /api/nutrition/agent/turns`。

家里有什么页的「推荐三道」改为调用 `turn`。有年龄资料时带上 `profile`，响应里的 `day` 写入当天三餐；没有年龄时只展示 `dishes`。`fallback` 和 `unrecognized` 仍显示在列表上方。

今日页继续只消费 `day` 的早、午、晚和克数，不自己再排一次。

## 7. 测试

- `IngredientDishRankerTest`、`IngredientMatchEvaluationTest` 继续作为规则分和离线评测。
- 新增回合测试：食材为「番茄、鸡蛋」时，`toolCalls` 含 `normalize_ingredients` 和 `search_dishes`，`dishes` 含 `wl-egg-tomato`，且没有模型时 `explanation` 非空。
- 新增拒绝测试：食材只有「火星菜」时，`dishes` 为空，`unrecognized` 含该词，`fallback` 非空。
- 新增锁定测试：模型把克数改掉时，返回的说明仍使用求解器克数。
- `TwoModelChainTest`：主模型超时重试一次；第二次仍超时才调用兜底模型；兜底模型也超时则返回空。
- 模型返回空时，食材「番茄、鸡蛋」仍返回 `wl-egg-tomato`，说明含「模型超时」和规则理由。只有「火星菜」时菜为空，说明含「不会另外编一道」，且不复述用户原话。
