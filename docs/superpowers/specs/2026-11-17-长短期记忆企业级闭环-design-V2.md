状态：**工程基线（待审确认后按本文施工）**  
版本：V2.0  
继承：`2026-11-17-长短期记忆企业级闭环-design.md`（V1）  
修订依据：`docs/superpowers/specs/记忆优化方案`（评审：保留架构，补齐正确性/一致性/治理）  

原则：**不推翻**长期事实链 + 短期快照 + 工作记忆 + 旁路抽取 + 确定性推荐；**不上** Graph / Mem0 / Zep 运行时。  
最终闭环：`表达 → 理解 → 确认 → 存储 → 更新 → 消费 → 推荐 → 问答 → 纠错 → 审计 → 删除`。

## 0. 背景与技术线路

### 0.1 业务背景

慢病/减重用户通过对话报食材、改口味、问「以前/现在不喜欢什么」。系统必须记住结构化事实，且改口后推荐与问答一致；克数与临床安全仍由 Java/档案主导。

### 0.2 现状与缺口（相对 V1 实现）

| 已有方向 | V2 必须补齐 |
| --- | --- |
| 三层记忆、旁路抽取、时效事实 | 语义模型（中性/条件/临时/多主体/撤销） |
| AVOID 默认过滤 | 强度分级；与临床硬过滤分离 |
| owner 锁、epoch | DB 事务、幂等、多实例缓存一致 |
| session→patient 合并 | 身份归属、幂等合并、失败回滚 |
| source + utteranceRef | 事实 / 事件 / 审核三表；证据与隐私策略 |
| T1–T12 故事 | 状态机、并发、纠错、隐私验收 |

### 0.3 技术线路（不变 + 强化）

| 层级 | 选型 |
| --- | --- |
| 服务 | Java 21、`nutritionist-service` |
| 编排 | `DialogueOrchestrator`：先旁路记忆，再主理解与执行 |
| 抽取 | `MemoryExtractor` → 结构化 `MemoryEvent`（§19） |
| 临床长期 | `ClinicalRecordService` + MySQL |
| 偏好长期 | `PreferenceStore` + 三表（§20/§21） |
| 会话 | 开发可 JVM；**生产以 Redis+epoch 为准**，MySQL 为偏好权威源 |
| 模型 | 现有 `ModelCompletion` / 主备链；抽取失败不脏写 |

```text
用户话
  → MemoryExtractor
  → Schema/归一/冲突/门禁
  → 【事务】关旧+开新+写 event + bump epoch
  → 提交成功后刷新 Session（Redis）快照
  → IntentUnderstander → Planner → Executor
       （硬约束齐全后再偏好过滤/降权/求解）
```

## 1. 目标与非目标

### 1.1 目标

分层清晰；结构化；时效；可问答（含变化类查询）；旁路写入；硬软分离；可审计可纠错；可多实例部署；记忆与推荐一体验收。

### 1.2 非目标

聊天摘要当事实；口语自动升过敏；Graph/Mem0/Zep 接管；偏好突破病情/过敏/主料；无审核全量重跑历史对话覆盖事实。

## 3. 长期记忆（V2 修正）

### 3.1 临床硬事实（A）

不变：病情、已确认过敏、用药、测量禁配餐、医嘱忌口。闲聊不自动升格。

### 3.2 饮食偏好事实（B）— 极性与类型拆开

```text
PreferenceFact
  ownerId, subject, subjectType(FOOD|CUISINE|TAG)
  polarity(LIKE|AVOID|NEUTRAL)     // 不再把 CUISINE/TAG 放进 polarity
  strength(ABSOLUTE|STRONG|MODERATE|WEAK)
  scope(PERMANENT|TEMPORARY|CONDITIONAL|TURN)
  conditionJson?                   // scope=CONDITIONAL 时
  validFrom, validTo               // null validTo = 现行
  source, eventId, version
```

**互斥（FOOD）**：同一 owner+subject 现行集合中，LIKE / AVOID / NEUTRAL 至多一条有效口味极性；新事件关闭旧现行。  
**NEUTRAL**：表示「不再厌恶/不再强调喜欢」，**不等于 LIKE**。  
**CUISINE/TAG**：用 subjectType 区分；「只吃粤菜」关闭其他现行 CUISINE。

### 3.3 强度 → 推荐消费（修正 V1「AVOID 默认 ABSOLUTE 全过滤」）

| 表达倾向 | strength | 推荐策略 |
| --- | --- | --- |
| 绝对不吃 / 别放 / 不要给我 | ABSOLUTE | 偏好硬过滤（仍非临床过敏） |
| 非常讨厌 | STRONG | 强降权；用户设置可升为过滤 |
| 不喜欢 | MODERATE | 默认降权 |
| 不太喜欢 / 偶尔可以 | WEAK | 轻度降权或不排除 |
| 过敏 / 绝对不能（医疗口吻） | — | **allergySuspects**，确认后进临床 |

临床安全过滤与偏好过滤**两套机制**，禁止混用。

### 3.4 投影与问答（扩展）

| 查询 | 数据 |
| --- | --- |
| 现在不喜欢 | current AVOID |
| 曾经不喜欢 / 以前不喜欢 | pastAvoids（含仍现行，产品默认） |
| 以前不喜欢现在喜欢 | 历史 AVOID ∩ 当前 LIKE |
| 以前喜欢现在不喜欢 | 历史 LIKE ∩ 当前 AVOID |
| 最近改过哪些 | 事件时间序 |
| 何时开始不喜欢 X | event/fact 的 validFrom / appliedAt，禁止 LLM 猜 |

推荐：**仅 current 且未过期**；TURN/已到期 TEMPORARY 不参与。

### 3.5 写入路径（带门禁）

```text
抽取 → Schema → 归一 → 冲突检查 → 确认门禁
  → 【单事务】写 fact + event + epoch
  → 提交成功
  → 再刷新 Session / 失效缓存
禁止：未提交成功就让推荐读到新偏好。
```

## 4. 短期记忆（V2 修正）

### 4.1 字段

同 V1，并强制：

- `preferenceEpoch`、`clinicalVersion` **分离**  
- `revision` 用于会话过程态并发  
- 菜列表项可带状态：`VALID | INVALIDATED | REPLACEMENT_PENDING | REPLACED | NO_FEASIBLE_REPLACEMENT`

### 4.2 匿名合并（替换「仅较新覆盖」）

`mergeSessionToPatient(sessionId, patientId, actor)` 必须满足：

| 规则 | 要求 |
| --- | --- |
| 鉴权 | 仅账号拥有该 patient 的主体可合并 |
| 多患者 | 记忆归属 `targetOwner`；禁止写入错误 patient |
| 幂等 | mergeId；重复合并无副作用 |
| 事务 | 全部成功或全部回滚 |
| 冲突 | 服务端事件序 + version；冲突则重试或失败 |
| 审计 | 保留 session→patient 关系；匿名数据按策略归档 |
| 绑定 | 已绑定其他 patient 的 session 禁止误合并 |

### 4.3 多实例

生产禁止依赖单机 JVM Session 权威。Redis 存会话；每次消费前若 `localEpoch < storeEpoch` **强制重载**；失效通知丢失时靠 epoch 兜底。

## 6. 运行时总流程（V2）

```text
1 鉴权与 owner/targetOwner 解析
2 MemoryExtractor(text)
3 校验管道（§23）
4 事务写入 PreferenceStore（成功才继续）
5 刷新/重载 Session 快照（epoch）
6 处理 queries → memoryAnswer（模板）
7 IntentUnderstander → Planner
8 Executor：
   8a 全部硬约束（禁配餐/过敏/病情/主料/已发布）
   8b 偏好 ABSOLUTE 过滤
   8c 软偏好降权排序
   8d 求解（若需要）
   8e 若新 AVOID 命中已荐菜 → 增量替换状态机（§10）
9 返回；客户端显式 avoidFoods 写入须鉴权且 source=client，可信等级低于 utterance+confirm
```

**说明**：§8 优先级是业务优先级，不是代码循环顺序；硬约束阶段必须在软偏好与求解前完成。

## 7. MemoryExtractor 契约（V2）

```json
{
  "events": [{
    "op": "ASSERT|REPLACE|RETRACT|CONFIRM|CORRECT",
    "subject": "海带",
    "subjectType": "FOOD",
    "polarity": "AVOID|LIKE|NEUTRAL",
    "strength": "ABSOLUTE|STRONG|MODERATE|WEAK",
    "scope": "PERMANENT|TEMPORARY|CONDITIONAL|TURN",
    "validFrom": null,
    "validTo": null,
    "condition": null,
    "targetOwner": null,
    "confidence": 0.92,
    "evidence": "不喜欢吃海带"
  }],
  "queries": [
    { "type": "CURRENT_AVOID|PAST_AVOID|AVOID_THEN_LIKE|LIKE_THEN_AVOID|WHEN_CHANGED", "subject": null }
  ],
  "turnOnlyHints": ["清淡"],
  "allergySuspects": [],
  "needsDisambiguation": null,
  "eventId": "idempotent-key"
}
```

- 同句多 event：按**语义**排序（改口/转折优先于机械文本序）；冲突无法消解则 disambiguation。  
- 「没有可乐」→ 不进 events；主路径 MISSING。  
- 「这顿/今天」→ TURN 或 turnOnlyHints。  
- 置信度只是门禁之一；还须过归一、归属、scope 校验。

## 8. 约束优先级与执行阶段

**业务优先级（高→低）**  
禁配餐 > 过敏/医嘱 > 病情适合 > 主料/已发布 > AVOID(ABSOLUTE) > 软降权 LIKE/强度 > 短期 hints。

**执行阶段**  
硬约束全集通过 → 偏好过滤 → 软排序 → 求解；已确认/烹饪中菜品不自动静默替换（见 §10）。

---

## 9–10. 场景与增量换菜（V2 补强）

保留 V1 T1–T12，并增加：

**增量换菜状态机**

```text
VALID → INVALIDATED → REPLACEMENT_PENDING → REPLACED
                    ↘ NO_FEASIBLE_REPLACEMENT
```

规则：

1. 被替换菜号加入本会话 exclude。  
2. 新菜重跑全部硬约束 + 现行偏好。  
3. 必要时重求解克数；禁止为凑三道突破安全。  
4. 与已荐菜去重。  
5. 无可行替代：保留 INVALIDATED 标记并说明，不返回违规菜当合格结果。  
6. 已确认/制作中：不自动替换，提示用户确认。  
7. 连续改口：按 epoch 串行，避免重复替换抖动。

## 11. 数据模型（V2 三表）

### 11.1 `diet_preference_fact`

业务现行/历史事实：§3.2 字段 + `event_id` + `version` + `updated_at`。  
并发：owner 级事务；应用层保证同 subject 不允许的多现行；可用生成列/唯一约束辅助。

### 11.2 `diet_memory_event`

变更原因与幂等：`event_id` 唯一；`operation`；`before_state`/`after_state`；`evidence_ref`/`evidence_hash`；`extractor_version`；`status(PENDING|APPLIED|REJECTED|FAILED)`。

### 11.3 `diet_memory_review`

确认/拒绝/纠错：`review_type`；`reviewer_type`；`corrected_value`；`reviewed_at`。

**职责**：Fact=是什么；Event=为何变；Review=是否确认/纠错。

证据策略：优先短 evidence + hash + 限期加密原文；若政策禁止存原文，则仅 hash/引用，并文档声明「无法还原原句」。

## 16. 风险

误抽、脏读未提交偏好、多实例旧快照、合并写错患者、证据与隐私冲突——对策见 §20/§21/§23。

## 17. 成功标准

1. 投影与最后有效事件一致，无非法双现行。  
2. 历史不被物理覆盖删除（除非治理删除）。  
3. 推荐只读已提交现行；epoch 一致。  
4. 硬约束不可被偏好突破。  
5. 纠错后推荐可重校验。  
6. 重载会话结果一致。

## 19. 记忆语义模型（P0）

### 19.1 操作

`ASSERT` 建立；`REPLACE` 替换现行；`RETRACT` 撤销（→ 关旧，可致 NEUTRAL 或无口味）；`CONFIRM` 确认候选；`CORRECT` 纠错。

### 19.2 范围 scope

| scope | 含义 | 过期 |
| --- | --- | --- |
| PERMANENT | 以后都… | 用户改口/撤销 |
| TEMPORARY | 最近/这段时间 | validTo 或默认策略结束 |
| TURN | 这顿/今天 | 会话或自然日结束 |
| CONDITIONAL | 除非做汤… | 条件结构；首版可只存不消费，二期消费 |

「最近」默认窗口可配置（如 14 天），到期关事实并刷 Session；**不**因长期未提及而自动删稳定 PERMANENT。

### 19.3 多主体

`targetOwner` 默认当前 patient；「孩子/老公」无法解析到档案则 **不写入**，请求澄清。

### 19.4 否定

「不再不喜欢 / 无所谓了」→ RETRACT/NEUTRAL，不是 LIKE。

---

## 20. 事实链一致性（P0）

1. owner 级 DB 事务锁或乐观锁（`version`）。  
2. owner 事件序列号单调。  
3. `eventId` 幂等，防 HTTP/模型重试双写。  
4. 关旧+插新+写 event+bump epoch **同事务**。  
5. 禁止非法多现行（应用约束 + 尽可能 DB 约束）。  
6. **提交成功后**再刷新 Redis；刷新失败靠 epoch 强制重载恢复。  
7. JVM 锁仅开发；生产以 DB+Redis 为准。

---

## 21. 记忆治理（P0）

### 21.1 纠错闭环

用户称「我没说过不吃海带」→ 查 event → 查 review → RETRACT/CORRECT → 重投影 → 失效 Session → 重校验已荐菜 → 记 review 事件。

### 21.2 删除与隐私

| 操作 | 处理 |
| --- | --- |
| 修改偏好 | 关旧开新 |
| 撤销 | 关旧 + 审计 |
| 用户删除偏好 | 按策略删或匿名化 |
| 注销 | 偏好与临床分策清理 |
| 会话过期 | 清短期 |
| 审计 | 依法定/企业期限保留 |

临床与偏好删除策略不得混用同一套默认。

### 21.3 质量监控

抽取准确率、错误记忆率、漏提率、归一准确率、冲突率、刷新延迟、问答准确率、错误推荐率、合并冲突率——按 extractor 版本与场景切片。

### 21.4 抽取版本

事实保留 `extractor_version`；Prompt 升级**不**自动重跑覆盖；重处理走迁移任务+审核。

---

## 22. 生命周期管理（P1）

三类过期：明确期限 / 永久待改口 / 未说明则持续但可纠正。  
区分：**事实失效（validTo）** vs **数据删除（治理）**。  
TEMPORARY/TURN 到期 → 关事实 → bump epoch → 刷 Session。

---

## 23. 异常恢复（P0）

管道每步显式失败态：非法 JSON、未知食材、归一歧义、多主体冲突、与历史冲突、主备不一致、写库失败、写成功响应超时（靠 eventId 幂等）。

规则：抽取成功但未提交 → 推荐**不得**见新偏好；超时重试只依赖幂等，不依赖「再抽一次」的偶然一致。

---

## 24. 企业级验收（P0）

在 T1–T12 上扩展：基础/否定/时间/条件/多主体/改口序列/同句冲突/归一/过敏隔离/并发/幂等/超时重试/多实例/合并/历史问答/纠错/过期/隐私/增量换菜/临床不被偏好突破。

**属性不变式**（任意 AVOID↔LIKE↔NEUTRAL 序列）：

1. 当前投影 = 最后有效事件  
2. 无非法双现行  
3. 历史保留（除非治理删除）  
4. 推荐只用已提交现行  
5. 重载会话一致
