# HIS 企业级架构

日期：2026-11-13。状态：临床上下文。工程上的拆分、合并、分层和错误码以同级仓库 `moonligh-platform` 的 `docs/企业架构规范.md` 为准。本文件只保留临床事实的模型、命令和故障行为。服务名是 `clinical-record`。

## 1. 架构决策

| 决策 | 选择 | 原因 |
| --- | --- | --- |
| 病情主人 | 独立临床数据仓库 `clinical-record` | 挂号、食材推荐、报告解读都只是智能体 |
| 写模型 | 追加事实，禁止原地改 | 配餐和解读要能引用当时的版本 |
| 读模型 | 按患者计算的临床快照 | 智能体不查对方的库，也不查 HIS 明细 |
| 契约放哪 | HIS 仓库发布内部 API | 平台仓不放临床模型，避免业务仓互相依赖 jar |
| 平台仓 | 鉴权、Trace、Redis、RocketMQ、错误码号段 | 与现有 `moonligh-platform` 边界一致 |
| 身份 | 只校验账号是否拥有 `patientId` | 诊断不进身份库 |
| 外部医院 | 以后只作为 HIS 的进口适配器 | 三个智能体不直连医院 |

错误码使用新号段 `31xx`，先在平台仓登记后再编码。不占用挂号 `11xx` 和营养 `21xx`。

## 2. 上下文

```text
浏览器 / App
    → 网关（登录、限流、Trace）
        → 智能挂号
        → 食材推荐
        → AI 报告解读
        → 身份服务

三个智能体 --内部令牌--> HIS
身份服务 <-- HIS 只核对接诊人归属
```

| 上下文 | 拥有的数据 | 没有的数据 |
| --- | --- | --- |
| 身份 | 账号、就诊人、`patientId`、`patientVersion` | 诊断、过敏、用药、报告指标 |
| 挂号 | 对话、号源、订单、医生确认动作 | 病情主表 |
| 食材推荐 | 身高、体重、饮食目标、菜谱、方案版本 | 病情主表 |
| 报告解读 | 原文解析任务、白话解读、依据片段 | 病情主表 |
| HIS | 临床事实、当前快照、事实版本 | 号源、菜谱、解读正文、支付 |

## 3. 服务结构

HIS 一个可部署服务，内部分四块。不按云医院拆成处方服务、检验服务和药店服务。

| 块 | 职责 |
| --- | --- |
| 命令 | 校验内部令牌和就诊人归属，幂等追加事实 |
| 事实库 | MySQL 只追加。旧行不更新业务字段 |
| 快照 | 同一事务里根据该患者当前事实生成新快照版本 |
| 出口 | 事务提交后发出「快照已变化」。智能体可丢弃该消息，以主动读快照为准 |

Redis 只缓存「`patientId` + `snapshotVersion` → 快照」。缓存丢失就从 MySQL 再算。Redis 不是事实源。

## 4. 事实模型

一条事实：

| 字段 | 规则 |
| --- | --- |
| `factId` | HIS 生成 |
| `patientId` | 必须能在身份服务核到 |
| `factType` | `DIAGNOSIS`、`ALLERGY`、`MEDICATION`、`OBSERVATION`、`NOTE` |
| `statement` | `PRESENT` 或 `ABSENT`。后者表示「明确没有」，不是空列表 |
| `author` | `DOCTOR`、`PATIENT`、`DOCUMENT` |
| `basis` | 医生事实必须有挂号就诊号。文档事实必须有报告号。患者声明可以没有 |
| `code` | 有编码才写 `codeSystem` 和 `code`。没有编码就只保留展示名，不猜测 |
| `replacesFactId` | 空表示新增。非空表示替代那一条 |
| `recordedAt` | 业务发生时间 |
| `commandId` | 调用方幂等键 |

`NOTE` 只放医生确认后的病历摘要。导诊草稿不进事实库。

当前快照的算法：

1. 取该患者全部事实，按记录顺序。
2. 被替代的事实移出「当前」。
3. 按类型列出仍有效的 `PRESENT` 和 `ABSENT`。
4. 报告只保留最近一份的异常指标名、日期和报告号。
5. 分配新的 `snapshotVersion`。

空列表只表示没有这项事实。

## 5. 命令和查询

浏览器不直接访问 HIS。三个智能体用内部令牌调用。

命令：

- `POST /internal/facts`：追加一条或同一命令里的一组事实。
- 请求带 `commandId`。同一个 `commandId` 再来一次，返回第一次的 `factId` 和 `snapshotVersion`，不追加第二套。

查询：

- `GET /internal/patients/{patientId}/snapshot`
- 可选 `If-None-Match: snapshotVersion`。版本未变返回 304。

智能体展示或配餐时只认这次读到的 `snapshotVersion`。HIS 不回调智能体改它们的方案。

挂号：医生确认这个动作成功后，同一业务事务里写挂号自己的「已确认」状态，并用发件箱投递 HIS 命令。HIS 拒绝时，挂号保持「确认未归档」，可以重放同一 `commandId`。不在挂号库保存诊断正文。

食材推荐：用户声明病情时，营养服务发命令。配餐前读快照。快照没有诊断，按无慢病减重。缺身高或体重，不配个体化餐。营养服务不因为 HIS 短暂不可用而改用本地旧病情表。

报告解读：解读可以先完成。归档指标是完成后的命令。归档失败不删除解读，标记「未进入病情档案」，用同一 `commandId` 重试。解读正文留在报告服务。

## 6. 一致性

| 场景 | 规则 |
| --- | --- |
| 一次命令内的多条事实 | 一个本地事务，同时出现在同一个新快照里 |
| 智能体和 HIS | 至少一次投递加 `commandId` 幂等。不要求分布式事务 |
| 智能体库和命令 | 智能体用自己的发件箱。禁止「远程调用成功但本地事务回滚」后丢失命令号 |
| 已生成的配餐、已发布的解读 | 写下当时的 `snapshotVersion`。以后的事实不改写它们 |
| 快照缓存 | 写入成功后删除该患者缓存。读到旧版本只能因为并发读，调用方以返回体里的版本为准 |

HIS 不保证三个智能体同时看到新快照的时刻相同。每个智能体以自己读到的版本工作。

## 7. 安全

- 网关不把 `/internal/**` 暴露给浏览器。
- 内部令牌与现有平台过滤器相同。令牌只证明调用方是某个智能体，不证明用户可以看这个患者。
- 每个命令和查询都带账号和 `patientId`。HIS 向身份服务核对归属。核对失败不写事实。
- 医生事实还要带挂号给出的医生标识和就诊号。HIS 不核号源，只要求该就诊号由挂号服务签名或由挂号服务自己调用。
- 日志不写病情正文、指标值、姓名和证件号。日志只写 `patientId`、`factId`、`snapshotVersion`、`commandId`、Trace。
- 库内病情按患者分区访问。导出和备份按医疗数据管理，不进 GitHub 仓库。

## 8. 故障

| 故障 | 行为 |
| --- | --- |
| HIS 不可读 | 食材推荐不个体化配餐，返回「病情档案暂不可用」。不用空快照假装无病 |
| HIS 不可写 | 挂号确认保持未归档并重试。报告解读保留未归档。用户声明病情失败则页面失败，不写营养库兜底 |
| 身份服务不可用 | HIS 拒绝新的命令和查询 |
| 重复消息 | `commandId` 命中则返回原结果 |
| 快照缓存损坏 | 丢弃缓存，从事实重算 |

空快照和 HIS 故障是两种响应。故障使用错误码，不返回空列表。

## 9. 运行和观测

部署单元：一个 HIS 进程，一套 MySQL，一套 Redis。与挂号、营养、报告解读分开库。

每个请求带 Trace。指标至少有：命令成功/拒绝、幂等命中、快照读取、身份核对失败、发件箱堆积。不把指标值打进指标标签。

备份恢复后，用事实重放校验当前最大 `snapshotVersion`。不从智能体库回填病情。

## 10. 落地顺序

1. HIS：事实表、幂等、快照、内部查询。无事实时返回空快照。
2. 身份核对接入。
3. 食材推荐改为读快照。停用营养库病情主表作为读路径。
4. 挂号只在医生确认后投递事实。
5. 报告解读只投递脱敏指标。

医院厂商适配器排在这些之后，写成 HIS 内部的进口，不新开智能体。
