# 第一轮语义理解精准识别（专项设计）

状态：**已收敛** → 完整施工稿见 **`2026-11-18-复杂提问第一轮语义理解完整方案-design.md`**（冲突以完整方案为准）。  
日期：2026-11-18  
主目标：**用户任意复杂的一句/一段话，同步链路里那一次理解模型，能稳定产出正确的白名单任务 + 槽位 + 本轮约束。**

原则：

1. **只解决「听懂」**，不在理解器里荐菜、写库、降级。  
2. **单次同步调用**为默认（问餐延迟约束）；不确定时输出可执行的澄清任务，而不是瞎猜。  
3. **精度靠契约 + 上下文 + 金标闭环**，不靠无限堆口头样例。  
4. Java 后处理只做 **合法化与指代补全**，不替代模型做开放域理解。

---

## 1. 要彻底解决的问题

### 1.1 失败模式（线上真实形态）

| 模式 | 表现 | 根因 |
| --- | --- | --- |
| 漏意图 | 「换一个再加个汤」只出其一 | 多标签抽取弱 / 样例不足 |
| 逃域外 | 选菜相关被打成 OUT_OF_SCOPE | 决策树与负例不足 |
| 槽位空/错 | REPLACE 无 dishHint；加汤 kind 空 | 缺会话菜列表或未强制槽位 |
| 约束与任务粘连 | 忌口写进 RECOMMEND 却漏 turnConstraints | schema 边界不清 |
| 复合句拆错序 | 先荐菜后改口，顺序反了 | 缺「原子意图」定义与排序规则 |
| 指代失败 | 「换第二个」不知道换谁 | 入参未结构化槽位 |
| 过度自信 | 歧义仍硬出 RECOMMEND | 缺 confidence / NEED_CLARIFY |

### 1.2 成功定义（可量化）

金标集上（见 §7）：

- **Task-set Exact**：任务类型多重集合完全匹配 ≥ **92%**  
- **Slot Exact**（在类型正确前提下）≥ **90%**  
- **Constraint F1**（avoid/cuisine/tags 等）≥ **88%**  
- **Critical miss**：换菜/加汤/绝对忌口漏检 ≤ **2%**  
- **False OUT_OF_SCOPE**（本应业务）≤ **1%**  
- 同步仍为 **1 次**理解调用（澄清追问算下一轮用户输入，不在本回合加第二次模型）

## 2. 目标架构：理解流水线（单次 LLM）

```text
输入打包 ContextPack
    → 一次 LLM（Structured TurnIntentV2）
    → IntentNormalizer（校验枚举/槽位/去噪）
    → SlotResolver（序数/这个 → dishHint，纯规则）
    → 输出 TurnIntent（给 Planner）
```

- **LLM**：负责开放表述 → 原子意图列表。  
- **Normalizer/Resolver**：负责合法与会话对齐，**不新造业务意图**。  
- 记忆抽取仍异步，不进本流水线。

---

## 3. ContextPack（给模型的「眼睛」）

第一轮也不是裸原文；复杂识别依赖结构化上下文。

| 字段 | 内容 | 作用 |
| --- | --- | --- |
| `utterance` | 用户原文 | 主信号 |
| `requestFoods` | 请求体食材 | 显式食材 |
| `currentDishes` | `[{index:1,name,id},…]` | 换菜/指代 |
| `phase` | IDLE/RECOMMENDED/… | 抑制乱荐菜 |
| `preferenceSummary` | 忌口/绝对/菜系/标签/病情/过敏，空=无，≤5 | 勿重复编造；助绝对/普通分级 |
| `lastFocusedDish` | 上轮焦点菜 | 「这个/那个」 |
| `domainHint` | 固定：食材选菜助手 | 降域外漂移 |

打包规则：总量控制（摘要截断）；**禁止**把整本菜谱或长对话塞进 prompt。

## 4. 输出契约 TurnIntentV2（精准识别核心）

相对现网增强三点：**原子化、置信度、澄清**。

```json
{
  "tasks": [
    {
      "type": "REPLACE_ONE",
      "dishHint": "水煮蛋",
      "dishIndex": 1,
      "confidence": 0.86
    }
  ],
  "turnConstraints": {
    "avoidFoods": ["香菜"],
    "absoluteAvoidFoods": [],
    "cuisine": "",
    "kind": "",
    "preferTags": ["清淡"],
    "turnHints": ["少油"]
  },
  "ambiguities": [
    {
      "code": "DISH_REF",
      "options": ["水煮蛋", "番茄炒蛋"],
      "ask": "要换哪一道？"
    }
  ]
}
```

### 4.1 原子意图规则（强制写进系统说明）

一句话拆成 **多个互不吞并的原子 task**：

- 「不吃香菜 + 推荐」→ `turnConstraints.avoidFoods` + `RECOMMEND`（忌口不是 task）  
- 「换 A + 加汤」→ `REPLACE_ONE` + `ADD_KIND` 两条  
- 「没有土豆了」→ `MISSING`，不要改成 RECOMMEND  
- 只有天气/闲聊等才 `OUT_OF_SCOPE`；**选菜相关禁止域外**  

### 4.2 类型与槽位硬表

| type | 必填槽位 | 识别触发（语义，非正则主路径） |
| --- | --- | --- |
| GREETING | — | 纯问候 |
| RECOMMEND | rawFoods（可空若仅约束） | 要做什么/推荐/家里有 |
| REPLACE_ONE | dishHint 或 dishIndex | 换、不想吃这道、换成别的 |
| ADD_KIND | kind | 再加汤/主食/菜 |
| MISSING | missingFood | 没有/缺了某食材 |
| SUBSTITUTE | fromFood, toFood | 用 B 代 A |
| OUT_OF_SCOPE | topic | 非选菜 |
| NEED_CLARIFY | （由 ambiguities 表达） | 槽位不可唯一确定 |

`NEED_CLARIFY`：可作为 task type **或**仅用 `ambiguities` 非空表示；实现二选一，建议 **ambiguities 非空 ⇒ Planner 只澄清、不执行找菜**。

### 4.3 confidence 策略

- `confidence < 0.55`：该 task 丢弃或降为澄清，不得执行写菜  
- 多候选指代：不填死 dishHint，填 `ambiguities`  
- 绝对忌口：宁可进 `absoluteAvoidFoods` 偏严，不可漏（安全优先）

## 5. Prompt 工程（为复杂句服务，而非堆样例）

### 5.1 结构（固定五段）

1. **角色与禁止项**  
2. **原子拆分规则 + 决策树**（OUT_OF_SCOPE 最后）  
3. **槽位硬表**  
4. **金标驱动的动态 few-shot**（见 §5.2）  
5. **ContextPack + 只输出 JSON**  

### 5.2 动态 few-shot（企业级关键）

不要把 50 条样例写死在代码字符串里。

- 金标库按桶：`multi_intent` / `anaphora` / `replace` / `add_kind` / `constraint` / `oos` / `missing`…  
- 每次调用 **检索 4～8 条**最相近金标（字面/embedding 均可，首版可用关键词桶 + 轮转）  
- 样例格式：输入 Context 摘要 → 标准 JSON  
- 改 prompt 文案与改金标 **同一 PR**  

### 5.3 负例（必须有）

- 「换一个」≠ OUT_OF_SCOPE  
- 「再加点汤」≠ RECOMMEND 全新三道  
- 「不太喜欢香菜」≠ absoluteAvoid  
- 「绝对不能吃虾」≠ 普通 avoid

## 6. 模型侧后处理（不第二次调用）

### 6.1 IntentNormalizer

- 非法 type 丢弃；空 tasks 且非问候 → 薄兜底（有 foods→RECOMMEND，否则引导重说，**慎用 OUT_OF_SCOPE**）  
- 空字符串槽位剔除  
- 历史偏好抄进 constraints 的重复项去掉  
- dishIndex 越界丢弃并转 ambiguities  

### 6.2 SlotResolver（规则）

- `dishIndex=2` → 映射 `currentDishes[1].name`  
- 「这个/那个」+ lastFocusedDish  
- 「换一个」且仅一道菜 → 自动 dishHint  
- **不做**开放域菜名猜测  

说明：Resolver 提高「槽位精准」，不解决「类型漏检」；类型漏检靠模型+金标。

## 7. 金标与评测（彻底解决的手段）

### 7.1 金标规模与分布（理解专项）

| 桶 | v1 条数 | 说明 |
| --- | --- | --- |
| 多意图复合 | 25 | 忌口+荐菜+换菜+加汤组合 |
| 指代/序数 | 15 | 第二个、这个、换一个 |
| 约束分级 | 15 | 绝对 vs 普通、菜系、清淡 |
| 增量单意图 | 15 | 纯换/加/缺/代替 |
| 域外与问候 | 10 | 负例 |
| 改口/撤销表述 | 10 | 识别为约束变化（任务或 constraints） |
| **合计** | **≥90** | 专测理解，不跑全链路 |

每条含：`context_pack` + `utterance` + `expect_tasks` + `expect_constraints` + `critical` 标记。

### 7.2 评测层级

| 级 | 内容 | 门禁 |
| --- | --- | --- |
| U1 | Normalizer/Resolver 单测 | PR 必过 |
| U2 | 金标：注入「标准模型 JSON」测后处理 | PR 必过 |
| U3 | 金标：真模型打分（Task-set / Slot / Constraint） | 合入理解改动必跑；未达标不合并 prompt |
| U4 | 线上抽样周报 | 运营 |

**没有 U3 达标，不算「彻底解决」。**

### 7.3 误差分析流程

每周：抽 False OOS / 漏 REPLACE / 漏 ADD → 归桶 → 补金标 → 更新动态 few-shot → 复测 U3。

## 8. 模型与调用策略

### 8.1 默认

- 现网主模型，`temperature` 尽量低（建议 0～0.2）  
- 超时：沿用问餐预算；失败 → 薄兜底，打点 `understand.fail`  

### 8.2 可选增强（需单独批准）

| 选项 | 收益 | 代价 |
| --- | --- | --- |
| A. JSON Schema / 约束解码（若网关支持） | 格式稳 | 依赖供应商 |
| B. 专用小模型微调（金标≥500 后） | 长尾稳 | 训练与发布成本 |
| C. 疑难二次调用（仅 ambiguities 非空时） | 极限精度 | **打破单次同步**；默认不做 |

本设计默认 **A 可做、B 中期、C 默认关闭**。

## 9. 与总纲的关系（范围切割）

| 本专项负责 | 不归本专项（理解准了再做） |
| --- | --- |
| ContextPack / TurnIntentV2 / Prompt / 动态 few-shot | ConflictPlanner 优先级细节 |
| Normalizer / SlotResolver | 召回降级阶梯 |
| 理解金标 U1–U3 | 记忆异步指标、warmup 产品态 |
| confidence / ambiguities | EMPTY_GUIDE 运营文案 |

理解不准时，上 Planner 只是把错意图执行得更「顺」，**不能**冒充听懂。

## 10. 分期（仅理解精准）

| 期 | 交付 | 完成定义 |
| --- | --- | --- |
| **U-P0** | ContextPack 含有序菜列表+phase；契约补 dishIndex/confidence/ambiguities；Normalizer+Resolver | 单测绿；Accept 换菜/加汤不回退 |
| **U-P1** | 理解金标 ≥90；动态 few-shot；U3 真模型报表 | Task-set ≥92% 或达阶段目标并公示缺口 |
| **U-P2** | 误差周报流程 + 负例库；可选 JSON Schema | Critical miss ≤2% |
| **U-P3** | 评估是否微调专用理解模型 | 立项材料：金标≥500、U3 平台期 |

## 11. 验收清单

- [ ] 复杂复合句金标：多 task 不合并、不漏换菜/加汤

- [ ] 歧义指代 → ambiguities，不硬执行  
- [ ] 绝对忌口进 absoluteAvoidFoods，普通不吃进 avoidFoods  
- [ ] 选菜相关 False OOS ≤1%（U3）  
- [ ] 同步路径仍 1 次理解 LLM  
- [ ] 改 prompt 必须带金标 diff + U3 报告
