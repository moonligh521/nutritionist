# 食材推荐基础设计

日期：2026-11-10

状态：已被 `2026-11-10-safe-nutrition-recommendation-design.md` 替代。本文件保留早期场景、竞品和开源项目调研，不作为实现基线。仓库仍只有骨架提交 `c1f58b4`，本文内容不是已经实现的代码，也不采用简历里的实现方式和指标。

## 要做的事

给必须按身体状态控制食物摄入的人推荐食材。可以只问一餐，也可以排一整天。只问晚餐时，先扣掉今天已经吃的，再用剩下的额度。

这个人的病、用药、过敏忌口、家里食材、每次测量和已经确认的吃法会一直留着。他可以每天测完后上报。系统看最新结果，决定这一餐或之后的餐改不改。允许维持原方案。

病和病的差别只在控哪些数。多种病同时存在时，取更紧的额度。热量和成分来自成分表。模型只在额度内把食材写成固定 JSON：饮食画像、核心原则、食谱表。偏好和限制冲突时，在额度内改做法、分量和搭配。Java 校验热量、宏量营养素、钠、禁忌成分和药物相关禁忌；不过就只重算这一餐。

方案确定之后，才从膳食指南抽出处，或回答「这个病能不能吃某样」。检索结果不决定克数，也不决定能不能过线。

本项目提供饮食信息整理，不能替代营养师或医师的个体化医嘱。

## 场景

场景分两层：人怎么用，以及哪种病会改额度。

### 人怎么用

| 场景 | 人拿到什么 | 这一版 |
| --- | --- | --- |
| 只问一餐 | 这一餐的食材、克数、做法，以及这一餐用掉后还剩的额度 | 第一批 |
| 排一整天 | 早、中、晚，需要时加一餐 | 第一批 |
| 今天已经吃过 | 先从当天额度扣掉，再推荐还没吃的餐 | 第一批 |
| 长期跟着同一个人 | 病、用药、过敏忌口、家里食材、测量和已确认吃法留着，下次接着用 | 第一批 |
| 上报新测量 | 血糖、体重等写进档案；可以改后续餐，也可以维持 | 第一批做血糖和体重 |
| 偏好和限制冲突 | 不放宽额度，只改做法、分量、搭配 | 第一批 |
| 家里有什么 | 优先用现有食材填额度 | 第一批 |
| 方案确定后要出处 | 从膳食指南抽出处 | 产品要有，第一批代码后做 |
| 这个病能不能吃某样 | 回答能不能吃，并在额度内给替换 | 产品要有，第一批代码后做 |

没说今天吃过什么时，只按这一餐自己的额度推荐，并标明其他餐还没计入。

### 哪种病会改额度

产品边界是：会改变摄入额度的成人慢病。依据是国家卫生健康委已经发布的成人食养指南，以及 2024 年四类慢性病营养和运动指导原则。儿童、孕产、生长迟缓不在这套里。

| 病种 | 额度要控的数 | 上报什么才会考虑改额度 | 这一版 |
| --- | --- | --- | --- |
| 减重 / 肥胖 | 热量缺口、蛋白质下限 | 体重 | 第一批 |
| 血糖高 / 糖尿病 | 每餐碳水、升糖、热量 | 血糖 | 第一批 |
| 高血压 | 钠 | 血压 | 后补 |
| 高脂血症 | 脂肪供能、热量 | 血脂 | 后补 |
| 高尿酸血症 / 痛风 | 嘌呤，并限制高果糖和酒 | 尿酸 | 后补 |
| 慢性肾病 | 按分期控能量、蛋白质、钠、钾、磷；水肿时再控盐和水 | 肾功能、血钾、血磷 | 后补 |

第一批如果同一个人既要减重又血糖高，两套额度一起生效，取更紧的限制。高血压、血脂、痛风、慢性肾病用同一套「上报 → 决定改不改 → 只重算受影响的餐」，规则后补。

具体克数和临床阈值不在这份基础设计里定死，放到后面的规则规格。药物相关饮食禁忌做成校验条目，具体药品表另写。

### 食谱和食物库

薄荷健康公开的饮食能力最完整。食物库、饮食分析、一周带量食谱都有。定制维度包括减重、增重、保持体重、偏好、禁忌、地域口味、高血压和高血糖。食谱可以是单餐、一天或多天，并按已经记录的饮食调整后续安排，不喜欢的菜可以替换。慢病分析写了糖尿病屏蔽高 GI、高血压看钠、按疾病调整推荐摄入量。精选食谱里还有得舒食谱、骨质疏松、无麦麸、孕期和婴幼儿。公开页没有把痛风嘌呤、慢性肾病的钾磷蛋白写成专属额度，也没有写「测完血糖后可以不改方案」。

### 控糖工具

清汤健康做 GI 查询、拍照识别、控糖食谱、血糖分析和连续血糖同步，异常时给调整建议。公开介绍集中在控糖。

糖护士把指血和多家动态血糖仪的数据放在一起，并按最新血糖、习惯和身体状况给 AI 建议，另有饮食、运动、监测任务。公开文章没有写按成分表生成带克数的一餐或一天。

Undermyfork 把餐食照片和 CGM、FGM 或指血对上，计算每餐之后的达标时间，标出适合重复和拉出目标的餐。它回答的是「这顿吃完以后怎么样」，不是事先按额度写克数。

January 用食物库和人口学信息预测血糖，可以不戴传感器；戴了连续血糖仪会更个体化。健康状态分成普通人、糖尿病前期和 2 型糖尿病，食物按预测升糖给低、中、高。AI 教练可以结合用药回答下一餐吃什么。公开页写的是升糖预测，不是多病种摄入上限。

Levels 把记餐、连续血糖、化验和习惯放在一起，看食物、睡眠和运动怎样影响血糖，再给下一步建议。

### 医院饭方和减重门诊

智膳饭方由医院侧的营养评估加上华佗 GPT，算出一日总热量、三餐能量和蛋白质、脂肪、碳水化合物克数，医生确认后，匹配维小饭已经做过熟制检测的菜品。用户可以自己做，也可以点餐。公开报道写明先做体重和糖尿病，其他专病随后做。这是最接近「先算额度、再落到食物」的产品。差别在于食物来自他们的菜品库和中央厨房，报道没有写家里现有食材，也没有写每天测完血糖后可以维持原方案。

京东健康要分开看。2025 年 6 月报道的 AI 营养师，公开案例是母婴喂养、辅食和商品推荐。2025 年 3 月的减重门诊由医生和营养师制定饮食与运动方案，可以同时管慢病，并提供司美格鲁肽相关检测。2025 年 4 月的体重管理专区是科普、评估、就医地图和预约。这些都不是一份可计算的食材额度。

### 运动应用上的饮食生成

Keep 在 2025 年 3 月上线 AI 营养师小程序。输入身高、年龄、体重目标、饮食偏好和身体状况，生成带食材、摄入量和烹饪方式的餐单；减脂按热量缺口来。可以拍照看热量，并和 Keep 的训练计划联动。公开稿没有写钠、嘌呤、钾、磷，也没有写按当天已吃扣剩余额度。

### 海外诊所和教练

Virta 针对 2 型糖尿病和减重，由教练和医生跟着，用血糖仪、酮仪和个体化营养方案。Noom 的糖尿病项目用年龄、性别、BMI 和代谢状态预测餐后血糖，公开说明可以不依赖连续血糖仪。Omada 通过雇主或保险提供体重、糖尿病、高血压的教练和连接设备。这类产品把饮食放在教练或诊疗旁边，公开资料没有按中国膳食指南做多病种额度校验。

## 和这些产品的差别

本方案把「吃什么」收成一条链：

1. 规则按病种、用药和最新测量算额度。
2. 状态差分只重算受影响的餐次。
3. 成分表提供热量和成分。
4. 模型只在额度内写固定 JSON。
5. Java 校验不过，只重算这一餐。
6. 新测量可以导致调整，也可以维持。
7. 膳食指南检索发生在方案确定之后，不参与克数和过线。

## 运行时

沿用仓库已经写明的运行时：JDK 21、Spring Boot 4.1.1、Spring AI 2.0.1、MySQL 8.0.46、Redis 8.2.10、RocketMQ 5.5.1。Redis 存对话中的饮食画像。MySQL 存已确认方案。食谱重算在当前对话里完成。模型接入用 Spring AI。简历里的 LangChain4j、单次生成小于 1 分钟、采纳率 85% 不进入仓库。

## 第一批做到哪

第一批做完一个能测的闭环：

- 一个人可以同时有减重和血糖高。
- 可以只问晚餐，也可以排一整天。
- 晚餐扣掉今天已经吃的。
- 上报体重或血糖后，给出「改」或「维持」，改的时候只重算受影响的餐。
- 食材克数来自成分表，并被额度卡住。
- 校验失败只重算这一餐。

高血压、血脂、痛风、慢性肾病先留在病种和额度接口上。指南检索和「能不能吃」后做。

## 不做的事

- 不把拍照识图当作主路径。
- 不做中央厨房配餐，不做开药和检验。
- 不做儿童、孕产和生长迟缓。
- 不在仓库里写真实用户档案。
- 不把任何竞品或简历里的效果数字写成自己的指标。

## GitHub 上的同类仓库

2026-11-10 能查到相近仓库。没有看到一份已经按本方案做完、可以直接接着写的成熟项目：规则额度随最新测量变、允许维持、单餐和一天共用剩余额度、成分表卡住克数、校验失败只重算这一餐、指南检索不决定克数。

推荐食材或食谱的：

- [acara-app/plate](https://github.com/acara-app/plate)：最接近。PHP。按年龄、体重、目标和病种（含 2 型糖尿病、糖尿病前期、高血压、心脏病）生成几天的食谱和克数，并记录血糖。许可证是 O'Saasy，允许自托管，限制拿它做竞争性质的托管服务。GitHub 页面显示约 31 star。
- [Hima-Mehta/NutriChef](https://github.com/Hima-Mehta/NutriChef)：MIT。面向印度素食家庭。糖尿病、高血压、高胆固醇、肥胖等有各自的忌口和替换；可以用冰箱里现有的食材做菜。食材规模是几十种，公开说明没有按每天的测量决定改不改额度。
- [umer1556/metabolic-care-assistant](https://github.com/umer1556/metabolic-care-assistant)：MIT。糖尿病 7 天食谱、血糖记录、高血压和胆固醇用标签过滤。餐库 14 道，作者标明是黑客松原型。约 2 star。
- [team-gigabyte/meal-planner](https://github.com/team-gigabyte/meal-planner)：MIT。按偏好给糖尿病用户排一周食谱和购物清单，数据存在浏览器里。
- [vishnupriyanpr/Verve](https://github.com/vishnupriyanpr/Verve)：MIT。Flutter。糖尿病、高血压、心脏病的饮食和运动建议。约 10 star。
- [polonnia/diabetes-recipe-recommender](https://github.com/polonnia/diabetes-recipe-recommender)：糖小智。按身高、体重、血糖做食谱推荐和对话。
- [runyuan-wang/diabetes-food-guide-skill](https://github.com/runyuan-wang/diabetes-food-guide-skill)：MIT。把《成人糖尿病食养指南（2023年版）》做成对话技能，含 GI、食物交换和 84 套地区季节食谱。它提供指南内容，不按个人当天额度重算。
- [wangtianrui/NutritionMaster](https://github.com/wangtianrui/NutritionMaster)：较早的中文课程项目。有糖尿病等菜谱分类、记饮食和热量，食材热量写明爬自薄荷。
- [Jiayu-zheng1/EveryDay_Food](https://github.com/Jiayu-zheng1/EveryDay_Food)：MIT。1077 道中文食谱，能算热量并搭配一日三餐。分类是减脂、增肌、家常和食疗，没有按病种额度校验。

只负责记录、不生成控病食谱的：

- [simonoppowa/OpenNutriTracker](https://github.com/simonoppowa/OpenNutriTracker)：GPL-3.0。记早中晚和加餐，有钠、钾等微量营养素和体重。食物来自 Open Food Facts、USDA、德国 BLS。
- [wger-project/wger](https://github.com/wger-project/wger)：AGPL-3.0。健身和饮食记录，食物来自 Open Food Facts。
- [rmasciulli/sugardaddi](https://github.com/rmasciulli/sugardaddi)：MIT。面向糖尿病的营养记录，接入 Ciqual、Open Food Facts、USDA。
- [michiella/macros-tracker](https://github.com/michiella/macros-tracker)：用 USDA 把食物填进早中晚，对照自己设的热量和三大营养素目标，可以换更合适的食物。

成分数据，不能直接搬进本仓库：

- [Sanotsu/china-food-composition-data](https://github.com/Sanotsu/china-food-composition-data)：由《中国食物成分表》标准版第 6 版识别而来，约 1677 条，含能量、蛋白质、脂肪、碳水、钠、钾、磷。原书有著作权，识别稿不能当成可以随意再分发的数据。
- [ruffood/cn-food-mcp](https://github.com/ruffood/cn-food-mcp)：约 1725 种食物、每 100 克 25 项营养素的查询服务，同样要先核对数据授权。
- USDA FoodData Central 是 CC0。Open Food Facts 使用 ODbL。两者可以作成分来源，覆盖的是美国通用食物和包装食品，不是中国家常食材全表。

## 复用取舍

- NutriChef 的 `Data/knowledge_base.json`、`src/agent.py`、`src/rag.py`。食材是印度素食，疾病建议写在 JSON 里，并由 RAG 直接生成菜。那条链路和「规则算额度、检索不决定克数」相反。

### 按模块吸收的方案

自己写的链路是：

1. 读长期画像。病、用药、过敏忌口、家里食材、今天已吃、测量历史。
2. 用最新测量决定额度改不改。不改就维持已确认的餐。
3. 规则算出这一餐或这一天的额度。多种病取更紧的。
4. 成分表按克数换算热量和成分。
5. 模型只在额度内写固定 JSON。冲突时改做法、分量、搭配。
6. Java 校验。不过只重算这一餐。
7. 通过的方案写入 MySQL。指南出处和「能不能吃」以后再接，不参与第 3 到第 6 步。

| 本仓库模块 | 参考哪里 | 吸收什么 | 不吸收什么 |
| --- | --- | --- | --- |
| 画像 | plate 的个人资料：年龄、性别、身高、体重、目标、病种、忌口；另加用药、家里食材、今天已吃 | 字段分成稳定资料和会变的测量 | 不复制 PHP 模型 |
| 测量后改或维持 | metabolic-care-assistant 的 `storage.py` 连续记血糖；plate 把血糖分成空腹、餐前、餐后 | 新读数先和上一档额度比较。波动小就维持，越界才重算受影响的餐 | 不复制绿黄红切点 |
| 停下来请人去看医生 | `triage.py` 的分流：读数严重时不发食谱 | 保留这一档。严重高血糖、低血糖、血压危象时只提示就医，不生成食材 | 数字以后按指南单写 |
| 额度 | OpenNutriTracker 把一天拆成早、中、晚、加餐，并给每餐热量份额；macros-tracker 用克数累加后对照目标 | 一天额度先扣已吃，剩下的分给还没吃的餐。热量、蛋白质、每餐碳水、升糖、钠用规则算 | 不复制 GPL 代码，也不把用户自填目标当成病种额度 |
| 病种约束和替换 | NutriChef `knowledge_base.json` 的 `conditions.*.dietary_rules.avoid`、`prefer`、`condition_specific_swaps`（`from`、`to`、`reason`） | 每种病有禁用食材、可用方向、替换原因。替换必须仍落在额度内 | 不搬印度食材，不把「苦瓜能调节血糖」这类句子写进规则 |
| 候选过滤 | `planner.py` 的 `_filter_meals`：高血压滤 `low_sodium`，高胆固醇滤 `low_satfat` | 过滤发生在模型写作之前 | 过滤条件是数值额度，不是菜上的标签，也不从固定菜库随机抽 |
| 成分查询 | sugardaddi 的多数据源：按食物查每 100 克营养素，再按克数缩放 | Java 做一个成分源接口。第一批用仓库内的小示例表。美国食物需要时查 USDA FoodData Central（CC0） | 不内置《中国食物成分表》识别稿，不内置 Ciqual 数据包 |
| 校验失败只重算一餐 | macros-tracker 的做法：某一餐超了目标，就换这一餐里的食物 | 热量、宏量营养素、钠、禁忌成分、药物相关禁忌不过，只重算这一餐 | 不复制它的前端 |
| 固定输出 | plate 的食谱输出：份量、热量、三大营养素、做法 | JSON 固定为饮食画像、核心原则、食谱表 | 模型不决定额度 |
| 家里食材 | NutriChef 的「只用冰箱里有的来做」 | 优先用画像里的现有食材填额度，不够再建议补充 | 不调用它的 agent |
| 指南出处 | diabetes-food-guide-skill 把原则、GI、食物交换、食谱分成不同文件 | 以后的检索库按这个结构组织，并指向卫健委原文 | 检索不回写克数，不提交那几份 Markdown |
| 对话里的长期状态 | plate 的 AI 营养师能接着问「这会不会升糖」 | 已确认方案和测量留在 Redis / MySQL，新问题读这份状态 | 这类问题放在方案确定之后 |

### 第一批自己写的示例数据

示例食材只覆盖血糖和减重要用的一小批中国家常食物，每 100 克写能量、蛋白质、脂肪、碳水、钠，有把握时再写升糖指数。数字来源写在示例文件旁，能用 CC0 或公开标准的用公开来源，对不上的就标成示例值。禁用和替换也只写这一小批，例如甜饮料换成无糖茶，精白米饭换成较小份的杂粮饭。药物相关禁忌先留空表，有公开且可引用的条目再填。
