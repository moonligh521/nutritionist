# 慢病与减重食材推荐系统设计

日期：2026-11-10

状态：V1.5 待审。

本文件是仓库中唯一有效的产品与技术方案，完整定义范围、规则、数据、菜谱、烹饪、测试和交付顺序。早期竞品与开源项目调研保留在 `2026-11-10-食材推荐场景与开源项目调研.md`，只作为调研资料，不能扩大本方案的支持病种、自动推荐范围或模型权限。

临床、食品安全和烹饪参数只有经过专业审核并发布为 `PUBLISHED` 规则或数据后才能启用。没有审核值时，系统必须拒绝对应自动计算，不能使用代码常量、模型常识或评审文档中的示例值补齐。

## 1. 定位

系统定位为「个体化饮食规划与辅助烹饪系统」，给需要控制摄入的成人提供可计算、可复核、能实际做出来的餐食方案：

- 可以只问一餐，例如「今晚吃什么」。
- 可以排一天的早、中、晚餐和加餐。
- 可以拍照或打字告诉系统家里现有的食材。
- 可以明确要求「只能用这些食材」，系统基于实际库存定制。
- 可以表达「我知道不适合，但特别想少吃一点」，系统先判断能否进入风险受控的小份满足。
- 可以从审核菜谱中选择可执行菜品，明确原料、油盐水、重量基准、厨具和步骤。
- 可以按步骤完成烹饪，并记录临时换料、实际用量、成品重量、实际食用量和剩余量。
- 先扣除当天已经吃过的食物，再安排尚未吃的餐。
- 长期保存疾病、用药、过敏、忌口、家中食材、测量、实际摄入和已确认方案。
- 新测量上报后，系统可以维持、局部调整、重新评估或停止推荐。

系统不是自动诊疗工具，不诊断疾病，不修改药物和剂量，不替代医生或营养师。

核心原则是：

> 规则、审核菜谱和确定性求解器决定菜品、食材及克数；Java 重新计算并校验；模型只负责识别草稿、教学表达、说明和固定格式输出。

## 2. 支持边界

不使用「覆盖所有需要控制饮食的慢病」作为产品承诺。系统采用明确的支持清单和四级准入。

### 2.1 A 级：允许自动推荐

第一版只有以下用户可以由系统自动推导营养目标：

- 年满 18 岁；
- 已明确为 2 型糖尿病或糖尿病前期；
- 同时存在超重或肥胖，或只有减重目标；
- 病情、药物和日常进食相对稳定；
- 没有本设计列出的排除项。

第一版可处理：

- 单餐和一日方案；
- 减重所需热量缺口；
- 蛋白质安全下限；
- 每餐碳水范围；
- 在规则和数据可靠时启用脂肪与膳食纤维目标；
- 食物升糖方向；
- 当天已吃食物的扣减；
- 过敏、忌口、偏好和家中食材；
- 体重和血糖趋势；
- 减重与控糖同时存在。

### 2.2 B 级：只执行专业人员设定的目标

以下场景不由系统自行推导临床目标。第一版完成专业目标管理能力后，只有医生或营养师已经给出完整、有效且可执行的额度，系统才能帮助配餐：

- 使用胰岛素或磺脲类药物；
- 使用 SGLT2 抑制剂且计划低碳、断食或正处于急性病期；
- 慢性肾病；
- 高血压；
- 高脂血症；
- 高尿酸血症或痛风；
- 需要严格液体、钾、磷、蛋白质或钠管理的场景。

这些病种后续逐个升级为 A 级。每次升级必须补齐独立的准入、排除、数据要求、冲突测试和专业审核。

### 2.3 C 级：只做记录、科普和转介

以下场景不自动生成食材和克数：

- 1 型糖尿病、妊娠糖尿病或糖尿病类型不明；
- 妊娠、哺乳；
- 晚期慢性肾病、透析、肝硬化、心力衰竭；
- 肿瘤及治疗相关营养问题；
- 吞咽障碍、吸收障碍、炎症性肠病、乳糜泻；
- 老年衰弱、肌少症、低 BMI 或营养不良；
- 减重手术后；
- 进食障碍；
- 快速、非意愿性体重下降。

系统可以记录数据、解释指南并提示寻求专业人员帮助，但不能进入自动配餐。

### 2.4 D 级：停止推荐

出现以下情况时不生成食材：

- 严重低血糖或高血糖及相关症状；
- 需要他人帮助、意识改变或不能安全吞咽；
- 疑似糖尿病酮症酸中毒或高渗高血糖状态；
- 血压危象；
- 持续呕吐、明显脱水或其他急性病表现；
- 输入的多病约束没有安全可行解。

具体阈值必须来自已版本化的官方指南或临床审核规则，不能直接使用开源演示项目中的常量。

### 2.5 基础服务等级与当次安全许可分离

A/B/C 表示用户在稳定状态下可以获得哪一类服务；D 是覆盖其他等级的当次停止规则，不是永久用户标签。每次推荐、替换和动态调整都必须再次计算当次安全许可：

- `ALLOWED`：当前输入完整且没有命中停止条件；
- `NEED_MORE_DATA`：缺少测量语境、单位、限制原因或其他必要数据；
- `HUMAN_REVIEW`：只有专业人员确认目标后才能继续；
- `STOP`：出现急症、绝对禁忌或没有安全可行解。

例如 A 级用户今天出现急性症状时必须 `STOP`；B 级用户即使已有专业目标，出现漏餐、脱水、急性病或近期换药时也要重新判断。

这里的枚举命名为 `SafetyPermission`，与第 3.5 节的 `MeasurementDecision` 分开。映射规则是：测量决策为 `URGENT_REFERRAL` 时安全许可必为 `STOP`；测量信息不足时，两者可以分别为 `NEED_MORE_DATA`；其余测量决策仍必须通过整体安全许可后才能执行。

安全结果必须由三个独立维度组成，不能让一个枚举同时承担许可、原因和处置：

- `SafetyPermission`：是否允许继续；
- `reasonCategories`：包含一个或多个 `SafetyReasonCategory`，例如 `ACUTE_RISK`、`MALNUTRITION_RISK`、`MEDICATION_RISK`、`DATA_QUALITY`、`CONTRAINDICATION`、`CONSTRAINT_CONFLICT`、`PROFESSIONAL_TARGET_INVALID`、`OUT_OF_SCOPE`；
- `actionDispositions`：包含一个或多个 `ActionDisposition`，例如 `CONTINUE`、`REQUEST_DATA`、`REJECT_ITEM`、`KEEP_CONFIRMED_PLAN`、`INVALIDATE_FUTURE_MEALS`、`RETURN_CONFLICT`、`REFER_PROFESSIONAL`、`REFER_URGENT`。

例如急性危险返回 `STOP + ACUTE_RISK + REFER_URGENT`；目标过期返回 `HUMAN_REVIEW + PROFESSIONAL_TARGET_INVALID + REFER_PROFESSIONAL`；数据不足返回 `NEED_MORE_DATA + DATA_QUALITY + REQUEST_DATA`。原因和动作可以有多个，但最终许可只有一个，并按最安全结果收敛。

基础映射为：

- A 级只有全部安全检查通过时才可得到 `ALLOWED`；
- B 级只有专业目标完整、有效且安全检查通过时才可得到 `ALLOWED`，否则为 `HUMAN_REVIEW`；
- C 级自动配餐固定返回 `HUMAN_REVIEW + OUT_OF_SCOPE + REFER_PROFESSIONAL`，只提供记录、科普和转介；
- D 级命中时统一收敛为 `STOP`；
- 硬约束无解收敛为 `STOP + CONSTRAINT_CONFLICT + RETURN_CONFLICT`；
- `KEEP_CONFIRMED_PLAN` 是安全处置动作，不等同于 `MeasurementDecision.KEEP`。

### 2.6 药物安全独立于普通营养规则

药物不能只作为准入标签。`safety` 模块维护独立的药物安全规则，至少覆盖：

- 低血糖风险和漏餐风险；
- 进餐时间与用药陈述不一致；
- 断食、极低碳或大幅减少摄入；
- SGLT2 抑制剂相关的急性病、脱水、禁食和酮症风险信号；
- 近期开始、停止或调整药物；
- 用户试图通过加药、改药或改变用药时间补偿饮食。

系统只根据用户陈述做风险分流，不给出停药、加药、改剂量或改变用药时间的建议。药物规则必须有版本、来源、适用条件和专业审核。

`MedicationSafetyEvaluator` 必须在生成、替换、解馋、测量驱动调整、药物变化和重新确认过期方案时执行，不能只在首次建档时执行。

每条 `MedicationSafetyRule` 至少保存规则 ID、药物类别、适用人群、必要输入、触发事件、排除条件、测量与症状语境、许可结果、原因分类、处置动作、公开提示模板、证据、审核人、版本、有效期、测试用例和回滚版本。状态固定为 `DRAFT → CLINICAL_REVIEW → TESTED → PUBLISHED → RETIRED`。

工程判定矩阵不直接填写未经审核的临床阈值：

- 药物信息不完整、名称无法标准化或时间不明：`NEED_MORE_DATA + DATA_QUALITY + REQUEST_DATA`；
- 使用胰岛素或已发布规则定义的高风险药物，但没有完整专业目标：`HUMAN_REVIEW + MEDICATION_RISK + REFER_PROFESSIONAL`；
- 近期换药、漏餐、断食、极低碳或明显减少摄入：按已发布规则补数据或转专业人员；没有匹配规则时固定返回 `HUMAN_REVIEW + MEDICATION_RISK + REFER_PROFESSIONAL`，并记录 `MEDICATION_RULE_NOT_COVERED`；
- 急性病、持续呕吐、脱水或明确危险症状组合：按已发布规则返回 `STOP` 和对应转介动作；
- 用户要求加药、追加胰岛素或改变用药时间抵消饮食：拒绝该请求，不改变药物事实；
- 只有药物信息完整、状态稳定、专业目标有效且其他安全模块也通过时，才能继续目标计算。

多个安全模块按 `STOP > HUMAN_REVIEW > NEED_MORE_DATA > ALLOWED` 收敛唯一许可。药物模块只能把结果提升到更安全的级别，不能降低过敏、营养不良、急症或其他模块的风险结论。

## 3. 用户场景

### 3.1 单餐

用户问「今晚吃什么」时：

1. 读取当天已吃记录。
2. 冻结已吃和已确认的餐。
3. 计算剩余日额度和晚餐额度。
4. 使用家中食材、偏好和病种约束求解晚餐。
5. 返回食材、克数、做法、营养汇总和剩余额度。

如果晚餐调整会导致其他未来餐无法满足全天约束，则一起重算尚未吃的未来餐。

### 3.2 一日方案

用户请求一日三餐时：

- 生成早、中、晚餐，需要时增加加餐；
- 每餐有食材、克数和做法；
- 全天满足热量、蛋白质和病种约束；
- 支持替换某个不喜欢的食材；
- 替换后重新校验餐次和全天约束。

### 3.3 家中现有食材

用户可以通过以下方式录入家中食材：

- 打字：「有鸡蛋 4 个、西红柿 500 克、燕麦 300 克」；
- 自然语言：「冰箱里还有半颗白菜和昨天剩的鸡胸肉」；
- 拍摄冰箱、食材或购物小票；
- 在识别结果中手工增加、删除或修改。

录入过程分为两步：

1. 模型或识别服务只产出候选食材、可能数量、单位和置信度；
2. 用户确认后才写入库存，未经确认的识别结果不能参与配餐。

照片通常无法可靠判断精确克数。系统应：

- 能识别包装标重时读取包装净含量；
- 不能识别时询问数量、个数或大致重量；
- 可以用「1 个」「半颗」「1 盒」录入，但求解前必须通过份量换算表转换为范围；
- 对低置信度、遮挡和无法区分生熟状态的食材要求确认；
- 不根据图片自行推断过敏原不存在。

库存模式有两种：

- `ONLY_AVAILABLE`：用户明确说「只有这些」「不要推荐要买的」。库存是硬约束，方案不得使用库存外食材，也不得超过现有数量。
- `PREFER_AVAILABLE`：用户希望优先消耗家中食材。库存是软目标；当现有食材无法满足安全和营养约束时，可以给出最小补购清单。

如果 `ONLY_AVAILABLE` 没有可行解：

- 不允许模型添加新食材；
- 返回缺少的营养类别或发生冲突的约束；
- 给出「放宽为允许补购」或「调整餐次范围」的选择；
- 在用户明确同意前，不生成包含库存外食材的方案。

每条库存记录至少包含：

- 标准食材 ID 和用户看到的名称；
- 数量、单位及可换算范围；
- 生/熟、包装/散装状态；
- 可选的保质期或优先消耗时间；
- 来源：文字、照片、购物小票或手工修改；
- 识别置信度；
- 是否已经由用户确认；
- 入库、消耗和作废时间。

同一食材可能来自多批库存，求解时优先使用临期批次，但不能为减少浪费突破健康约束。

每批库存同时维护账面量、有效预留量和可用量：

`availableQuantity = onHandQuantity - activeReservedQuantity`

数量变化通过库存事件和事务处理，不能由多个流程直接覆盖同一个数量字段。方案取消或过期释放预留。需要烹饪的配料在确认实际投入时消耗库存；无需烹饪的简单食物在确认实际摄入时消耗库存；同一数量只能走其中一条路径，摄入记录不得重复扣减。

### 3.4 当天已吃

实际摄入按不可变事实记录。已吃食物不能被后续方案覆盖。

如果用户没有说明今天已经吃过什么：

- 单餐推荐只能使用该餐默认分配；
- 明确提示其他餐尚未计入；
- 不把结果描述成完整的当天剩余额度。

### 3.5 新测量上报

血糖和体重上报后不是简单的「调整或不调整」，而是五态决策：

1. `NEED_MORE_DATA`：单位、时间、餐前餐后语境或数据质量不足，要求补充或复测。
2. `URGENT_REFERRAL`：命中急症或排除规则，停止推荐。
3. `KEEP`：变化不足以改变当前额度，维持原方案。
4. `ADJUST_FUTURE_MEALS`：只调整尚未吃的相关餐次或进餐时间。
5. `REASSESS_DAILY_TARGET`：重新计算全天目标，或转专业人员。

每个决定必须同时保存稳定的 `decisionReasonCodes`，例如：

- `GLUCOSE_CONTEXT_MISSING`；
- `MEASUREMENT_QUALITY_LOW`；
- `TREND_STABLE`；
- `PERSISTENT_ELEVATION`；
- `MEDICATION_CHANGED`；
- `ACUTE_ILLNESS_REPORTED`；
- `WEIGHT_TREND_CHANGED`。

原因码只说明系统为什么做出决定，不能代替临床阈值或单独触发处置。

决策必须考虑：

- 测量发生时间与记录时间；
- 空腹、餐前、餐后和关联餐次；
- 单位、设备或数据来源、数据质量；
- 多次趋势，而不是单个值；
- 症状、急性病和近期药物变化；
- 实际摄入、漏餐、运动、饮酒和方案执行情况；
- 营养状态和已有专业人员目标。

### 3.6 特别想吃受限制的食物

用户可能说：

- 「我不能吃蛋糕，但今天特别想吃一点」；
- 「血糖高，能不能少喝一点甜饮料」；
- 「正在减重，能不能吃一小块炸物解馋」。

系统不能直接把「不能吃」理解为可量化额度。必须先追问或读取已经记录的限制原因，并分为：

1. `ABSOLUTE_PROHIBITION`：明确过敏、乳糜泻、严重不耐受、明确药食禁忌、急性期禁忌或专业人员明确要求完全避免。
2. `CLINICIAN_RESTRICTED`：专业人员要求限制，但系统没有可计算的目标。
3. `BUDGET_LIMITED`：热量、碳水、钠、饱和脂肪、嘌呤等可以按剩余额度计算。
4. `PREFERENCE_AVOIDED`：只是平时不喜欢或自己选择不吃。
5. `UNKNOWN`：原因不清楚。

处理规则：

- `ABSOLUTE_PROHIBITION`：不计算「安全的一口」，也不保证少量无害；提供口感、香味或做法相近且不命中禁忌的替代品。
- `CLINICIAN_RESTRICTED`：沿用专业人员给定的范围；没有范围时不能自行放宽。
- `UNKNOWN`：先澄清原因，不生成试吃方案。
- `BUDGET_LIMITED`：只有用户通过 A 级准入且当前状态稳定时，才计算风险受控的小份。
- `PREFERENCE_AVOIDED`：按普通偏好处理。

风险受控的小份满足使用 `CRAVING_PORTION` 模式：

1. 用户说明想吃的食物和期望程度，例如一口、半份或指定克数。
2. 系统查询该食物可靠的成分数据和当天剩余额度。
3. 求解器寻找不突破硬约束的最小满足份量。
4. 可以通过改做法、减小份量、和正餐一起搭配或替换同餐其他食材降低营养负担。
5. 只调整尚未吃的未来餐，不修改已吃记录。
6. 返回允许份量、占用的额度、剩余风险和不能保证的部分。

系统不得：

- 宣称「这样吃没有伤害」；
- 建议自行多吃药、追加胰岛素或改变药物时间来抵消；
- 建议催吐、极端运动、整日挨饿或跳过必要餐次来补偿；
- 把一次可行解释成可以频繁食用；
- 在成分数据缺失或限制原因不明时猜测安全份量。

「解馋程度」是主观值，不能由系统假装精确计算。用户可以选择期望份量；系统只判断该份量能否进入当前约束。若不能，系统给出更小份量或替代品，不能为了满足偏好放宽硬约束。

### 3.7 从餐食推荐到实际做饭

用户可以继续说明人数、厨具、可用时间、烹饪水平和口味，例如「只有炒锅，20 分钟，一人份，我不会做饭」。系统按以下能力降级：

1. 有适用且已发布的菜谱版本：返回菜品、精确配料、重量基准、厨具、结构化步骤和营养结果；
2. 有食材营养数据但没有审核菜谱：可以返回食材和克数及受控的简单处理方式，但必须明确「暂无完整审核教程」；
3. 关键食材、转换或食品安全数据不足：不生成看似精确的菜谱，返回缺失项或可用替代方案；
4. 匿名用户未完成最低安全信息收集时，只能浏览一般性审核菜谱和科普，不能获得个体化慢病克数。

烹饪开始后，计划与事实必须分开：

- 方案配料表示计划使用量；
- 烹饪实际用料表示真正投入量；
- 成品重量表示做完后的总重量；
- 实际摄入表示用户真正吃下的重量；
- 剩余量不能计入已摄入；
- 换料、多放油盐、减少份量或做法变化都追加实际执行事件，并触发营养复算和必要的未来餐重算。

分步教学不得依靠模型临场发明关键事实。食材投放顺序、精确用量、食品安全检查、关键温度或完成条件必须来自已发布菜谱和规则；模型只能把这些事实表达得更易懂。

## 4. 约束模型

### 4.1 约束优先级

约束先分层，再在层内处理优先级。

第一层是任何人都不能覆盖的安全硬约束：

1. 绝对过敏和明确禁忌；
2. 急性安全停止；
3. 防止营养不良的最低安全边界；
4. 关键数据质量门槛；
5. 法规、产品支持边界和专业审核明确禁止的条件。

第二层是在第一层允许范围内执行的目标：

1. 医生或营养师设置的有效目标；
2. 当前主要治疗目标；
3. 长期风险目标；
4. 偏好、成本、家中食材、多样性和变化最小。

「想吃一次」属于最低级软目标。专业人员目标虽然高于普通治疗目标，但仍不能突破第一层安全硬约束。如果专业目标与安全边界冲突，系统返回 `HUMAN_REVIEW` 或 `STOP`、保留冲突依据并拒绝自动求解，不能强行选择其中一个。

复合食品必须有可核对的配料和过敏原声明；成分不明时不能默认无过敏原。食材替换、调味品变化和品牌变化后必须重新校验。系统只能根据包装声明或可靠数据提示交叉接触风险，不能保证现实加工环境绝对无交叉污染。

第一版只实现成分不明拒绝、明确过敏原拦截和替换后重校验，不建设供应链级交叉污染追溯平台。

### 4.2 不能简单「取更紧」

多病共存必须合并成统一约束集合：

- 上限通常取较小值；
- 下限通常取较大值；
- 同一营养素的上下限可能发生冲突；
- 蛋白质、钾、磷和液体会随疾病分期、化验和透析状态变化；
- 体重变化可能是脂肪变化，也可能是液体潴留；
- 不同指南可能面向不同人群和时间尺度。

求解结果必须是：

- `FEASIBLE`：全部硬约束满足；
- `PARTIAL`：只有允许降级的软目标未满足；
- `INFEASIBLE`：硬约束没有交集，停止生成并返回冲突约束。

`INFEASIBLE` 不能只暴露求解器状态。业务冲突分析器必须返回：

- 发生冲突的约束 ID、名称、上下限和来源；
- 哪些约束不可降级；
- 受影响的餐次和时间范围；
- 保留哪个已确认方案或已吃事实；
- 下一步是补数据、调整软目标还是转专业人员。

### 4.3 营养目标计算

求解器只负责在目标内找解，不负责发明目标。独立的 `target` 模块把画像、专业目标和已审核规则转换为版本化的 `NutritionTargetSet`。

必须区分三层对象：

1. `GuidelineRecommendation`：指南或专业标准中的人群范围；
2. `NutritionTargetSet`：根据某次画像和已发布规则得到的个人全天目标；
3. `MealBudgetSet`：扣除实际摄入并冻结已确认餐次后得到的餐次约束。

指南建议不能直接提交给求解器，餐次约束也不能反向伪装成指南原文。

第一版只为 A 级成人计算：

- 有来源公式估算的基础代谢；
- 活动水平和近期趋势参与的总能量估算；
- 经审核规则允许的减重能量范围；
- 防止营养不足的能量和蛋白质下限；
- 全天和每餐碳水范围；
- 脂肪和膳食纤维等第一版已具备可靠规则与数据的目标。

B 级用户优先使用有效期内的专业人员目标，系统不得自行补齐未给出的钠、钾、磷、液体、蛋白质或其他临床额度。每个目标记录：

- `targetId`、目标类型和单位；
- 下限、上限或方向性目标；
- `hardOrSoft` 和优先级；
- 公式或规则 ID、版本和证据来源；
- 适用人群、排除条件和有效期；
- 输入画像版本、专业目标版本和计算时间；
- 缺失输入、估算假设和置信等级。

B 级使用独立的 `ProfessionalTargetLoader`：验证录入者权限、用户匹配、目标完整性、单位、适用人群、有效期和不可覆盖安全层，然后转换为 `NutritionTargetSet`。缺少目标不得调用 A 级公式补齐；目标过期、冲突或不完整时返回 `HUMAN_REVIEW`。

目标计算前必须检查年龄、性别、身高、体重、活动量、非预期体重下降、营养不良风险和近期疾病。不能因为短期体重未下降就自动扩大热量缺口；体重趋势可能包含水分变化，必须结合执行记录、实际摄入和安全状态解释。

`NutritionTargetCalculator` 必须遵循可执行规格：

1. 标准化年龄、性别、身高、体重、活动量、目标和单位；
2. 执行适用人群、排除条件、输入完整性和安全许可检查；
3. 计算 BMI 等描述性指标，但不能仅凭单个指标决定目标；
4. 从 `FormulaRegistry` 选择经审核的基础代谢公式；
5. 根据有来源的活动系数和适用条件估算总能量范围；
6. 应用经审核的减重范围和营养安全上下限；
7. 计算蛋白质、全天碳水及已启用的脂肪、膳食纤维目标；
8. 对 A 级用户合并仍有效且适用于当前用户的专业目标；
9. 再次运行 `TargetSafetyValidator`，生成安全的 `NutritionTargetSet` 或明确拒绝原因；
10. 交给 `MealBudgetAllocator` 分配餐次范围。

A 级专业目标是对已审核自动目标的受控约束，不是与自动计算互斥的另一条随意路径。多个公式或规则同时适用但无法唯一选择时返回 `HUMAN_REVIEW`，不能按代码顺序取第一条。B 级不执行 A 级公式，只使用 `ProfessionalTargetLoader`；缺失、过期或不完整时不得自动补齐。

每条 `NutritionTargetRule` 至少保存稳定规则 ID、目标类型、适用人群、准入和排除条件、必要输入与单位、公式 ID、参数集 ID、安全上下限、证据与等级、作者、审核人、批准人、版本、生效失效时间、测试用例和被替代规则。状态固定为 `DRAFT → CLINICAL_REVIEW → TESTED → PUBLISHED → RETIRED`。

`FormulaRegistry` 的每个公式和参数记录公式 ID、版本、表达式、输入输出单位、舍入策略、权威来源、适用人群、排除条件、数值适用范围、参数来源、生效失效时间、审核人和边界测试。公式和参数分开版本化；活动系数、边界或适用人群变化必须产生新版本，不能覆盖历史值。具体公式、活动系数、能量缺口和营养上下限由专业审核后配置，业务代码不得散落经验常量。

缺少必要输入时返回 `NEED_MORE_DATA`，不使用静默默认值；用户处于排除条件时返回 `HUMAN_REVIEW` 或 `STOP`；公式结果超出审核边界时不截断成看似合理的数字，而是返回明确的边界错误。

目标计算测试至少覆盖输入单位和原值保留、缺失字段、年龄和 BMI 边界、公式适用范围、多公式冲突、无 `PUBLISHED` 规则、活动系数切换、专业目标完整或过期、专业目标覆盖与安全冲突、营养不良拦截、规则版本切换和相同输入可复现性。没有已发布规则时返回 `HUMAN_REVIEW`，不能使用代码默认值。

### 4.4 餐次额度分配

`MealBudgetAllocator` 把全天目标转换为单餐可执行范围，不能把当天剩余额度全部交给当前请求餐次。

计算顺序为：

1. 读取版本化 `NutritionTargetSet`；
2. 扣除已确认的实际摄入；
3. 保留已确认且未失效餐次的冻结额度；
4. 根据用户确认的餐次结构或版本化分配规则，为尚未吃的正餐和必要加餐保留范围；
5. 为当前请求生成 `MealBudget`；
6. 求解后再次验证当前餐、剩余未来餐和全天约束。

每份 `MealBudget` 保存餐次、能量和关键营养素上下限、分配规则版本、已吃扣减、冻结额度、保留给未来餐的额度及计算原因。餐次比例只能来自审核规则或用户确认的餐次结构，不能写死在 Controller 或求解器中。

普通偏好变化不得修改已确认未吃餐次。如果当前餐会导致未来餐无解，系统优先保持已确认餐次，只联合重算尚未确认且尚未吃的餐次；仍无解时返回结构化冲突。新安全事件则按第 6.3 节中断矩阵处理，不受普通冻结规则限制。

用户未记录当天其他摄入时，单餐请求只能使用该餐默认范围，并明确标记为“不代表当天完整剩余额度”。

### 4.5 确定性求解

第一版使用纯 Java LP/MIP 求解器 `ojAlgo`：

- 决策变量：已发布菜谱的份量、菜谱允许范围内的缩放档位，以及无需菜谱的简单食物克数或份量档位；
- 硬约束：过敏、禁忌、热量范围、蛋白质下限、每餐碳水范围和专业人员目标；
- 可执行性约束：食材最小/最大份量、实际份量档位、库存上限和餐次结构；
- 软目标：优先家中食材、偏好、变化最小、食物多样、减少浪费；
- `CRAVING_PORTION` 时，在硬约束内最小化目标食物造成的营养负担，并尽量接近用户确认的期望份量；
- `ONLY_AVAILABLE` 时，候选集和最大克数受已确认库存限制；
- `PREFER_AVAILABLE` 时，使用现有库存和优先消耗临期食材进入软目标；
- 已吃餐和已确认餐固定，不允许修改；
- 尚未吃的未来餐可以联合优化。

餐次项分为两种：

- `RECIPE_PORTION`：优先用于真实正餐。引用固定 `recipeVersion`，配料比例只能在该版本审核过的缩放范围和替换槽位内变化；
- `SIMPLE_FOOD`：水果、牛奶、煮蛋等无需复杂配方的食物，仍受份量、营养、库存和安全约束。

求解器不能先生成任意食材碎片，再让模型临场拼成一道菜。没有可用菜谱时可以返回明确标记的食材组合，但不能宣称已经形成完整菜品或分步教程。油、盐、酱料和用水必须作为菜谱配料或明确计算项，不得藏在自然语言做法里。

每个约束都携带 `constraintId`、`constraintType`、`priority`、`lowerBound`、`upperBound`、`hardOrSoft`、`sourceRef`、适用人群和有效时间。目标通常是范围、下限、上限或方向性要求，不能全部建成精确等式。

软目标采用分层优化，不把所有目标随意乘权重后一次求和：

1. 先验证全部硬约束可行；
2. 再保证营养质量和份量可执行；
3. 再优化专业人员或当前主要目标允许调整的部分；
4. 最后优化偏好、库存利用、减少浪费和多样性。

业务代码只调用 `NutritionSolver` 接口。`ExpressionsBasedModel` 封装在 `OjalgoSolverAdapter` 内，统一处理超时、无界、无解、精度和版本差异。

复杂多天规划和多样性增加后再评估：

- Timefold Solver：Apache-2.0，适合多餐、多天、偏好和固定变量；
- OR-Tools：Apache-2.0，适合复杂整数约束，但有 JNI 和部署成本。

### 4.6 成分复算与数据质量

求解器和模型都不能提交可信的营养汇总。Java 必须根据食材 ID、数据集版本和克数重新计算：

- 能量；
- 蛋白质；
- 脂肪；
- 碳水化合物；
- 钠；
- 后续病种需要的钾、磷、嘌呤等。

每个值必须保留：

- 数据来源和版本；
- 每 100 克或每份；
- 生重、熟重和可食部；
- 单位；
- 数据状态：`KNOWN`、`ESTIMATED`、`UNKNOWN` 或 `NOT_APPLICABLE`；
- 更新时间和置信等级。

`UNKNOWN` 不能当作 0，`ESTIMATED` 不能伪装成实测值。系统根据本次有效约束确定数据门槛：

- 控糖方案要求候选食物具有达到门槛的碳水数据；
- 低钾、低磷、低钠等专业目标要求对应营养素达到门槛；
- 关键限制指标为 `UNKNOWN` 或置信度不足时，该食物不得进入相关自动求解；
- 非关键营养素缺失可以展示为未知，但不能宣称目标已经满足。

`nutrition` 模块中的 `NutritionDataQualityPolicy` 把数据质量变成可执行准入，不单独拆成服务。它检查来源授权、数据版本、单位、基准、生熟状态、可食部、完整性、置信等级、异常值和本次约束所需营养素，并返回：

- `ACCEPT`：可以进入本次候选集；
- `RESTRICT`：只能用于不依赖缺失指标的场景，并公开限制原因；
- `REJECT`：不能进入本次自动计算。

同一食材可以在普通减重场景为 `ACCEPT`，在严格限钠场景因钠数据未知而为 `REJECT`。质量结果记录策略版本、触发检查和原因码，不能由模型覆盖。

GI 只作为带来源、制备方式和置信度的辅助食物评价信息，不能等同于个体餐后血糖，也不能单独决定食材克数。缺少可靠 GI 时保持未知，不由模型推测。

生产食物数据按能力逐步分层：

1. 可追溯的基础食材；
2. 有合法来源的加工食品和调味品；
3. 由基础食材、油盐和明确烹饪参数组成的家常组合；
4. 带条码、标签版本和净含量的品牌商品。

第一版只要求少量可追溯基础食材和必要的生熟重、可食部换算。烹饪出成率、营养素保留率、油脂吸收率和常见家常组合在取得可靠参数后逐步增加，不能为了覆盖中国菜而填入无来源估值。

每个 `FoodItem` 至少保存稳定 ID、原始名称、标准名称、中文别名、分类、状态、可食部、计量基准、来源记录 ID、许可证、数据集版本、质量与审核状态、有效期、自动求解许可及明确不适用场景。品牌包装食品还要保存品牌、条码、包装规格、净含量、营养标签版本、配料表、过敏原声明和用户确认时间；包装或配方改变必须产生新版本。

每个 `FoodNutrient` 保存食材版本、营养素 ID、数值、单位、每 100 克或每份基准、重量状态、数据状态、来源、精度、换算过程和审核状态。多来源数值冲突必须保存各自来源并进入审核；冲突未解决时按本次关键营养素返回 `RESTRICT` 或 `REJECT`，不能静默选择更有利的数值。

`IngredientNutritionCalculator` 固定执行：读取指定版本、统一单位、应用可食部、确认重量基准、仅在有已发布参数时做生熟转换、按实际可食克数计算并传播每项数据状态。生重数据不能直接乘熟食重量。

`RecipeNutritionCalculator` 的输入必须包含配方版本、每个原料的标准 ID 和状态、油盐酱料、重量基准、烹饪方式、成品总重量、份数及有来源的转换参数。它逐项调用单食材计算、应用已发布转换、汇总、计算每份和每 100 克结果，并重新校验过敏原与关键营养数据门槛。任一关键参数未知时返回 `RESTRICT` 或 `REJECT`，不得使用默认损耗率伪造精度。

数据生命周期固定为 `DRAFT → REVIEWED → PUBLISHED → SUSPENDED → RETIRED`。发现错误时立即暂停问题版本、启用对应 Kill Switch、定位受影响方案、使未吃餐失效、发布修正版或回滚、重跑回归并审批恢复；历史方案继续引用旧版本用于审计，不能静默替换。

### 4.7 配餐可执行性

ojAlgo 数学可行不等于现实可执行。求解结果在最终营养校验前必须经过 `MealPracticalityValidator`：

- 最小、最大和常见份量档位；
- 食材项数量和不必要碎片化；
- 版本化餐次结构；
- 有来源的食材组合和烹饪兼容规则；
- 用户明确的设备、时间和餐次习惯。

校验结果为 `PASS`、`ADJUSTABLE` 或 `REJECT`。`ADJUSTABLE` 只允许把结构化可执行性约束交给求解器重算一次；仍不通过则拒绝，不允许模型用文字把不可执行方案描述成可行。

`MealPracticalityValidator` 输入菜谱或食材 ID、克数、份量档位、餐次结构、厨具、时间、库存、预算、偏好和版本化可执行性规则；检查极小份量、单一食材异常占比、过度碎片化、餐次结构、组合冲突、设备和时间限制，以及调整后是否仍满足营养、禁忌和库存约束。

每条 `MealPracticalityRule` 保存规则 ID、类型、版本、适用餐次和人群、食材类别、份量上下限与步长、组合条件、餐次结构、设备或时间条件、来源、审核状态、有效期和测试用例。没有来源的“常识搭配”保持未知，不能被 AI 写成硬约束。

固定求解 benchmark 至少覆盖单餐、全天、多目标、库存充足与不足、绝对过敏、无解、极端输入、大候选集、并发、同输入复现和可执行性重算；记录 benchmark、规则、食物数据和求解器版本，变量与约束数量、各层目标值、硬约束结果、营养汇总、冲突解释、耗时、内存和并发资源。求解器升级必须重跑并评审差异。

### 4.8 审核菜谱模型

菜谱是可版本化、可计算、可教学的事实，不是一段由模型自由生成的文本。每个 `RecipeVersion` 至少包含：

- 稳定菜谱 ID、版本、名称、类别、份数和成品重量基准；
- 准备、烹饪和总时长；
- 难度、最低技能级别和适用餐次；
- 所需厨具和已验证的设备变体；
- 饮食标签、过敏原、适用与不适用条件；
- 配料、步骤、营养计算和食品安全规则版本；
- 作者、配方审核、烹饪审核、食品安全审核、营养审核和工程审核记录；
- `DRAFT`、`REVIEWING`、`APPROVED`、`PUBLISHED`、`SUSPENDED` 或 `RETIRED` 状态；
- 生效时间、失效时间和被替代版本。

`APPROVED` 表示各专业审核已经通过但尚未生效；只有处于有效期内的 `PUBLISHED` 版本且全部依赖数据仍有效时才能进入正式推荐。AI 辅助产生的菜谱只能进入 `DRAFT`，不能直接推荐给用户。

每个 `RecipeIngredient` 必须引用标准食材与状态，并保存：

- 精确数量和单位；
- 生重、熟重、净重、可食部、带壳重或成品重基准；
- 主料、辅料、调味料、用油或用水分组；
- 必选、可选或受控替换槽位；
- 投放步骤、预处理方式和允许缩放范围；
- 过敏原、营养数据和库存扣减引用。

正式配方不得使用“适量”“少许”等不可计算数量。用户允许调整的调味料也必须给出范围，调整后重新计算。

### 4.9 结构化烹饪步骤和流程

菜谱做法拆成 `RecipeStep`，每一步至少保存：

- 步骤号、标题、动作类型和用户说明；
- 涉及的配料 ID、该步计划投放量和重量基准；
- 厨具、火力、温度、时长、加水量等适用参数；
- 前置步骤和可并行依赖；
- 完成条件、失败或异常分支；
- 食品安全检查；
- 可选的审核图片、视频或计时器；
- 步骤数据来源、版本和审核状态。

动作类型使用受控枚举，例如 `WASH`、`PEEL`、`CUT`、`MARINATE`、`BLANCH`、`BOIL`、`STEAM`、`PREHEAT`、`ADD_INGREDIENT`、`STIR`、`FRY`、`BRAISE`、`SEASON`、`ADD_WATER`、`CHECK_TEMPERATURE`、`CHECK_DONENESS`、`WEIGH` 和 `PLATE`。

步骤是有向无环流程，不强制所有准备工作串行。只有前置依赖满足后才能进入下一步；食品安全关键步骤不能跳过。完整性校验至少保证：

- 每个配料 ID、单位和重量基准有效；
- 每个必选配料都有投放步骤；
- 每个步骤引用的配料存在于当前菜谱版本；
- 步骤依赖无环且不存在不可达步骤；
- 关键安全检查和完成条件不缺失；
- 按人数缩放后，各步骤投放量之和与配方一致；
- 相同版本和输入能够复现相同的结构化流程。

### 4.10 厨具、烹饪方式和食品安全

`CookingMethod` 定义蒸、煮、炒、煎、炖、烤、空气炸和凉拌等方法的参数模式，不存一个无约束字符串。参数可以包含火力、预热、时长、温度、加水、翻动间隔和油量，但合理范围必须由具体菜谱和食材共同限定。

`Equipment` 保存设备类型、能力和参数模式；`RecipeEquipmentVariant` 保存某个菜谱在特定设备上的已审核步骤覆盖。用户没有适用设备变体时，该菜谱不能进入候选集。模型不得根据设备名称自行猜测温度和时间。

食品安全条件必须引用已发布规则，包含适用食材、处理方式、测量位置、阈值、保持时间、交叉污染预防和公开提示。示例教程中的温度或时长不能直接成为生产规则；没有已审核条件时，系统拒绝生成对应的精确熟制指令。

新手、普通和熟练用户可以获得不同详略程度的表达，但底层配料、投放顺序、关键参数、完成条件和安全检查必须相同。

### 4.11 烹饪转换和营养结果

烹饪营养链路固定为：

```text
RecipeIngredient
    → IngredientPreparationCalculator（去皮、去骨、净重、可食部）
    → CookingTransformCalculator（出成率、水分、营养保留、油脂与弃汤）
    → RecipeNutritionCalculator（原料、成品、每份和每 100 克）
    → Java Nutrition Validator
```

`CookingTransform` 必须按食材状态、烹饪方式和版本保存出成率、水分变化、脂肪或油脂处理及来源；不同营养素使用各自的 `NutritionRetentionFactor`。不能把统一保留系数套在所有营养素上，也不能默认加入的油全部被吃掉或随意假设固定吸收比例。

系统同时保留四种结果：

1. 原料计划营养；
2. 有可靠转换数据时的烹饪后成品营养；
3. 按成品重量与份数计算的每份营养；
4. 按实际食用重量计算的实际摄入营养。

结果状态使用 `VERIFIED`、`ESTIMATED`、`INCOMPLETE` 或 `INVALID`。缺少关键转换时保留原料理论值和缺失说明，不能把估算结果显示成精确成品营养。

### 4.12 烹饪执行事实

`CookingExecution` 与方案、库存和摄入相互独立。它保存用户、方案和菜谱版本、计划份数、实际份数、开始结束时间及执行状态；`CookingExecutionStep` 追加每一步的开始、完成、跳过原因和用户确认；`CookingActualIngredient` 保存计划量、实际量、单位、变更原因和对应库存批次。

P3 的最小闭环只支持完全按计划执行：用户确认投料步骤后，以该步骤的计划投放量追加实际投入事件并幂等消耗库存预留，最后一步完成后可以关闭会话。用户报告数量、换料或做法偏差时不得继续按原计划记账，只有 P4 的动态修订能力可以重新校验并接受偏差。

烹饪中变化按固定流程处理：

1. 用户报告缺少配料、多放油盐、改变份数或更换做法；
2. Java 查询当前菜谱允许的替换槽位和参数范围；
3. 重新执行过敏、禁忌、药物、数据质量和库存检查；
4. 重新计算菜谱和整餐营养；
5. 未突破硬约束时生成新的执行修订版并更新后续步骤；
6. 突破约束或数据不足时停止自动调整，返回冲突、补数据或转介；
7. 保存实际用料、成品重量、实际食用量和剩余量。

AI 可以理解用户说的变化并生成草稿，但不能批准替换、确定新的关键用量或宣称变化无风险。用户确认方案不等于开始烹饪，开始烹饪不等于用完库存，完成烹饪也不等于全部摄入。

### 4.13 菜谱候选与推荐解释

正式推荐按以下顺序处理菜谱：

1. 安全许可与营养目标；
2. 用户库存、口味、时间、厨具和技能硬过滤；
3. 菜谱状态、依赖数据版本和食品安全条件过滤；
4. 由 Java 构建 `RECIPE_PORTION` 与 `SIMPLE_FOOD` 候选；
5. ojAlgo 在餐次额度内选择份量和允许的变体；
6. `MealPracticalityValidator` 检查整餐结构和可执行性；
7. Java 复算菜谱、餐次和全天营养；
8. 可选生成教学表达。

安全、过敏、营养上限和食品安全不是评分项。通过硬过滤后，才可以按营养贴合、库存利用、时间、口味、厨具和变化最小做分层优化。

Java 构建结构化 `RecommendationExplanation`，包含菜品选择原因、份量依据、本餐额度使用、未来剩余额度、活跃约束、偏好取舍、数据质量、待确认项、证据和限制。Spring AI 只能改写这些事实；解释失败时仍返回 Java 结构化结果。

## 5. 模型边界

Spring AI 只负责：

- 从文字或图片中提取待用户确认的画像、库存和烹饪变化草稿；
- 根据已发布菜谱步骤生成适合用户水平的教学表达；
- 解释为什么这样搭配；
- 在不改变约束的情况下调整口味和表达；
- 输出固定 JSON；
- 生成 SSE 最终展示内容。

模型不得：

- 自行修改食材 ID 和克数；
- 自行修改菜谱版本、配料比例、油盐用量、投放顺序、食品安全参数和关键完成条件；
- 把临场生成的菜谱直接标记为已审核；
- 生成新的营养数字并作为事实；
- 调整药物；
- 用检索片段突破规则；
- 在没有可行解时编造方案。

输出固定为：

- `profileSummary`：本次使用的结构化画像摘要；
- `corePrinciples`：核心原则；
- `mealPlan`：餐次、菜谱版本、食材 ID、名称、克数和确定性步骤引用；
- `cookingTutorial`：只包含后端给定步骤事实的易懂表达，不包含新的关键参数；
- `nutrientSummary`：Java 复算后写入；
- `decision`：包含唯一 `SafetyPermission`、`reasonCategories` 数组、`actionDispositions` 数组和稳定的 `decisionReasonCodes`；只有本次执行了测量评价时才包含 `MeasurementDecision`；
- `recommendationExplanation`：由 Java 生成的选择原因、份量依据、额度使用、剩余额度、活跃约束、数据质量和待确认项；
- `evidenceRefs`：方案确定后补充的来源引用。

校验分三层：

1. JSON Schema：必填、枚举、类型、范围和禁止额外字段；
2. 领域校验：食材 ID、单位、重复项、数据版本和禁忌；
3. 营养复算：餐次和全天硬约束。

最多允许一次格式修复和一次明确错误码驱动的内容修复。仍失败时返回确定性求解结果或无可行方案，不无限调用模型。

未经完整校验的食谱不能通过 SSE 流给用户。SSE 可以先发送处理阶段，最后发送通过校验的完整结果。

### 5.1 SSE 只做最外层 WebFlux 封装

应用主体使用同步 Java。只在接口适配层使用 Reactor/WebFlux 类型封装 SSE：

```text
RecommendationSseController
    -> Flux<ServerSentEvent<RecommendationEvent>>
        -> RecommendationApplicationService (普通 Java)
            -> RecommendationProgressSink (普通 Java 回调接口)
```

技术约束：

- 主 Web 运行时沿用挂号项目的 `spring-boot-starter-web`；
- 额外引入 `spring-webflux` 模块，只用于 `Flux` 和 `ServerSentEvent` 外层适配；
- 不引入 `spring-boot-starter-webflux`，避免把整个应用切换为响应式运行时；
- Controller 和 SSE adapter 之外不出现 `Mono`、`Flux` 或 Reactor `Context`；
- 数据库继续使用 Spring JDBC，不使用 R2DBC；
- Redis 继续使用 `StringRedisTemplate`/Redisson，不使用 Reactive Redis；
- Spring AI、规则、求解和校验都暴露普通同步 Java 接口；
- 耗时任务交给 Java 21 虚拟线程执行器，不能阻塞请求线程；
- 客户端取消订阅时设置取消标记，应用服务在阶段边界检查并停止后续模型调用；
- 中间事件只报告阶段和可公开进度，最终通过校验后才发送完整方案。

第一版只实现这一种 SSE 适配，不同时维护 `SseEmitter`。工程初始化先在 Boot 4.1.1 下验证 MVC 流式返回、断开取消、慢客户端和代理超时；如果验证失败，再单独评审适配实现，不能直接把整个应用改成 WebFlux。

SSE 事件固定为：

- `STARTED`；
- `VALIDATING`；
- `SOLVING`；
- `GENERATING_EXPLANATION`；
- `COMPLETED`；
- `FAILED`；
- 可选 `HEARTBEAT`。

`COMPLETED` 事件必须只有一次。`FAILED` 只返回稳定错误码和可公开信息，不能泄露提示词、堆栈、模型原始响应或健康隐私。

推荐任务使用独立的 `RecommendationTaskStatus`：

- `PENDING`；
- `RUNNING`；
- `SUCCEEDED`；
- `FAILED`；
- `CANCELLED`；
- `TIMED_OUT`。

SSE 的 `COMPLETED` 是任务事件，`PlanStatus.COMPLETED` 是用户方案生命周期状态，两者不是同一个枚举。任务取消只终止尚未执行的工作；已经落库的方案版本仍按方案状态处理。

## 6. 状态、长上下文和差分

### 6.1 不保存文本长记忆

长上下文由结构化状态实现：

- 稳定资料：年龄、性别、身高、诊断、过敏、长期忌口；
- 可变资料：体重、血糖、用药、家中食材、目标；
- 不可变事实：测量、已吃记录、用户确认；
- 当前投影：从事实重建的画像快照；
- 方案版本：每次推荐、确认和替换的不可变版本。

对模型只传当前结构化快照、本次增量和必要的已确认方案。对话摘要不能作为医疗事实源。

每条健康事实保留来源和确认状态，例如用户自述、用户确认、专业人员录入、医疗机构导入或系统推断。系统推断不能自动升级为已确认事实。事实修正以更正事件追加，保留原值、修正值、原因和操作者，不能覆盖历史记录。

### 6.2 影响图

状态差分不是对自然语言做文本 diff，而是：

`字段变化 → 命中规则变化 → 约束变化 → 影响时间窗 → 待优化餐次`

例子：

- 新晚餐偏好只影响晚餐软目标；
- 新午餐摄入影响当天剩余额度和所有尚未吃的餐；
- 新体重趋势可能影响下一天起的全天热量目标；
- 一次餐后血糖通常先关联对应餐次，不直接降低下一餐碳水；
- 新药物可能直接触发重新准入或转人工。

### 6.3 方案生命周期

方案版本不可覆盖，至少使用以下状态：

- `DRAFT`：求解或表达尚未完成；
- `VALIDATED`：已通过规则、数据质量和 Java 复算；
- `CONFIRMED`：用户确认采用；
- `CANCELLED`：已确认方案被用户取消，保留历史并释放未消耗预留；
- `EXPIRED`：输入版本、有效期或安全状态已失效；
- `INTERRUPTED`：方案执行期间因新测量或急症而中断；
- `COMPLETED`：相关餐次均已结束或记录实际摄入。

只有 `VALIDATED` 可以确认。任何调整都新建 `plan_version`，记录原因码、父版本和受影响餐次。已吃事实永远冻结；当新测量要求停止推荐时，历史版本仍保留，但所有尚未开始的未来餐失效。

餐次执行状态与方案状态分开，至少区分 `GENERATED`、`CONFIRMED`、`PARTIALLY_CONSUMED`、`CONSUMED`、`CANCELLED` 和 `INVALIDATED`。

P2 必须实现普通冻结规则：

- 已吃或部分已吃：历史摄入永远不修改，只处理尚未吃部分；
- 已确认、未吃：普通偏好和普通重新求解默认冻结；
- 已生成、未确认：普通请求可以重新求解；
- 未生成：按当前目标正常求解。

P4 再增加安全中断矩阵：

- 已吃或部分已吃：不修改历史，只追加更正和安全审计；
- 已确认、未吃：新安全事件可以标记为 `INVALIDATED`，但不能删除旧版本；
- 已生成、未确认：新安全事件立即失效；
- 未生成：安全许可不是 `ALLOWED` 时不再生成。

冻结用于防止普通优化覆盖用户确认，不能让旧方案凌驾于新的安全判断。方案失效只影响未来执行，不撤销已经发生的 `intake_event`。

### 6.4 业务闭环

系统必须形成由真实事实驱动的 Business Loop：

```text
用户画像、疾病、目标、库存和当天已吃
    → 安全许可与营养目标计算
    → 食材克数求解与 Java 营养校验
    → 用户确认并执行
    → 实际摄入记录
    → 体重、血糖和营养充分性评价
    → KEEP、调整未来餐、重算目标或转专业人员
    → 下一轮推荐
```

闭环约束：

- 推荐方案不等于实际摄入，只有用户确认的摄入事件才能扣减额度和进入效果评价；
- 测量必须保留发生时间、语境、单位和质量，不能只按录入时间解释；
- `OutcomeEvaluator` 只输出六类结构化评价、原因码和 `MeasurementDecision`，不直接修改目标；
- 目标变化仍需经过安全许可、规则版本和目标计算模块；
- 测量上报和摄入后的长期效果评价都收敛为同一套 `MeasurementDecision`；两条入口都必须回到 `安全 → target → MealBudgetAllocator → solver → MealPracticalityValidator → Java 校验`，不能直接改克数；
- 短期体重不降、单次血糖异常或记录不完整不能自动扩大热量缺口或压低下一餐碳水；
- 每轮决策保存输入快照、评价结果、受影响餐次和父方案版本；
- 急症、营养不足、关键数据缺失或规则冲突随时终止闭环并转介。

`OutcomeEvaluator` 依次输出 `DataCompletenessAssessment`、`AdherenceAssessment`、`MeasurementQualityAssessment`、`TargetAchievementAssessment`、`TrendAssessment` 和 `MeasurementDecision`。评价必须考虑记录不完整、水分变化、测量时间不一致、运动、急性病和药物变化，只描述事实，不进行道德评价。它不能直接修改目标；任何调整决策都必须重新进入安全、目标、额度、求解和校验链路。

P0～P3 建立画像、目标、求解、确认和摄入事实；P4 才启用测量趋势、`OutcomeEvaluator` 和反馈驱动的未来餐调整；P5 用真实用户验证评价规则是否可靠。

### 6.5 Java 控制的有限工作流循环

系统可以具有 Agent Loop 的“感知—判断—执行—观察”结构，但实现为 Java 控制的有限状态工作流，不允许模型自主无限循环。

`RecommendationWorkflow` 的固定步骤为：

1. `PERCEIVE_INPUT`：读取结构化画像、本次请求、库存、摄入和测量；
2. `ASSESS_SAFETY`：计算基础等级和当次安全许可；不是 `ALLOWED` 时立即按处置动作结束；
3. `BUILD_TARGETS`：A 级按已发布规则计算并合并有效专业目标，B 级只装载完整有效的专业目标；
4. `ALLOCATE_MEAL_BUDGET`：扣除已吃并为当前与未来餐分配额度；
5. `BUILD_CANDIDATES`：由 Java 根据库存、食物数据质量、审核菜谱、厨具、时间和禁忌建立候选集；
6. `SOLVE`：调用确定性求解器选择菜谱份量、简单食物和允许变体；
7. `VALIDATE_PRACTICALITY`：检查份量、餐次和烹饪可执行性，必要时最多重算一次；
8. `VALIDATE_SOLUTION`：Java 复算原料、菜谱、餐次与全天营养并校验；
9. `BUILD_TUTORIAL`：从已发布菜谱版本加载结构化步骤；
10. `GENERATE_PRESENTATION`：可选调用 Spring AI 生成教学表达、解释或固定格式输出；
11. `REVALIDATE_OUTPUT`：重新执行 Schema、领域、菜谱版本和营养校验；
12. `COMPLETE`、`NEED_MORE_DATA`、`HUMAN_REVIEW` 或 `STOP`。

模型工具调用只允许出现在明确步骤内，并执行以下限制：

- 工具使用白名单、类型化输入输出和最小数据权限；
- 模型不能调用修改药物、修改目标、确认方案、写实际摄入或放宽禁忌的工具；
- 识别结果和模型输出只能形成草稿，不能直接成为健康事实或已确认方案；
- 每个模型步骤设置调用次数、总步骤数、超时、取消和费用上限；
- 第一版最多一次格式修复和一次内容修复，不允许模型自行决定继续循环；
- 每次调用记录工具、输入版本、结果摘要、错误码和校验结果；
- 客户端取消、输入版本变化或安全许可改变时，在阶段边界停止后续调用。

第一版不引入自主 Agent 框架。以后即使接入 Agent 框架，也只能作为 `RecommendationWorkflow` 内部的受限适配器，不能取得规则、目标、克数和最终确认的控制权。

## 7. 数据存储

### 7.1 MySQL

MySQL 是唯一事实源，至少保存：

- `user_profile`、`profile_snapshot`：当前基础资料、不可变快照和版本；
- `condition_record`：疾病声明、来源和状态；
- `medication_statement`：药物、剂型、频次、开始结束时间和来源；
- `allergy_intolerance`：过敏和不耐受；
- `measurement_event`：测量值、单位、发生时间、记录时间、语境和来源；
- `intake_event`、`intake_item`：实际摄入事件，以及简单食物或熟制成品的重量、基准和营养快照引用；
- `pantry_item`、`pantry_lot`：家中食材、批次、数量范围、来源、确认状态和保质期；
- `pantry_reservation`：方案版本对库存批次的预留、消耗、释放和过期；
- `pantry_change_event`：入库、修改、预留、消耗和作废事件；
- `recognition_draft`：照片或文本识别候选；用户确认前不能进入求解；
- `food_item`、`food_item_state`、`food_nutrient`：食材、状态和版本化成分值；
- `food_allergen`、`ingredient_allergen`：食材、配料和明确过敏原关系；
- `condition_nutrient_rule`：疾病、适用人群和营养素约束关系；
- `medication_food_risk`：药物类别和饮食风险关系；
- `food_substitution`：带适用条件的食材替代关系；
- `cooking_method`、`cooking_method_parameter`：烹饪方式和受控参数模式；
- `equipment`、`recipe_equipment_variant`：厨具能力和已审核菜谱设备变体；
- `recipe`、`recipe_version`、`recipe_ingredient`：菜谱、不可变版本和精确配料；
- `recipe_step`、`recipe_step_dependency`：结构化步骤、完成条件和依赖；
- `recipe_review`、`recipe_audit_log`：配方、烹饪、食品安全、营养和工程审核；
- `cooking_transform`、`nutrition_retention_factor`：有来源的生熟重、出成率和分营养素转换；
- `recipe_nutrition_result`：原料、成品、每份和每 100 克的版本化计算结果；
- `evidence_source`、`knowledge_review`：证据来源、版本和专业审核；
- `nutrition_formula`、`formula_parameter`：公式注册表、参数、适用条件和版本；
- `nutrition_target_set`、`nutrition_target_entry`：目标、来源、上下限、质量和版本；
- `meal_budget`：餐次额度、扣减、冻结、未来保留和分配规则版本；
- `professional_target`、`professional_target_version`：专业人员设定的目标、有效期和审计；
- `rule_set`、`rule_entry`：规则版本、来源、审核状态；
- `plan`、`plan_version`、`meal`、`meal_item`：方案、不可变版本和餐次执行状态；
- `plan_confirmation`：用户确认、取消和失效事实；
- `cooking_execution`、`cooking_execution_step`：实际烹饪会话和步骤事件；
- `cooking_actual_ingredient`：计划与实际用料、替换和变更原因；
- `recommendation_task`、`recommendation_event`：可恢复的任务状态和公开事件；
- `outcome_evaluation`：结构化效果评价、原因码、受影响餐次和父方案版本；
- `capability_switch`、`capability_switch_event`：Kill Switch 当前范围和不可变变更记录；
- `decision_audit`：输入版本、唯一安全许可、原因分类数组、处置动作数组、测量决策、约束、求解状态和校验结果；
- `access_audit`：敏感健康数据访问审计。

本清单是最终领域模型，不代表第一批一次建完所有表。Flyway 按 P0～P4 逐阶段创建；每张表归属唯一模块，跨模块只能通过应用接口读取或写入。数据库唯一约束、乐观锁、外键或等价业务约束、事件追加顺序和失败事务补偿必须随对应迁移一起交付。

`outbox_event` 在真正引入异步集成时再建表并接线，第一版同步主链路不创建空壳消息流程。

每个写入接口都有 `idempotencyKey` 和数据库唯一约束。方案生成使用乐观锁或版本比较，旧输入不能覆盖新测量产生的状态。

每个方案记录：

- `profileVersion`；
- `profileSnapshotId`；
- `ruleSetVersion`；
- `targetSetVersion`；
- `foodDatasetVersion`；
- `recipeVersions`；
- `cookingTransformVersion`；
- `foodSafetyRuleVersion`；
- `pantryVersion`；
- `intakeVersion`；
- `schemaVersion`；
- `modelVersion`；
- `promptVersion`；
- 输入摘要哈希和输出哈希。

版本或快照 ID 必须能够重建当次推荐使用的完整输入。不能因为画像、规则或食物数据后来更新，就无法解释历史方案。

### 7.2 Redis

Redis 只用于：

- 对话快照缓存；
- 短期任务状态；
- 分布式锁；
- 限流。

Redis 丢失后必须能从 MySQL 重建。不能把 Redis 作为唯一饮食画像存储。

### 7.3 RocketMQ

第一版同步推荐链路不接 RocketMQ。以下需求出现后再通过 transactional outbox 和幂等消费者引入：

- 设备测量异步接入；
- 批量重算；
- 通知；
- 跨服务审计或分析。

这样仍保留既定技术选型，但不提前引入重复消费、乱序和旧版本覆盖问题。

### 7.4 隐私、安全和权限

疾病、用药、血糖、体重、过敏和实际摄入均按敏感健康数据处理：

- 明确记录处理目的、范围、期限和用户授权；
- 所有查询按用户和角色隔离，普通用户、营养师、医生和管理员最小权限分配；
- 传输使用 TLS，敏感字段按风险加密存储，展示和日志默认脱敏；
- 禁止日志记录完整病史、提示词中的健康详情、模型原始隐私响应和访问令牌；
- 调用模型时只发送当前任务必要字段，并优先使用不保存请求的服务配置；
- 用户数据导出、撤回授权和删除请求使用独立审计流程；依法必须保留的记录不能静默删除；
- 每次专业人员或管理员访问、导出和修改健康数据都写入不可变访问审计；
- 境外模型、跨境传输、第三方处理者和自动化决策在接入前完成单独评估。

具体上线方式必须接受适用地区的隐私、健康服务和产品监管审查。本节定义工程基线，不替代法律意见。

### 7.5 库存预留与实际摄入事务边界

`PlanConfirmation`、`PantryReservation` 和 `IntakeEvent` 是三个独立业务事实：

- 确认方案只表示用户计划采用，不表示已经吃完；
- 库存预留只减少可用量，不表示已经消耗；
- 实际摄入记录用户真正吃下的食物和数量，才会扣减当天营养额度。

库存流程为：

`可用库存 → 生成方案 → 原子预留 → 用户确认或取消 → 部分/全部实际使用 → 消耗或释放剩余预留`

实际摄入流程为：

`记录实际克数 → 幂等写入 intake_event → Java 复算实际营养 → 更新当日投影 → 触发下一轮评价`

`IntakeItem` 分为：

- `SIMPLE_FOOD`：引用食材版本、实际克数和重量基准；确认摄入时消耗尚未消耗的简单食物库存预留；
- `COOKED_BATCH`：引用 `CookingExecution`、成品批次、实际食用克数、成品重量基准和 `recipe_nutrition_result` 版本；其原料库存已在实际投入时消耗，写摄入时不得再次扣库存。

事务规则：

- 方案通过最终校验后、标记 `VALIDATED` 前，按请求中的 `pantryVersion` 原子创建带过期时间的预留；
- 预留失败表示库存已变化，当前结果不能返回为可确认方案；应用服务刷新库存后最多重新求解一次；
- 用户确认时再次检查预留仍有效、批次版本一致且数量充足，否则将方案标记 `EXPIRED` 并要求重新生成；
- 预留使用批次版本和条件更新，不能超出 `availableQuantity`；
- 每个预留记录方案版本、批次、预留量、已消耗量、过期时间和状态；
- 支持部分摄入、部分库存消耗和剩余预留释放；烹饪配料与简单食物使用各自唯一的消耗路径；
- 方案取消、失效或预留超时只释放未消耗部分；
- 重复摄入请求通过 `idempotencyKey` 和唯一约束保证只扣减一次；
- 并发方案竞争同一批库存时只有满足版本条件的事务成功；
- 摄入更正追加更正事件，不直接覆盖原始事实。

烹饪执行增加第四类事实，但不能取代前三类：

- 开始烹饪时把计划配料快照复制到 `CookingExecution`，不修改原菜谱版本；
- 实际投入配料时按幂等事件消耗对应库存预留，部分投入只消耗实际数量；
- 换料或超量使用创建执行修订和新的营养计算结果，不覆盖原计划；
- 完成烹饪只确认成品事实，不自动创建摄入；
- 用户记录实际食用重量后才创建 `IntakeEvent`；
- 成品剩余可以进入单独的熟食库存批次，但必须携带菜谱、成品营养和保存信息版本。

## 8. 接口边界

产品接口边界如下，具体交付批次以第 17.8 节为准：

- `PUT /api/v1/profile`：写入基础资料；
- `POST /api/v1/measurements`：上报血糖或体重；
- `POST /api/v1/intakes`：幂等记录实际吃下的部分或全部食物；
- `POST /api/v1/intakes/{id}/corrections`：追加摄入更正，不覆盖原事件；
- `POST /api/v1/pantry/recognize-text`：P3 从自然语言提取库存候选；
- `POST /api/v1/pantry/recognize-image`：P3 从照片或购物小票提取库存候选；
- `POST /api/v1/pantry/confirm`：确认、修改并写入库存；
- `GET /api/v1/pantry`：查看当前库存；
- `POST /api/v1/pantry/adjust`：手工增减、消耗或作废库存；
- `POST /api/v1/recommendations`：请求单餐或一日方案；
- `POST /api/v1/recommendations/craving`：评估受限制食物能否小份纳入当前方案；
- `GET /api/v1/recommendations/{id}/events`：SSE 获取处理状态和最终方案；
- `GET /api/v1/recommendations/{id}`：断线重连后查询任务状态或最终结果；
- `DELETE /api/v1/recommendations/{id}`：请求取消尚未完成的推荐任务；
- `POST /api/v1/plans/{id}/confirm`：确认方案；
- `POST /api/v1/plans/{id}/cancel`：取消未完成部分并释放剩余预留；
- `POST /api/v1/plans/{id}/replace`：P2 只支持 `DRAFT` 或 `VALIDATED` 且尚未确认餐次的确定性替换，P4 扩展到已确认未来餐的动态修订；
- `GET /api/v1/plans/current`：获取当前确认方案；
- `GET /api/v1/recipes/{id}/versions/{version}`：读取已发布菜谱、配料、步骤和营养；
- `POST /api/v1/recipes/{id}/scale`：在审核范围内按人数或份量缩放并重新计算；
- `POST /api/v1/cooking-executions`：P3 基于已确认餐次开始烹饪；
- `POST /api/v1/cooking-executions/{id}/steps/{stepNo}/complete`：P3 幂等完成一个步骤并支持恢复；投料步骤要求用户确认完全按计划投入，并据此记录实际投入和消耗预留；
- `POST /api/v1/cooking-executions/{id}/adjustments`：P4 提交换料、实际用量或做法变化草稿并重新校验；
- `POST /api/v1/cooking-executions/{id}/finish`：P3 支持完全按计划执行时关闭会话，P4 扩展为记录偏差、成品重量、实际份数和剩余量；
- `POST /api/v1/professional-targets`：有权限的专业人员创建带有效期的目标版本；
- `POST /api/v1/professional-targets/{id}/revoke`：撤销专业目标并保留审计；
- `POST /api/v1/questions/food`：方案确定后的「能不能吃」问答，第五批实现。

推荐请求必须包含：

- `scope`：`SINGLE_MEAL` 或 `FULL_DAY`；
- 解馋请求使用 `CRAVING_PORTION`；
- `date` 和时区；
- 单餐时的 `mealType`；
- `pantryMode`：`ONLY_AVAILABLE` 或 `PREFER_AVAILABLE`；
- 使用的 `pantryVersion`；
- `profileVersion`；
- `idempotencyKey`。

`POST /recommendations` 返回持久化的 `recommendationId`。HTTP 连接断开不删除任务；客户端可以使用 `Last-Event-ID` 恢复事件，或通过查询接口取得终态。虚拟线程执行器必须设置并发上限、队列容量、任务超时和拒绝策略，不能用无限虚拟线程掩盖模型、数据库或求解器容量限制。

## 9. 指南和 RAG

### 9.1 规则证据与运行时检索

指南有两个不同用途：

1. 规则编制：临床审核人员根据官方指南形成可计算规则，记录来源、版本、适用人群和审核状态。
2. 运行时解释：方案确定后检索出处，或回答「这个病能不能吃某样」。

运行时检索不决定克数，不修改硬约束，也不能把指南中的通用示例直接当成个人方案。

规则生命周期为：

`DRAFT → CLINICAL_REVIEW → TESTED → PUBLISHED → RETIRED`

每条规则保存规则编号、适用病种和人群、排除条件、触发条件、执行动作、证据来源和等级、适用地区、优先级、编制与审核人员、生效失效时间、版本、测试用例和回滚版本。第一版实现发布流程和数据结构，不建设独立的规则治理后台。

证据链分为五类，不能混为一个引用列表：

1. 临床规则证据；
2. 食物成分和数据质量证据；
3. 菜谱、烹饪转换和食品安全证据；
4. 目标计算与求解结果；
5. 模型生成的教学表达和解释。

关键营养目标必须能追溯到规则、版本、适用人群、审核记录和生效时间；模型解释只能引用前四类已确定事实，不能反向修改它们。

检索文档按以下类型分开：

- 食养原则；
- 病种适用范围和排除项；
- GI、食物交换和食材选择方向；
- 示例食谱；
- 风险和转介提示。

第一版只接卫健委原文链接和少量可引用片段，不复制第三方整理稿。

### 9.2 知识关联模型

系统需要知识图谱的建模思想，但第一版不建设独立知识图谱产品，也不引入图数据库。V1 只通过 MySQL 显式关系表和普通 SQL 组织、加载候选关系，不进行运行时图遍历或向量召回；规则引擎、目标模块、求解器和 Java 校验仍拥有最终决定权。

第一版需要表达的知识实体包括：

- 疾病和适用人群；
- 症状、体征和测量指标；
- 营养素和营养目标；
- 食材、加工食品、过敏原和烹饪方式；
- 药物类别和饮食风险；
- 替代关系；
- 指南、证据、规则和审核版本。

用户画像、用户测量、库存、实际摄入和方案不进入共享医学营养知识库。它们是带用户权限和不可变版本的业务事实，只通过 ID、规则版本和证据引用关联知识。

核心关系包括：

- 疾病规则约束营养素；
- 食材含有营养素；
- 食材或配料包含过敏原；
- 药物规则触发饮食安全风险；
- 烹饪方式改变重量基准或有来源的营养参数；
- 食材在明确条件下可以替代另一食材；
- 规则和关系由证据支持并经过审核。

不使用简单的「疾病 → 推荐/禁止 → 食材」黑白名单代替计算。一般适宜性由：

`疾病或专业目标 → 营养约束 → 食材成分 → 求解 → Java 校验`

推导。只有明确过敏原、药食禁忌、急性期禁忌和专业人员完全禁止等有可靠证据的关系，才能形成直接硬拦截。

每条知识关系至少保存：

- 起点类型和 ID；
- 关系类型；
- 终点类型和 ID；
- 限制程度或影响方向；
- 适用人群和排除条件；
- 剂量、份量或条件范围；
- 证据来源、证据等级和数据质量；
- 规则版本、审核状态、生效时间和失效时间。

### 9.3 知识存储演进

V1 使用 MySQL 显式关系表，不设计万能 `entity_relation` 表承载所有语义：

- `condition_nutrient_rule`：疾病和营养素约束；
- `food_nutrient`：食材成分；
- `food_allergen`、`ingredient_allergen`：明确过敏原；
- `medication_food_risk`：药物类别和饮食风险；
- `food_substitution`：带条件的食材替代；
- `cooking_transform`：有来源的生熟重和烹饪转换；
- `evidence_source`、`knowledge_review`：证据和审核。

这样便于初级开发者理解、使用外键和事务、按模块维护，也能通过普通 SQL 完成第一版查询。

后续只有出现实际需求才增加检索能力：

- 指南和文献数量达到普通数据库检索难以维护时，增加全文检索；
- 语义召回经过离线评测证明优于关键词和元数据过滤时，增加向量检索；
- 多跳遍历成为真实性能瓶颈、关系模型稳定且确有图分析或可视化需求时，评估 Neo4j。

Elasticsearch、向量数据库和 Neo4j 都不是固定的 V2/V3 必选项。即使以后引入，它们也只是从 MySQL 和版本化证据构建的可重建读模型，不能成为用户事实、临床规则或最终方案的唯一事实源。

图或向量召回结果只能产生候选关系，必须经过适用条件、证据版本、数据质量和安全规则校验，不能直接决定用户能不能吃或具体克数。

### 10.1 复用原则

本项目采用「核心业务自研、兼容源码可移植、全部在本仓库开源」的原则：

1. 规则、求解编排、状态管理和安全校验等核心业务由本项目主导设计；
2. MIT、Apache-2.0、BSD、ISC 等许可证明确兼容的代码，可以选择性移植、翻译或改写；
3. 移植前必须证明代码质量和适配价值，不能因为许可证允许就整库搬入；
4. 通用能力优先通过 Maven 使用正式发布的依赖；只有依赖无法满足、代码边界小且稳定时才移植源码；
5. GPL、AGPL、O'Saasy、无许可证、许可证不明和来源不明源码不进入主仓库；
6. 临床规则、食谱和营养数据单独核对来源，不能跟随代码许可证推定。

本仓库是产品实现的唯一源码仓库，不保留私有业务模块或仅在本地存在的核心实现。自研和合法移植的 Java 源码、测试、数据库迁移、配置模板、提示词模板及构建文件全部公开。密钥、真实用户健康数据、受限数据集、模型权重、运行日志和构建产物不得提交；这不属于隐藏业务源码。

### 10.6 拍照、OCR 和条码

拍照输入分三条路径：

1. 包装食品先用 ZXing 识别条码，再查询已授权的产品数据；
2. 购物小票和包装文字用 PaddleOCR 或经过验证的 Java OCR 组件；
3. 冰箱或散装食材照片交给多模态模型生成候选。

开源食物视觉项目只能作研究参考：

- [FoodSeg103 Benchmark](https://github.com/LARC-CMU-SMU/FoodSeg103-Benchmark-v1) 代码为 Apache-2.0，可参考食物分割和多标签输出；

- 图片无法可靠给出克数、生熟状态和剩余库存。

第一版不复制或训练这些视觉模型。多模态识别只创建 `recognition_draft`，所有食材和数量必须由用户确认。

- 两次并发推荐竞争同一份库存；
- 单位错误、迟到上报和重复上报；
- 已吃早餐后请求晚餐；
- 家中食材不足；
- 过敏和偏好冲突；
- 过敏食物即使只想吃一口也被拒绝；
- 限制原因未知时要求澄清；
- 高碳水食物的小份可以放入剩余额度；
- 用户期望份量过大，返回更小份量；
- 小份也会突破硬约束，返回替代品；
- 不得生成加药、挨饿、催吐或极端运动补偿；
- 硬约束无解；
- 急症停止推荐；
- 营养不良风险转介；
- 新旧版本并发和幂等重放。

这些数据按本仓库 Apache-2.0 发布。数值仅用于触发测试分支，不能宣称代表临床分布。

#### USDA FoodData Central 小型食材夹具

USDA FoodData Central 数据是 CC0，可以选取少量 Foundation Foods 或 SR Legacy 记录作为测试夹具。仓库中应保留：

- `fdcId`；
- 英文原名；
- 版本和发布日期；
- 每 100 克营养值；
- USDA 来源说明；
- 手工中文别名与原始数据分开。

适合测试：

- 每 100 克到实际克数的换算；
- 单位归一；
- 缺失营养素；
- 同食物不同数据版本；
- 求解器上下限。

它不能完整代表中国家常菜，不能把手工中文映射描述成官方中文名。

#### FHIR 官方示例和 SMART 合成数据

FHIR 规范内容采用 CC0。可以参考官方 Observation 示例编写：

- 体重：LOINC `29463-7`；
- 血糖：LOINC `2339-0`；
- UCUM 单位 `kg`、`mg/dL`、`mmol/L`。

`smart-on-fhir/sample-bulk-fhir-datasets` 的数据明确可按 CC0 使用，且由 Synthea 生成。可以截取少量 Patient、Condition、MedicationRequest 和 Observation，测试导入映射。

首批内部模型不直接使用 FHIR；这些数据只用于适配层和字段语义测试。

### 11.2 可以生成或离线分析，但不作为临床真值

#### Synthea

Synthea 软件是 Apache-2.0，生成数据没有真实患者隐私限制。可用来生成：

- 虚构患者；
- 疾病、用药和测量历史；
- FHIR/CSV 导入压力数据。

生成记录使用的术语系统可能有各自许可，提交前要检查 NOTICE。Synthea 不提供本项目所需的可靠饮食摄入和个体化营养目标。

#### SimT2D

`everval/SimT2D.jl` 使用 MIT 许可证，但当前实现不作为测试数据生成器：

- 多个事件概率和生理参数没有文献来源；
- 随机种子没有贯穿主要随机过程，难以稳定复现；
- 代码字段与仓库 CSV 的血糖单位存在冲突。

只参考「时间序列 + 餐食/运动/用药事件日志」的数据结构。五态决策使用本仓库自己编写、固定种子且逐条标明预期状态的合成序列。

#### GluFormer

GluFormer 代码为 Apache-2.0，可以生成类似 CGM 的轨迹，但模型主要来自非糖尿病成人数据，依赖和模型体积较大。第一版不引入，只作为以后压力和缺失片段测试的候选。

#### NHANES

NHANES 有饮食回顾、体重、血糖和化验等公开使用数据，适合离线统计分析和构建现实范围测试。

它仍是真实调查数据，并受 NCHS 数据使用协议约束：

- 只能用于统计分析和报告；
- 不得重识别；
- 不与可识别数据连接。

因此第一版不把 NHANES 个体行记录提交进仓库，也不用它作为接口单测夹具。

### 11.3 不能直接使用

- `china-food-composition-data` 和 `cn-food-mcp` 中来自《中国食物成分表》的识别数据；
- 从薄荷等网站抓取的食物数据；
- Open Food Facts 整库或混入自有数据库的数据，除非单独处理 ODbL 义务；
- 第三方仓库中来源不明的食谱和营养值；
- NutriChef 的疾病知识 JSON；
- metabolic-care-assistant 的临床阈值；
- 国家指南中的整套示例食谱和第三方整理稿，除非确认再发布授权；
- 真实用户、简历项目或工作数据。

## 12. 测试策略

### 12.1 规则单元测试

- 支持清单和排除规则；
- 血糖单位换算；
- 测量发生时间和记录时间；
- 五态决策；
- 长期准入与当次安全许可组合；
- `SafetyPermission`、原因分类和处置动作组合；
- 不可覆盖安全约束拒绝冲突的专业目标；
- 公式注册表、输入缺失、适用人群和版本切换；
- 热量、蛋白质和碳水上下限；
- 过敏和独立药物安全分流；
- 漏餐、断食、急性病、脱水和换药场景；
- 疾病到营养约束的关系必须经过适用人群、版本和审核状态过滤；
- 食材替代后重新执行过敏原、禁忌和营养校验；
- 受限制食物的五类原因和 `CRAVING_PORTION`；
- 多病约束优先级；
- 无可行解。

### 12.2 成分计算测试

- 每 100 克换算；
- 生熟和可食部；
- 缺失值不当作 0；
- `KNOWN`、`ESTIMATED`、`UNKNOWN` 和 `NOT_APPLICABLE`；
- 关键营养素不满足质量门槛时排除候选；
- `NutritionDataQualityPolicy` 的 `ACCEPT`、`RESTRICT` 和 `REJECT`；
- 同一食材在不同疾病约束下得到不同质量准入结果；
- 相同食材不同版本；
- 生熟重、可食部和有来源的烹饪换算；
- 原料营养、成品营养、每份营养和实际摄入营养分离；
- 油盐酱料、弃汤、实际成品重量和实际食用重量；
- 未知转换参数不会被默认值或 0 补齐；
- 菜谱缩放后配料、步骤投放量和营养结果一致；
- 小数精度和单位归一；
- 模型返回的营养数字被忽略。

### 12.3 求解器测试

- 可行方案满足全部硬约束；
- 无解时返回结构化冲突约束、来源和后续动作；
- 最小/最大份量和离散份量可执行；
- 分层优化不会用偏好突破营养质量；
- `MealBudgetAllocator` 不会把全部剩余额度交给当前餐；
- 已吃扣减、已确认冻结、未来餐保留和必要加餐额度；
- 当前餐导致未来餐无解时只联合重算允许变化的餐次；
- 已吃和已确认餐被冻结；
- `ONLY_AVAILABLE` 不使用库存外食材且不超出现有数量；
- `PREFER_AVAILABLE` 优先库存，不可行时只返回必要补购项；
- 未经用户确认的照片或文字候选不进入求解；
- 临期优先不能突破硬约束；
- 修改一餐后全天仍满足约束；
- 相同输入、相同版本得到可复现结果；
- 偏好变化只影响软目标；
- 优先家中食材但不突破硬约束；
- 解馋软目标不能突破过敏、药食禁忌、营养下限或临床限制；
- `MealPracticalityValidator` 使极小份量、碎片化或明确不可组合的结果重算或拒绝；
- 正餐优先从已发布菜谱和简单食物中求解，不会由任意碎片临场拼菜；
- 菜谱比例只在审核范围内缩放，油盐和调味料始终进入计算；
- 没有适用厨具变体或食品安全条件的菜谱不会进入候选。

固定 benchmark 还要记录规则、食物数据、菜谱数据和求解器版本，变量与约束数量、各层目标值、硬约束结果、营养汇总、耗时、内存和并发资源。同输入复现比较约束和数值结果，不要求说明文字完全一致。

### 12.4 状态和并发测试

- 相同 `idempotencyKey` 不重复写入；
- 延迟测量按发生时间处理；
- 重复和乱序事件不破坏当前投影；
- 旧画像版本不能确认新方案；
- Redis 清空后可从 MySQL 重建；
- SSE 断开后可查询终态并恢复事件；
- 取消任务后阶段边界不再继续工作；
- 方案调整生成新版本且保留父版本；
- 普通偏好变化遵循 P2 普通冻结规则，新安全事件遵循 P4 安全中断矩阵；
- 方案确认、库存预留和实际摄入互不替代；
- 部分摄入只消耗实际数量并释放或保留剩余预留；
- 推荐、实际摄入和测量反馈形成新一轮决策而不覆盖历史事实；
- `OutcomeEvaluator` 只能输出评价，不能直接修改目标；
- 并发替换只有一个版本成功。
- 并发方案对同一库存批次的预留不会超卖。
- 烹饪计划、实际用料、成品重量和实际摄入不会相互覆盖；
- P3 完全按计划投料时，步骤幂等确认只消耗一次库存并产生会话终态；
- P3 收到数量、换料或做法偏差时不会按原计划静默完成；
- 实际换料或超量使用产生执行修订，并且只影响尚未发生的步骤和摄入；
- 烹饪完成不会自动把整份菜记为已吃。

### 12.5 模型契约测试

向模型适配层注入：

- 非 JSON；
- 缺字段；
- 额外字段；
- 不存在的食材 ID；
- 擅自修改克数；
- 编造营养数字；
- 被检索文本诱导突破禁忌。
- 用「只吃一口」诱导模型绕过绝对禁忌；
- 建议加药、跳餐或极端运动抵消。

系统必须拒绝、有限修复或回退到确定性结果。

受控工作流还必须验证：

- 模型只能调用白名单工具；
- 超过步骤、次数、费用或超时上限立即停止；
- 工具输出只形成草稿，未经用户确认不能写入健康事实；
- 模型不能修改目标、食材克数、实际摄入或方案确认状态；
- 模型不能修改菜谱版本、油盐用量、步骤顺序、食品安全参数或完成条件；
- AI 生成的新菜谱只能是草稿，不能绕过审核进入候选；
- 格式修复和内容修复次数固定，不存在自主无限循环。

### 12.6 集成测试

使用 Testcontainers 启动 MySQL 和 Redis，覆盖：

- 画像写入；
- 测量上报；
- 已吃扣减；
- 单餐和全天求解；
- 方案确认；
- 已发布菜谱读取、缩放和步骤完整性；
- 开始烹饪、步骤完成、实际用料调整、成品记录和部分摄入；
- 版本冲突；
- SSE 最终结果；
- 模型失败回退。
- Boot 4.1.1 下 Spring MVC 与最外层 `Flux<ServerSentEvent<?>>` 的实际流式行为；
- 虚拟线程、模型、求解器、队列和数据库连接池达到容量上限时的拒绝与超时；
- Kill Switch 按全局、病种和规则版本停止新任务并中断运行中任务。

SSE 契约测试必须验证：

- 事件顺序合法且 `COMPLETED` 恰好一次；
- 完整校验前不会发送方案正文；
- 客户端取消后不再发起后续模型调用；
- `FAILED` 不泄露提示词、堆栈、模型原始响应或健康隐私；
- 慢客户端不会无限占用内存，`HEARTBEAT` 不影响最终结果。

第一版没有 RocketMQ 集成测试。

### 12.7 不可破坏的验收条件

- 被接受的方案硬约束通过率为 100%；
- D 级场景绝不生成食材方案；
- 当次安全许可不是 `ALLOWED` 时不生成自动方案；
- 目标必须有来源、版本和适用人群；
- 专业目标不能覆盖绝对安全约束；
- 单餐额度来自版本化分配规则且保留未来餐额度；
- 关键营养数据未达到门槛时不进入相关自动求解；
- 模型不能改变求解器确定的食材 ID 和克数；
- 营养汇总全部由 Java 根据同版数据复算；
- 无解必须显式返回，不能降级成模型自由生成；
- 旧版本不能覆盖新状态；
- Kill Switch 能在不发布新代码的情况下停止受影响推荐；
- 每个决定可追溯到画像、规则、数据和模型版本；
- 正式菜谱的配料、步骤、食品安全和营养结果都可追溯到审核版本；
- 烹饪中的换料和实际用量变化必须重新校验，不能仅由 AI 口头放行；
- 测试夹具和产品营养数据严格隔离。

以上条件只能证明实现符合当前输入、规则和数据，不能证明临床规则本身正确，也不能等同于临床安全性 100%。真实用户上线还必须通过专业审核、隐私与监管评估以及分阶段验证。

### 15.3 生产运维与安全运营

生产能力分为以下运营面：

- 规则运营：草稿、审核、灰度、生效、回滚和命中监控；
- 数据运营：食材数据审核、质量告警、版本发布、错误数据下架和影响重算；
- 菜谱运营：配方、步骤、设备变体、食品安全和营养审核，问题菜谱下架及影响方案定位；
- 安全运营：急症命中、禁忌拦截、错误推荐、投诉和人工转介监控；
- AI 运营：调用失败、越权输出、校验拒绝、延迟、令牌和费用；
- 求解运营：可行率、无解率、冲突类型、求解耗时、超时和候选规模；
- 系统运维：JVM、虚拟线程任务、队列、数据库连接池、MySQL、Redis 和外部模型监控；
- 数据安全：备份、恢复演练、密钥轮换、保留期限、导出和删除审计；
- 事故处理：停止推荐、规则或数据回滚、影响用户识别、通知和复盘。

`SafetyGovernanceService` 统一协调规则发布、食材或菜谱数据下架、Kill Switch、影响方案查询、未吃餐失效、回归和恢复审批。它只执行经过授权的治理动作，不编辑临床规则或菜谱事实、不绕过审核，也不参与日常营养决策。

必须提供 `EmergencyKillSwitch`，支持按全局、服务等级、病种、规则集版本、食材数据版本、菜谱版本和模型表达能力停止。开关状态以 MySQL 审计记录为事实源，Redis 只做快速传播；每次变更记录操作者、原因、范围、生效时间和恢复条件。

Kill Switch 命中后：

- 不再创建受影响范围的新自动推荐；
- 运行中任务在下一个阶段边界停止；
- 已吃事实和历史方案保留；
- 未吃的受影响未来餐标记失效；
- 模型表达被单独关闭时可以回退到通过校验的确定性结果；
- 只有经过授权和审计的恢复动作才能重新开放。

虚拟线程不等于无限容量。第一版分别配置推荐任务并发、模型调用并发、求解并发、队列容量、数据库连接池、求解超时、模型超时和任务总超时；具体数值由压力测试确定，不在代码中散落。超过容量时返回稳定错误码或排队状态，不继续创建无限任务。

上线前必须完成备份恢复演练、Kill Switch 演练、规则回滚演练、食材错误数据下架演练和安全事件复盘演练。

## 16. 决策摘要

保留的方向：

- 单餐和一日方案；
- 「特别想吃一次」时，在不突破硬约束的前提下评估小份或替代品；
- 拍照或文字录入家中食材；
- 只有现有食材时的硬约束定制；
- 长期结构化画像；
- 测量后维持或调整；
- 当天已吃扣减；
- 家中食材优先；
- 审核菜谱、精确配料和结构化分步教学；
- 计划用料、实际烹饪、成品和实际摄入分离；
- Java 校验；
- 方案确定后再做 RAG 解释。

修改的方向：

- 「所有慢病」改成支持清单和四级准入；
- 「多病取更紧」改成优先级约束和可行性检测；
- 「模型决定克数」改成求解器决定克数；
- 「只重算一餐」改成冻结已吃餐并重算受影响的未来餐；
- 「停止或继续」改成安全许可、原因分类和处置动作三层决策；
- 「有目标即可求解」改成公式注册、专业审核、目标安全校验和餐次额度分配；
- 「确认方案等于吃掉」改成方案确认、库存预留和实际摄入三个独立事实；
- 「Redis 存画像」改成 MySQL 是事实源、Redis 是缓存；
- RocketMQ 推迟到确有异步需求；
- 药物、急症和营养不良安全能力前置；
- 「模型临场写菜谱」改成审核菜谱决定配料与步骤，模型只生成教学表达；
- 「任意食材克数再拼菜」改成优先求解菜谱份量和简单食物；
- 「做完等于吃完」改成烹饪执行、成品记录和实际摄入三个独立事实；
- 生产安全增加按范围 Kill Switch、规则回滚、数据下架和恢复演练。

## 17. 推荐实施方案

本节把前面的选择收敛成第一版唯一实施方案。未列入的候选技术不进入第一版。

### 17.1 架构形态

采用模块化单体，不拆微服务：

```text
Spring MVC HTTP / SSE adapter
    |
application orchestration (RecommendationWorkflow)
    |
    +-- safety       准入、急症、营养不良和药物安全
    +-- profile      长期画像和当前投影
    +-- pantry       文字、图片、条码、库存确认和预留
    +-- intake       实际摄入和当天已吃扣减
    +-- nutrition    食材、成分、烹饪转换、质量和 Java 复算
    +-- recipe       审核菜谱、精确配料、步骤、缩放和设备变体
    +-- cooking      分步执行、实际用料、成品和剩余量
    +-- equipment    厨具能力和菜谱设备适配
    +-- target       版本化营养目标计算和专业目标
    +-- rule         版本化病种规则和约束构建
    +-- solver       ojAlgo 可行性、克数求解、基准和冲突分析
    +-- plan         单餐、全天、可执行性、替换、解馋和方案版本
    +-- outcome      摄入、测量趋势和结构化效果评价
    +-- task         可恢复推荐任务和 SSE 事件
    +-- ai           Spring AI 做法、解释和固定 JSON
    +-- evidence     方案完成后的指南出处和问答
    +-- audit        决策依据、幂等和版本追溯
    |
MySQL (事实源) + Redis (可丢失缓存)
```

原因：

- 当前只有一个产品和一个代码仓库，微服务会放大事务、版本和部署成本；
- 规则、求解、校验必须在同一个一致性边界内完成；
- SSE 只在最外层适配器使用 `Flux<ServerSentEvent<?>>`，内部保持同步 Java；
- 模块接口先固定，确有独立扩缩容需求时再拆；
- 每个模块拥有自己的应用服务和 Repository，禁止 `PlanService` 直接调用其他模块的 Mapper；
- 跨模块读取和写入必须通过公开接口或应用编排完成，`audit` 只追加记录；
- RocketMQ 保留在技术路线中，但第一版不参与主链路。

### 17.4 推荐主链路

#### 17.4.1 P0～P3 基础确定性链路

一次推荐按以下顺序执行：

1. 接收 `SINGLE_MEAL` 或 `FULL_DAY` 请求。
2. 校验 `profileVersion`、`pantryVersion`、日期、时区和幂等键。
3. 从 MySQL 重建当前画像，不使用对话文本作为事实。
4. 计算基础服务等级以及 `SafetyPermission`、原因分类和处置动作。
5. 检查最新测量是否存在当次急性风险或必要数据缺失，不做趋势驱动调餐。
6. A 级由已审核公式和规则计算目标并合并有效专业目标；B 级只装载完整有效的专业目标。
7. 扣除实际摄入，并由 `MealBudgetAllocator` 生成当前餐和未来餐额度。
8. 按 P2 普通冻结规则固定已吃、已确认和用户指定不改变的餐次。
9. 使用 `NutritionDataQualityPolicy` 过滤或限制候选。
10. 根据餐次额度、库存模式和病种规则构造带来源约束。
11. Java 从已发布菜谱和简单食物构造候选，过滤不适用厨具、时间、步骤、安全条件和失效依赖；
12. ojAlgo 返回 `FEASIBLE`、`PARTIAL` 或 `INFEASIBLE`，决定菜谱份量、简单食物克数和允许变体；无解由业务冲突分析器解释；
13. `MealPracticalityValidator` 检查餐次和烹饪可执行性，必要时把约束交给求解器最多重算一次；
14. Java 按同版食材、菜谱和转换数据重新计算并校验；
15. 后端加载确定性的结构化烹饪步骤；
16. Spring AI 只能生成步骤表达和说明；
17. JSON Schema、领域、菜谱版本和营养复算再次检查模型输出；
18. 最外层 SSE adapter 返回阶段事件和最终方案；
19. 保存通过校验的结果、输入快照和决策审计。

任何一步失败都不能降级成模型自由生成。

P0～P3 期间测量只参与当次安全检查和记录。普通单餐或全天请求对尚未吃餐次的联合优化在 P2 启用，但不会因为趋势自动改变目标。

这条主链路是第一版唯一的有限工作流循环，具备 Agent Loop 的感知、判断、执行和观察结构；步骤、分支、工具和重试由 Java 固定，模型不能自行增加步骤或绕回目标与求解阶段。

P4 的 `CRAVING_PORTION` 完成限制原因判断后复用目标、餐次额度、求解和校验步骤。第五批的指南出处和食物问答只在方案确定后执行，不属于 P0～P3 完成门槛，也不能反向修改方案。

#### 17.4.2 P4 测量反馈增强链路

P4 在基础链路之前增加反馈决策：

1. 接收幂等的实际摄入和新测量事件；
2. 校验发生时间、餐前餐后语境、单位、质量和关联餐次；
3. `OutcomeEvaluator` 生成六类结构化评价、原因码和唯一 `MeasurementDecision`；
4. 根据该决策再次执行当次安全许可；
5. `KEEP` 时保留当前方案，只追加决策审计；
6. `ADJUST_FUTURE_MEALS` 时冻结已吃事实，按安全中断规则处理已确认未吃餐，并只重算受影响的未来餐；
7. `REASSESS_DAILY_TARGET` 时重新进入 `安全 → target → MealBudgetAllocator → solver → MealPracticalityValidator → Java 校验`；
8. `NEED_MORE_DATA` 时要求补充或复测，不生成调整方案；
9. `URGENT_REFERRAL` 时使受影响未来餐失效、停止自动推荐并返回转介动作；
10. 任何调整都创建带父版本和原因码的新 `plan_version`，由用户重新确认。

增强链路不能直接修改目标、历史摄入或已吃餐，也不能把单次异常自动转换成更严格的克数。

### 17.5 家中食材推荐

文字输入：

1. Spring AI 从自然语言提取候选食材、数量、单位和不确定项。
2. Java 完成单位标准化。
3. 用户确认后形成 `pantryVersion`。

照片输入：

1. 多模态模型识别食材候选；
2. 包装食品优先尝试条码；
3. 包装净含量或小票文字后续可接 OCR；
4. 无法估重时要求用户选择个数、份量或克数范围；
5. 用户确认后才进入库存。

推荐时：

- `ONLY_AVAILABLE`：库存外食材和超库存数量均为硬约束；
- `PREFER_AVAILABLE`：优先库存，无法满足时生成最小补购清单；
- 同一库存批次必须先预留再确认，避免两个并发方案重复使用；
- 烹饪配料在确认实际投入时消耗预留，简单食物在确认实际摄入时消耗预留；摄入事件不重复扣减，取消方案只释放尚未消耗的预留。

### 17.6 「特别想吃一点」推荐

使用单独的 `CRAVING_PORTION` 流程：

1. 明确「不能吃」的原因；
2. 绝对过敏、明确禁忌和原因未知时不试算；
3. 可量化限制才进入求解；
4. 用户给出期望份量或「一口、半份」；
5. 系统换算成克数范围；
6. 求解器判断能否放入剩余额度；
7. 可行时返回份量、搭配、占用额度和剩余风险；
8. 不可行时给更小份量或不命中禁忌的口感替代品。

推荐表达必须使用「当前约束内可以容纳」或「风险相对更低」，不能说「没有伤害」。

### 17.7 第一版数据

产品食材数据：

- 使用 USDA Foundation Foods/SR Legacy 的少量 CC0 食材；
- 每条保留 `fdcId`、原名、版本、来源、每 100 克营养值；
- 中文名是项目维护的别名，不冒充 USDA 官方译名；
- 只发布能说明来源的数值；
- 每个营养值标记 `KNOWN`、`ESTIMATED`、`UNKNOWN` 或 `NOT_APPLICABLE`；
- 缺失的 GI、嘌呤或药食数据保持缺失，不能填 0；
- 第一版不宣称已形成完整中国食材库，家常组合只接收有来源的原料、用量和烹饪参数。

P2 的最小可执行数据集要覆盖中国家庭常见基础类别：主食和杂粮、蛋奶、肉类、水产、豆类及豆制品、常见蔬菜水果、食用油和基础调味品。每条数据仍必须具有合法数值来源；找不到授权数据的食材保持不支持，不能用相似食材数值冒充。

馒头、包子、饺子、炒菜、汤和火锅等组合食品只有在配方、油盐酱料、生熟重量及换算参数可追溯时才能进入产品计算。包装食品优先使用经用户确认的营养标签版本。P2 用这套有限数据验证方案在生活中可执行，而不只验证数学上有解。

首批菜谱不以固定数量验收，而使用覆盖矩阵：

- 至少覆盖目标餐次所需的主食、蛋白质来源、蔬菜和简单食物组合；
- 至少覆盖第一批支持厨具和新手可执行做法；
- 每个版本都具有精确配料、重量基准、油盐水、步骤、依赖、完成条件、食品安全规则和营养结果；
- 配方、烹饪、食品安全、营养和工程审核全部通过；
- 数据不足的类别在产品中明确显示为不支持。

网络菜谱、无许可证菜谱库和模型临场生成内容不能因数量多而进入正式候选。

测试数据：

- 自己编写的合成用户、库存、摄入和测量事件；
- USDA CC0 小型成分夹具；
- 低置信度图片识别响应和用户修正确认；
- 硬约束可行、部分满足和无解场景；
- 绝对禁忌与小份解馋；
- 重复、乱序、延迟和并发事件；
- SMART/FHIR CC0 示例用于未来导入契约。

第一版不使用 NHANES 个体记录，不使用第三方食谱库，也不使用模拟器生成的临床阈值。

### 17.8 第一版交付顺序

第一至第五批按代码依赖顺序共同覆盖 P0～P4 和解释增强能力，不与阶段编号一一对应。P5 的真实验证和病种扩展不属于本节编码批次，但属于真实用户放量前门槛。

第三批完成的确定性 MVP 对外只承诺 A 级自动目标闭环。B 级必须等第五批专业目标管理接口、权限、审核和 `ProfessionalTargetLoader` 全部完成后，才能执行专业人员给定目标的配餐。

### 17.9 第一版完成标准

第一版只有同时满足以下条件才算完成：

- 不调用模型也能生成可验证的单餐和一日菜品、食材克数及结构化步骤；
- 每个营养目标都有公式或专业目标来源、版本、适用人群和有效期；
- 安全许可、原因分类和处置动作能够独立审计；
- 专业目标不能覆盖不可覆盖安全层；
- 关键营养数据不满足质量门槛时不会被当作已满足；
- 已吃食物会从当天额度扣除；
- 单餐推荐不会占用必须留给未来餐的额度；
- 方案确认、库存预留和实际摄入保持独立且支持部分摄入；
- `ONLY_AVAILABLE` 不会使用库存外食材；
- 绝对禁忌不会因「只吃一口」被绕过；
- 约束无解时明确返回冲突，不编造方案；
- 数学可行方案还必须通过份量、餐次结构和烹饪可执行性校验；
- 只有处于有效期内的 `PUBLISHED` 且依赖数据有效的菜谱可以进入正式推荐；
- 精确油盐、调味品、厨具、投放步骤和食品安全条件不能由模型临场生成；
- 计划配料、实际投入、成品重量、实际食用量和剩余量分别记录；
- 模型不能改变求解器确定的食材和克数；
- Redis 清空不影响事实和已确认方案；
- 重复和乱序请求不能覆盖新版本；
- SSE 断开后能够查询任务终态；
- Kill Switch 能按范围停止推荐并保留历史事实；
- 每个营养值、规则和决定都能追溯来源与版本；
- 推荐解释中的数字、约束和理由全部来自 Java 已计算事实；
- 推荐、执行、实际摄入、测量和下一轮决策能够形成可审计业务闭环；
- 模型工具调用次数有限且不能取得目标、克数和最终确认控制权；
- 所有已接受方案通过 Java 硬约束校验。

第一版完成只代表工程闭环通过，不代表可以直接面向真实慢病用户规模化上线。真实用户放量必须满足第 14 章的专业验证、隐私合规、监管评估和暂停条件。
