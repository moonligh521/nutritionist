## 0. 背景

### 0.1 业务背景

系统面向慢病与减重用户，根据家里食材从**已发布菜谱**中推荐能做的菜，克数由求解器锁定。用户通过小程序/对话表达需求，而不是只点表单。

对话里会出现大量「需要记住」的信息，例如：

- 临床向：糖尿病、已确认过敏、用药、测量是否禁止自动配餐；
- 口味向：不喜欢海带、最喜欢娃娃菜、爱吃川菜；且会**改口**（以前不喜欢，现在喜欢了）；
- 过程向：本轮已推荐的三道菜、没有可乐、白蔡→白菜、这顿清淡一点。

若没有企业级记忆分层，会出现：每轮重查档案、改口后仍按旧厌恶过滤、把「不吃」误当成过敏、把「没有」当成忌口、无法回答「以前/现在不喜欢吃什么」。

### 0.2 现状与缺口

| 已有 | 缺口 |
| --- | --- |
| 临床档案（病情/过敏/用药/测量） | 对话回合未完整装载进会话快照 |
| 会话短期（菜列表、缺料等）雏形 | 与长期偏好未形成闭环 |
| 对话规划主路径（理解→规划→执行） | **无旁路**从自然语言抽取偏好 |
| 口味进程内结构 | **无时效**（关旧开新）；难答「以前/现在」 |
| 产品要求不记聊天原文 | 需避免用摘要当事实源 |

### 0.3 设计动机（为何单独做记忆子系统）

1. **安全**：克数、过敏、病情必须由 Java/档案主导，记忆层不能让模型改硬约束。  
2. **体验**：同句「不喜欢海带，帮我推荐」必须立刻生效；改口后推荐与「现在」问答一致。  
3. **合规审计**：能说明「何时因何话记下不喜欢海带、何时改口」。  
4. **可演进**：先内存后 MySQL；思想可对齐 Mem0/Zep，实现保持 Java 自研可控。

### 0.4 范围边界

- **在范围**：长/短/工作记忆模型、旁路抽取、时效偏好、记忆问答、与推荐过滤的接口、落库与合并、分期。  
- **不在范围**：向量召回策略、ojAlgo 求解公式、Spring AI Agent 框架选型、管理台 UI 细稿。

---

## 0.5 一句话结论

**长期 = 可跨会话的结构化事实（临床硬事实 + 带时效的饮食偏好事实链）；短期 = 本会话工作副本与过程态；工作记忆 = 单请求。**  
记忆由**旁路抽取器**只读用户原文写入；推荐与求解只消费**现行投影**；问答可查**现行与历史**；聊天原文永不作为事实源。

## 0.6 技术线路

### 0.6.1 总体技术选型

| 层级 | 选型 | 说明 |
| --- | --- | --- |
| 语言/运行时 | Java 21、Spring Boot（与 nutritionist-service 一致） | 不新起服务 |
| 主对话编排 | 现有 `DialogueOrchestrator` + 有限计划执行 | 不上 Graph 接管 |
| 意图理解 | 现有 `IntentUnderstander` + `ModelCompletion` | 只拆推荐类任务 |
| 记忆抽取 | 新增旁路 `MemoryExtractor`，独立一次模型调用 | 只读用户原文 |
| 临床长期 | `ClinicalRecordService` + MySQL（现有） | 只读装载进快照 |
| 偏好长期 | `PreferenceStore`（事实链）→ 后期 MySQL `diet_preference_fact` | 自研时效，不接 Mem0 运行时 |
| 会话短期 | `SessionMemoryStore`：一期内存，二期 Redis | TTL 会话 |
| 食材归一 | 现有 `DishRecommendService.normalize` / `FoodNormalizer` | 偏好 subject 用规范名 |
| 推荐消费 | `DialogueExecutor` 读现行投影过滤/hints | 过期事实不参与 |
| 缓存（非记忆） | Redis `dish:{id}` 菜卡 | 与用户记忆分离 |

**明确不采用作为记忆运行时**：Spring AI Alibaba Graph、LangGraph、Mem0/Zep 托管服务（可借鉴「旁路抽取 / 事实时效」思想，数据与控制权留在本仓）。

### 0.6.2 技术架构图

```text

                    │         nutritionist-service         │

  HTTP turns ──────►│  DialogueOrchestrator                │

                    │    │       │                         │

                    │    │  (owner 锁 / 关旧开新)           │
                    │    │       │                         │

                    │    │    ClinicalRecord (MySQL)       │
                    │    │    + current(PreferenceStore)   │
                    │    │       │                         │
                    │    │       ▼                         │
                    │    │  SessionMemory.longTermSnapshot │
                    │    │  (+ Redis 二期)                 │
                    │    │                                 │
                    │    ├─3─ IntentUnderstander (主 LLM)  │
                    │    │       ▼                         │
```

### 0.6.3 关键链路（技术步骤）

```text
1. 解析 ownerId = patientId ?: "session:"+sessionId
2. MemoryExtractor.complete(userText) → JSON events/queries/…
3. PreferenceStore.apply（串行）：validTo=now 关旧，插入现行
4. bump preferenceEpoch；刷新 SessionMemory 快照
5. IntentUnderstander → Planner（推荐/换菜等）
6. 若有 queries → 投影 past/current → 固定模板 memoryAnswer
7. Executor 推荐：filter(current.AVOID ∪ allergen ∪ missing)
8. 持久化：一期内存；M4 起写 MySQL；会话可选 Redis
```

### 0.6.4 模型调用线路

| 调用 | 模型用途 | 失败策略 |
| --- | --- | --- |
| MemoryExtractor | 只抽记忆事件/问答意图 | 不写偏好；沿用旧现行；主路径可继续 |
| IntentUnderstander | 只拆 GREETING/RECOMMEND/… | 极薄兜底；不抽偏好 |
| 说明生成（若有） | 不写记忆 | — |

两者均走现有 `ModelCompletion` / `TwoModelChain`（主备超时降级），**密钥与地址不进记忆库**。

### 0.6.5 数据线路

| 数据 | 一期 | 企业目标 |
| --- | --- | --- |
| 偏好事实链 | JVM `ConcurrentHashMap` | 表 `diet_preference_fact` |
| 临床事实 | 现有 MySQL + 服务内存表 | 不变 |
| 会话短期 | JVM SessionMemoryStore | Redis + TTL |
| 现行投影 | 每次 apply/装载计算 | 可缓存，以 epoch 失效 |
| 审计 | fact 全链 + utteranceRef | 同表可查 history API |

### 0.6.6 与「借鉴开源」的关系

| 开源思路 | 本线路落地 |
| --- | --- |
| Mem0：对话旁路抽事实 | `MemoryExtractor` + 结构化 JSON |
| Zep：事实带有效期 | `validFrom` / `validTo`，推荐只用现行 |
| LangMem：独立 memory namespace | PreferenceStore 与 ClinicalRecord 分库分责 |

不引入其运行时，避免自由文本记忆进入医疗过滤链路。

### 0.6.7 技术约束清单

- Java 控制编排与过滤；模型不改克数、不升过敏。  
- 同句必须「先 apply 再推荐」。  
- 服务端 `Instant` 为唯一时间源；同 owner 写入串行。  
- 菜卡 Redis 与用户记忆 key 空间隔离。

## 1. 目标与非目标

### 1.1 目标（闭环）

| 能力 | 说明 |
| --- | --- |
| 分层清晰 | 长期 / 短期 / 工作记忆职责不混 |
| 结构化 | 只存编码、标准食材名、极性、时间窗；不存对话全文当记忆 |
| 时效 | 偏好可改口；旧事实过期；推荐只用现行 |
| 可问答 | 「以前/现在 × 不喜欢/喜欢」有确定答案 |
| 旁路写入 | 抽取与主推荐 Agent 解耦 |
| 硬软分离 | 过敏/病情/禁配餐不可被口语偏好推翻 |
| 可审计 | 何时、因何句话、记成什么、何时过期可追溯 |
| 可落地 | Java 自研；可先内存后 MySQL；不强制引入 Mem0/Zep |

### 1.2 非目标

- 用 LLM 聊天摘要替代结构化记忆  
- 口语「不吃」自动写入临床过敏表  
- Spring AI Graph / LangGraph 接管记忆与推荐控制权  
- 通用人生画像、非饮食记忆  
- 偏好覆盖医嘱、病情适合规则或主料门槛

## 2. 三层记忆总览

```text
┌─────────────────────────────────────────────────────────────┐
│ 长期 Long-Term（跨会话，按 patientId）                        │
│  A. 临床事实库 ClinicalRecord（版本化、审核流）                │
│  B. 饮食偏好事实链 PreferenceStore（带 validFrom/validTo）    │
└───────────────────────────┬─────────────────────────────────┘
                            │ 会话开始或偏好变更时投影
                            ▼
┌─────────────────────────────────────────────────────────────┐
│ 短期 Short-Term / SessionMemory（按 sessionId）               │
│  longTermSnapshot（现行投影副本）                             │
│  + 过程态：当前菜、foodIds、missing、corrections、turnHints…  │
└───────────────────────────┬─────────────────────────────────┘
                            │ 单次请求
                            ▼
┌─────────────────────────────────────────────────────────────┐
│ 工作记忆 Working（请求内）                                    │
│  任务队列、归一中间结果、本轮 memoryAnswer                     │
└─────────────────────────────────────────────────────────────┘
```

| 层 | 生命周期 | 权威性 | 典型消费者 |
| --- | --- | --- | --- |
| 长期-临床 | 跨会话，落库 | 最高（硬） | 安全、过滤、说明 |
| 长期-偏好 | 跨会话，事实链 | 现行投影供推荐；全链供问答/审计 | 过滤、hints、QUERY |
| 短期 | 会话；可 Redis | 过程正确性 | 增量换菜、本轮纠错 |
| 工作 | 单请求 | 无持久 | Orchestrator |

## 3. 长期记忆（完整内容）

### 3.1 临床硬事实（A 类）

来源：`ClinicalRecordService` / 专业录入 / 用户确认后的档案。  
**不**由旁路从闲聊自动升格（病情、过敏尤其禁止闲聊推断）。

| 事实 | 用途 | 写入方式 |
| --- | --- | --- |
| 病情编码 → 控糖等标签 | 菜谱适合/不适合硬过滤 | 档案 API |
| 已确认过敏原 | 硬过滤 | 档案 + 确认 |
| 用药名称/类别 | 说明与安全模块 | 档案 |
| 最新测量是否禁自动配餐 | 门禁：可问答记忆，不可推荐 | 测量事件 |
| （可选）专业忌口/医嘱 | 硬，高于口语 AVOID | 专业目标/医嘱模块 |

### 3.2 饮食偏好事实链（B 类，带时效）

口语与稳定口味走此链，**与过敏分表/分字段**。

```text
PreferenceFact
  id
  ownerId          // patientId；匿名阶段 session:{sessionId}
  subject          // 规范食材名或 foodId；菜系/标签原文规范值
  subjectType      // FOOD | CUISINE | TAG
  polarity         // AVOID | LIKE | CUISINE | TAG
  strength         // ABSOLUTE（过滤）| SOFT（降权）；首版 AVOID 默认 ABSOLUTE
  validFrom        // Instant
  validTo          // null=现行；非空=已过期
  source           // utterance | request | merge | confirm
  utteranceRef     // 回合 id / 原文摘要哈希
  createdAt
```

**互斥**：同一 `ownerId + subject(FOOD)` 上，`AVOID` 与 `LIKE` 不可同时现行；新事件将旧现行 `validTo=now`。  
**菜系**：默认可多条现行；用户说「以后只吃粤菜」则关闭其他 CUISINE 现行。  
**标签**：按 subject 覆盖或并存（「减肥」与「快手」可并存）。

### 3.3 长期投影 API

```text
current(owner, at=now) →
  conditions, allergens, medications, measurementStopsPlanning,
  avoidFoods,      // 现行 AVOID
  preferLikes,     // 现行 LIKE
  preferCuisines, preferTags

pastAvoids(owner)  → 历史上出现过 AVOID 的 subject（含仍现行）
pastLikes(owner)   → 历史上出现过 LIKE 的 subject
at(owner, t)       → 时刻 t 的现行集合（合规/客服）
history(owner)     → 全链（管理端，不对 C 端默认下发）
```

**问答约定（产品默认）**

| 问 | 答数据源 |
| --- | --- |
| 现在不喜欢吃什么 | `current.avoidFoods` |
| 以前不喜欢吃什么 | `pastAvoids`（曾 AVOID 过的都算；一直不喜欢则以前=现在都含） |
| 现在/以前喜欢 | `preferLikes` / `pastLikes` |

**推荐约定**：只用 `current.*`；过期事实不参与过滤。

### 3.4 长期写入路径（闭环）

```text
① 档案 API（临床） → ClinicalRecord
② 请求显式字段 avoidFoods/prefer* + patientId → PreferenceStore.apply
③ 旁路 MemoryExtractor(仅用户原文) → events → PreferenceStore.apply
④ 过敏嫌疑 allergySuspects → 确认流 → ClinicalRecord（不进 AVOID）
⑤ apply 成功 → bump 偏好版本 → 刷新所有活跃 Session 的 longTermSnapshot
```

## 4. 短期记忆（会话闭环）

### 4.1 结构

```text
SessionMemory
  sessionId
  patientId?
  longTermSnapshot     // LongTermMemory 现行投影 + version
  preferenceEpoch      // 与 Store 对齐，变更则强制重载投影
  currentDishes[]      // 菜号去重
  foodIds[]
  missing[]            // 「没有可乐」——缺货，不是 AVOID
  corrections{}        // 白蔡→白菜
  turnHints            // 「这顿清淡」——不升长期
  profile              // 求解用
  revision
```

### 4.2 生命周期

| 事件 | 行为 |
| --- | --- |
| 创建会话 | 若有 patientId，装载临床 + current 偏好投影 |
| 偏好 apply | 立即刷新本会话 snapshot（防「刚说不吃又推荐」） |
| 临床档案变更 | preferenceEpoch/clinicalVersion 失效 → 下次请求重载 |
| 会话结束/TTL | 丢过程态；长期已落 Store/档案不丢 |
| 匿名→登录 | session 偏好链 **merge** 进 patient（较新覆盖较旧） |

### 4.3 短期专有、禁止升长期

- 寒暄、跑题拒答  
- 未确认错别字  
- 「这顿 / 今天」限定的口味  
- 模型说明草稿、工具原始 JSON  
- 未确认过敏嫌疑  

---

## 5. 工作记忆（单请求）

- Intent 任务列表、规划结果  
- FoodNormalizer 中间结果 / needConfirm  
- 本轮 `memoryAnswer`、`appliedEvents`  
- 执行中的临时 exclude 菜号集合  

请求结束即销毁。

## 6. 运行时总流程（企业闭环）

```text
POST /agent/turns (sessionId, patientId?, text, foods?, …)

1. 取/建 SessionMemory
2. 解析 ownerId = patientId ?: "session:"+sessionId
3. 【旁路】MemoryExtractor(text only)
      → apply events（owner 锁内串行）
      → 记录 queries / turnOnlyHints / allergySuspects
4. 若 clinical/preference 版本变化或首次 → 装载/刷新 longTermSnapshot
5. turnHints ← turnOnlyHints（短期）
6. 【主路径】IntentUnderstander → Planner
7. 若有 QUERY → 用 Store 投影生成 memoryAnswer（模板，不编造）
8. Executor：推荐/换菜/加菜…（过滤用现行 AVOID∪过敏∪missing；hints 用 LIKE 等）
9. 若本轮新 AVOID 命中已荐菜 → 只替换违规槽位
10. 返回 DialogueReply（dishes, plan, longTerm 现行摘要, memoryAnswer, needConfirm…）
```

约束：旁路与主路径并行时，**必须先完成 apply + 刷新 snapshot，再执行推荐**，保证同句「不吃海带，推荐菜」一致。

## 7. 旁路 MemoryExtractor

### 7.1 职责

只读用户原文，输出结构化候选；不推荐菜、不改克数、不编病情。

### 7.2 输出契约

```json
{
  "events": [
    {
      "polarity": "AVOID",
      "subject": "海带",
      "subjectType": "FOOD",
      "strength": "ABSOLUTE",
      "confidence": 0.92
    }
  ],
  "queries": [
    { "tense": "CURRENT", "polarity": "AVOID" },
    { "tense": "PAST", "polarity": "AVOID" }
  ],
  "turnOnlyHints": ["清淡"],
  "allergySuspects": [{ "subject": "虾", "confidence": 0.8 }],
  "needsDisambiguation": null
}
```

### 7.3 映射规则

| 用户表达 | 输出 |
| --- | --- |
| 不吃/不喜欢/别给我 X | AVOID(X) |
| 喜欢/最爱/想多吃 X | LIKE(X) |
| 以后都吃川菜 / 只吃粤菜 | CUISINE；「只吃」关其他菜系现行 |
| 过敏 | allergySuspects，禁止写 AVOID 当过敏 |
| 这顿/今天清淡 | turnOnlyHints |
| 没有可乐 | **不**写 AVOID；由主路径 MISSING 或同句识别为缺货 |
| 以前/现在不喜欢吃什么 | queries |

同句多 event：**有序**，后者覆盖同 subject。  
无法消解矛盾 → `needsDisambiguation`，不写入。

### 7.4 置信与确认

| 类型 | 策略 |
| --- | --- |
| 饮食偏好 confidence≥0.85 | 直接 apply |
| 饮食偏好较低 | 回显确认后再 apply（可二期） |
| 过敏嫌疑 | **必须确认**后进 ClinicalRecord |
| 无模型 | 不抽复杂句；可用已有长期记忆继续推荐 |

主体经食材归一（别名/高置信纠错）；低置信错别字不 apply。

## 8. 与推荐 / 安全的优先级

```text
1 测量禁配餐 STOP          → 禁止推荐；允许记忆问答与偏好写入
2 过敏 / 医嘱绝对禁忌      → 硬过滤
3 病情适合·不适合          → 硬过滤（LIKE 不能突破）
4 主料齐全 / 已发布菜      → 硬
5 现行 AVOID(ABSOLUTE)     → 偏好过滤
6 现行 LIKE/CUISINE/TAG    → 软 hints
7 短期 turnHints / missing → 本轮
```

---

## 9. 关键产品场景闭环（验收故事）

```text
T1  「我不喜欢吃海带，帮我推荐菜」
    → AVOID(海带) 现行；推荐无海带
T2  「以前不喜欢吃什么」→ 海带
T3  「现在不喜欢吃什么」→ 海带
T4  「我现在喜欢吃海带了」
    → AVOID 过期，LIKE 现行；其后可含海带
T5  以前不喜欢→海带；现在不喜欢→无海带
T6  「我不喜欢海带了」
    → LIKE 过期，AVOID 现行；推荐再无海带；以前&现在均可答海带
T7  「虾过敏」→ 过敏确认，不进 AVOID
T8  「这顿清淡一点」→ 仅短期 hint
T9  「家里没有可乐」→ missing，不是 AVOID
T10 「我最喜欢娃娃菜」→ LIKE；不强制上菜
T11 已荐三道后新 AVOID 命中其中一道 → 只换该道
T12 匿名会话积累 AVOID 后登录 → merge 到 patient，现行一致
```

---

## 10. 必须注意的边界（汇总）

1. **过敏 ≠ 不喜欢 ≠ 没有 ≠ 这顿不要 ≠ 代替**  
2. **推荐只用现行；问答可查历史**  
3. **硬约束永远压过偏好**  
4. **apply 后立即刷新会话快照**  
5. **多患者不串档；儿童偏好写对 patient**  
6. **服务端时钟；同 owner apply 串行**  
7. **历史默认不对 C 端全量下发**  
8. **「没有」走 missing；「不喜欢」走 AVOID**  
9. **主路径不靠正则堆偏好；旁路模型 + 薄兜底**  
10. **菜号去重、增量换菜策略与记忆变更兼容**

## 11. 数据持久化（企业级）

### 11.1 表 `diet_preference_fact`

| 列 | 说明 |
| --- | --- |
| id | PK |
| owner_id | patient 或 session: |
| subject / subject_type / polarity / strength | |
| valid_from / valid_to | valid_to NULL=现行 |
| source / utterance_ref | 审计 |
| created_at | |

索引：`(owner_id, subject, polarity, valid_to)`；查询现行用 `valid_to IS NULL`。

### 11.2 临床表

沿用现有 condition / allergy / medication / measurement；记忆装载只读。

### 11.3 会话

- 一期：进程内 `SessionMemoryStore`  
- 二期：Redis Hash + TTL（如 7 天），key=`nutrition:session:{id}`  
- 菜卡缓存 `dish:{id}` 仍独立，非用户记忆  

### 11.4 合并

`mergeSessionToPatient(sessionId, patientId)`：按 subject 时间序重放或「取各 subject 最新事件」写入 patient 链并关闭冲突现行。

## 16. 风险与对策

| 风险 | 对策 |
| --- | --- |
| 误抽「不吃」当过敏 | 分字段；过敏强制确认 |
| 误抽「没有」当 AVOID | 抽取契约显式区分；主路径 MISSING |
| 抽失败导致体验回退 | 失败不写；沿用旧现行 |
| 会话未刷新 | apply 同步刷新 snapshot |
| 多端乱序 | owner 级串行锁 |
| 隐私 | C 端只给现行摘要 + 当次问答列表 |

## 17. 成功标准（企业闭环）

1. 长期临床与偏好分离，审计可分。  
2. 任意改口后，推荐行为与「现在」问答一致，且「以前」可追溯。  
3. 同句「不吃 X + 推荐」结果不含 X。  
4. 硬约束（过敏/病情/禁配餐）不被 LIKE/AVOID 推翻。  
5. 短期过程态支持增量换菜；长期重启可恢复（M4 后）。  
6. 无聊天原文依赖即可完成推荐与记忆问答。
