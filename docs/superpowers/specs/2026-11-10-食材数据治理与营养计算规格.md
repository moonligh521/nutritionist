# 食材数据治理与营养计算规格

日期：2026-11-10

状态：待审。

上位基线：`2026-11-10-慢病与减重食材推荐系统设计.md`

## 1. 目的

本规格定义食材数据如何进入产品、如何计算营养、如何发现错误并安全下架。数据质量不足时宁可拒绝自动计算，也不能填 0、猜测或用相似食材冒充。

## 2. 数据分层

### 2.1 基础原材料

米、杂粮、肉、蛋、奶、蔬菜、水果、豆类、食用油等单一原料。

### 2.2 加工食品

豆腐、豆干、面制品、奶制品、调味品和预制食品。必须保存加工状态、配料和适用的数据基准。

### 2.3 组合菜品

米饭、炒菜、炖菜、汤等由明确原料、用量、油盐酱料、成品重量和烹饪参数组成的版本化配方。

### 2.4 品牌包装食品

保存品牌、条码、包装规格、营养标签版本、配料表、过敏原声明和用户确认时间。包装或配方改变必须产生新版本。

## 3. 标准食材合同

每个 `FoodItem` 至少保存：

- 稳定标准食材 ID；
- 原始名称、标准名称和项目维护的中文别名；
- 食材类别和层级；
- 生、熟、加工或包装状态；
- 可食部和计量基准；
- 数据来源、原始记录 ID、许可证和版本；
- 数据质量状态和置信等级；
- 审核状态、生效时间和失效时间；
- 是否允许进入自动求解；
- 适用限制和明确不适用场景。

中文别名不能改变原数据含义。USDA 的数据不能仅翻译名称后宣称为中国同名食材的官方数据。

## 4. 营养值合同

每个 `FoodNutrient` 保存：

- 食材版本和营养素 ID；
- 数值、单位和每 100 克或每份基准；
- 生重、熟重或成品重；
- `KNOWN`、`ESTIMATED`、`UNKNOWN` 或 `NOT_APPLICABLE`；
- 来源和数据集版本；
- 小数精度和换算过程；
- 更新时间和审核状态。

`UNKNOWN` 不参与对应营养约束满足性计算；`ESTIMATED` 必须公开估算来源和适用限制。

## 5. NutritionDataQualityPolicy

策略检查：

- 来源和再发布授权；
- 数据集、包装或配方版本；
- 单位和每份基准；
- 生熟状态和可食部；
- 本次约束要求的营养素完整性；
- 数值范围和异常值；
- 多来源冲突；
- 审核状态和有效期。

输出：

- `ACCEPT`：满足本次场景要求；
- `RESTRICT`：可以用于不依赖缺失指标的场景；
- `REJECT`：不得进入本次自动求解。

质量判断依赖场景。同一食材可以用于普通减重，但因钠未知而不能用于严格限钠目标。

## 6. IngredientNutritionCalculator

单食材计算顺序：

1. 读取食材和营养值版本；
2. 统一重量、体积和份量单位；
3. 应用可食部；
4. 确认输入使用生重、熟重还是包装份量；
5. 只有存在已发布转换参数时才做生熟重换算；
6. 按实际可食克数计算营养；
7. 保留每个营养值的状态和来源；
8. 输出计算明细和数据质量结果。

生重数据不能直接乘熟食重量。缺少可靠转换时要求用户改用数据支持的重量基准，或把结果标为不可自动计算。

## 7. RecipeNutritionCalculator

组合菜计算必须包含：

- 配方版本；
- 每个原料的标准 ID、状态和原始用量；
- 油、盐、酱料和其他调味品；
- 可食部处理；
- 烹饪方式；
- 成品总重量和份数；
- 有来源的出成率、吸水失水、油脂吸收和营养素保留参数；
- 每份和每 100 克成品营养结果。

计算顺序：

1. 分别调用 `IngredientNutritionCalculator`；
2. 应用已发布的烹饪转换；
3. 汇总所有原料和调味品；
4. 按成品重量计算每 100 克和每份；
5. 传播未知值和估算状态；
6. 重新校验过敏原和关键营养数据门槛。

任一关键参数未知时，不能用默认损耗率补齐。可以返回 `RESTRICT` 或 `REJECT`，但不能宣称结果精确。

## 8. 第一版最小覆盖

P1 只建立合法、可追溯的子集和数据管道。P2 才要求最小品类覆盖：

- 主食和杂粮；
- 蛋奶；
- 常见肉类和水产；
- 豆类及豆制品；
- 常见蔬菜和水果；
- 食用油和基础调味品。

每个类别至少有足以组成单餐和一日方案的候选，但不以固定数量冒充覆盖率。产品界面必须明确不支持的食材。

馒头、包子、饺子、炒菜、汤和火锅等组合食品只有具备可追溯配方和参数时才进入产品数据。测试专用合成食材不能进入生产数据库。

## 9. 发布和下架

数据状态为：

`DRAFT → REVIEWED → PUBLISHED → SUSPENDED → RETIRED`

发布前检查授权、字段完整性、异常值、单位、生熟状态、关键营养素和回归用例。

发现错误时：

1. 立即将问题版本标记 `SUSPENDED`；
2. 通过 `SafetyGovernanceService` 启用对应数据范围的 Kill Switch；
3. 查询引用该版本的未执行方案和历史方案；
4. 使受影响未吃餐失效；
5. 发布修正版或回滚到已审核版本；
6. 重跑回归和影响分析；
7. 经审批后恢复自动推荐。

历史方案继续引用旧版本用于审计，不能把旧数据静默替换成新数据。

## 10. 模块和数据所有权

- `nutrition` 拥有食材、营养值、烹饪转换和质量策略；
- `pantry` 只引用标准食材 ID，不修改营养数据；
- `solver` 只读取通过质量准入的候选快照；
- `plan` 保存所用数据版本，不直接查询外部数据源；
- `evidence` 保存来源和审核记录，不修改计算结果。

禁止 `PlanService` 或 `PantryService` 直接调用 `NutritionMapper` 写数据。

## 11. 测试合同

至少覆盖：

- 每 100 克、每份和单位换算；
- 生熟状态不匹配；
- 可食部；
- 缺失值传播；
- `ACCEPT`、`RESTRICT` 和 `REJECT`；
- 同食材不同版本；
- 油盐和调味品计入组合菜；
- 成品重量和份数；
- 未知烹饪参数拒绝；
- 包装标签版本变化；
- 错误数据下架和未吃方案失效；
- 历史方案按旧版本重建；
- 测试数据与产品数据隔离。

## 12. 发布门槛

P2 的最小食材集必须通过授权、质量、营养复算、过敏原、组合可执行性和方案盲测。食材数量不是放行条件；可追溯、可计算和能组成现实餐食才是放行条件。
