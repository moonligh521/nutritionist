## 0. 问题与目标

### 0.1 现状

已具备：白名单任务、增量换菜/加汤、主料硬门槛、记忆权威分层、问餐/记忆读写拆分、理解决策树+少样例、10 轮 HTTP 门禁。

不足：覆盖的是竖切样例，不是真实行为分布。一句话多意图冲突、指代、改口、空结果引导、约束降级、金标回归尚未产品化。

### 0.2 目标

1. **行为完备**：常见长尾可进入可解释状态，而不是静默 `OUT_OF_SCOPE` 或乱荐菜。  
2. **路径清晰**：问餐同步 ≤1 次文本模型；记忆 LLM 异步；安全规则同步。  
3. **结果可信**：主料/绝对忌口/临床过敏不可破；软偏好只排序。  
4. **可度量**：金标集 + Langfuse 分路径看板 + CI 门禁。  
5. **可演进**：TaskType 白名单冻结；扩展走 Planner 策略与金标，不先加模型自由发挥。

### 0.3 非目标

- 通用闲聊 / 情感陪伴  
- 模型直接生成菜名或改克数  
- 再加一轮「统一润色」LLM  
- MQ/Outbox（记忆写仍 V2.1 同步 DB 事务；异步仅指「不阻塞问餐」）  
- 用 AcceptIT 故事替代金标全集

## 1. 总体架构

```text
                    ┌─────────────────────────────┐
  点「问餐」按钮 ──►│ PreferenceWarmup（只读投影）  │──► Session.longTerm + epoch
                    └─────────────────────────────┘
                                      │
  POST /turns (text, foods, …) ───────┤
                                      ▼
┌──────────────────────────────────────────────────────────────┐
│ AskMealSyncPath（nutrition.ask_meal）                        │
│  1. expireDue / bindOwner / requestTaste                     │
│  2. MEMORY_REFRESH（只读 Snapshot，无 LLM）                    │
│  3. RULES_COMMIT（thinFallback 同步，无 LLM）                  │
│  4. UNDERSTAND（唯一同步文本模型）→ TurnIntent                 │
│  5. DialoguePhase + ConflictPlanner → 有序 plan              │
│  6. EXECUTE（召回/增量/确认）+ 降级阶梯                         │
│  7. SESSION_SAVE + 本地拼回复（无润色模型）                     │
└──────────────────────────────────────────────────────────────┘
                                      │ fire-and-forget
                                      ▼
┌──────────────────────────────────────────────────────────────┐
│ MemoryWriteAsyncPath（nutrition.memory.write）               │
│  模型抽取 → validate → MySQL commit → epoch++                 │
│  失败：指标 + 日志；不影响本回合荐菜                             │
└──────────────────────────────────────────────────────────────┘
```

控制权分层：

| 层 | 职责 | 技术 |
| --- | --- | --- |
| 理解 | 听懂 → TurnIntent | 1× LLM + 契约 JSON |
| 规划 | 冲突消解、阶段门禁、指代补全 | Java Planner |
| 执行 | 归一/召回/增量槽位 | Java Executor + Recall |
| 记忆写 | 持久化偏好 | 规则同步 + 模型异步 |
| 权威 | 偏好/会话/临床 | MySQL / Redis / 临床 API |

## 2. 会话阶段（DialoguePhase）

存在 `SessionMemory.phase`（Redis 快照字段），每回合规划前后更新。

| 阶段 | 含义 | 允许的主任务 |
| --- | --- | --- |
| `IDLE` | 无有效荐菜 | GREETING / RECOMMEND / OUT_OF_SCOPE |
| `CONFIRMING` | 待确认食材 | 仅确认相关；阻断找菜 |
| `RECOMMENDED` | 已有 1～3 道 | REPLACE / ADD_KIND / MISSING / SUBSTITUTE / 再 RECOMMEND |
| `ADJUSTING` | 连续增量调整中 | 同 RECOMMENDED |
| `EMPTY_GUIDE` | 上轮空结果 | 引导补食材/放宽约束；或重新 RECOMMEND |
| `BLOCKED` | 测量禁配餐等硬阻断 | 只解释，不荐菜 |

转移（摘要）：

- 成功写出 dishes → `RECOMMENDED`  
- `needConfirm` 非空 → `CONFIRMING`  
- 荐菜/增量后 dishes 空且 emptyReason 非 NONE → `EMPTY_GUIDE`  
- 确认完成且无阻断 → 回到 `IDLE`/`RECOMMENDED`  
- `measurementStopsPlanning` → `BLOCKED`

阶段用于 **Planner 门禁**，不替代 TaskType。

## 3. 理解契约（TurnIntent）稳定版

### 3.1 输出

```json
{
  "tasks": [ { "type": "…", "…slots": "…" } ],
  "turnConstraints": {
    "avoidFoods": [],
    "absoluteAvoidFoods": [],
    "cuisine": "",
    "kind": "",
    "preferTags": [],
    "turnHints": []
  }
}
```

- `memoryQueries`：**默认不由理解产出**；「以前不喜欢」等走同步规则。  
- TaskType **冻结**为现有枚举；新增类型须改设计 + 金标，禁止模型发明。

### 3.2 入参

- 用户原文、请求 foods  
- PreferenceSnapshot 摘要（空=「无」，每类 ≤5）  
- **当前已荐菜名**（有序，对应槽位 1..n）  
- 当前 `phase`（只读提示，防止 CONFIRMING 时乱荐菜）

### 3.3 Prompt 策略

- 决策树：业务意图优先，`OUT_OF_SCOPE` 最后  
- 少样例：金标驱动更新，不手工无限堆  
- 禁止荐具体新菜名、改克数、编病情

## 4. 冲突规划器（ConflictPlanner）

在 `DialoguePlanner` 之上（或内聚升级），输入：`TurnIntent` + `SessionMemory` + `phase` + 归一预览。

### 4.1 优先级（高 → 低）

1. `BLOCKED` → 只解释  
2. 待确认 / 本轮产生 `CONFIRM_FOODS` → 阻断后续找菜任务  
3. 本轮 **RETRACT/改口**（规则事件）→ 先更新过滤，再执行后续荐菜/换菜  
4. `MISSING` / `SUBSTITUTE`（改约束）先于 `REPLACE_ONE` / `ADD_KIND`  
5. 多个 `REPLACE_ONE` → 按 dishHint 去重合并  
6. `RECOMMEND` 与增量并存：若已有 dishes 且用户未说「重新推荐」，增量优先，RECOMMEND 降为约束刷新或忽略  
7. `OUT_OF_SCOPE` 与业务并存 → 旁支一句后继续业务  
8. `GREETING` 可前置  

### 4.2 指代解析（Resolver）

在进 Executor 前补全槽位：

| 说法 | 规则 |
| --- | --- |
| 「换一个」无菜名 | 默认槽位 0；或上轮刚提到的菜 |
| 「换第二个 / 第2道」 | 按下标映射当前 dishes |
| 「那个 / 这个」 | 优先上轮 `lastFocusedDishId`，否则槽位 0 |
| 「换成别的」+ dishHint 模糊 | 与当前菜名模糊匹配；多候选则追问（不硬猜） |

`SessionMemory.lastFocusedDishId`：每次 REPLACE/用户点名后更新。

### 4.3 空结果引导（EMPTY_GUIDE）

当 `emptyReason ∈ {SCALAR_EMPTY, NO_FEASIBLE_MAINS, FILTER_FAIL_CLOSED, ANN_EMPTY, …}`：

- 回复结构化引导，而非仅一句「没有主料齐全…」  
- 建议动作枚举（产品文案模板）：`ADD_FOODS` / `DROP_CUISINE` / `DROP_TAGS` / `KEEP_WAITING`  
- 下轮若用户补 foods 或说「不限川菜」，Planner 清除对应约束再 RECOMMEND

## 5. 记忆完整方案

### 5.1 权威（不变）

- 偏好：MySQL `diet_preference_*`  
- 会话：Redis `nutrition:session:{id}` + `preferenceEpoch`  
- 临床过敏/病情：临床服务；嫌疑表不升格硬过滤  

### 5.2 读路径

| 触发 | 行为 |
| --- | --- |
| 点「问餐」 | `POST .../preference/warmup`：只读加载 Snapshot → 写入会话 |
| 每回合 turns | `MEMORY_REFRESH`：epoch 落后则重载；否则复用会话副本 |
| 理解 | Snapshot 摘要进 prompt |
| 过滤 | Snapshot ∪ TurnConstraints（绝对硬 / 普通软） |

### 5.3 写路径

| 类型 | 时机 | 失败语义 |
| --- | --- | --- |
| 规则（绝对不能吃 / 薄 AVOID 等） | 同步 RULES_COMMIT | 失败则本轮无权威落库；仍可用 TurnConstraints |
| 模型抽取 | AsyncMemoryWriter | 失败不影响问餐；打点 `memory.write.fail` |
| 客户端 avoidFoods | merge，强度 ≤ MODERATE | 不得当 ABSOLUTE |
| 治理 retract/correct/delete | 同步 API | 成功后可选刷新会话 + auto-replace |

### 5.4 改口与撤销（产品化）

- 「不算了 / 可以吃了 / 不再忌口」→ 规则或治理 RETRACT  
- 同步规则命中则本轮刷新 Snapshot；异步模型作补充  
- 已荐菜触犯新 ABSOLUTE → `autoReplaceHitByAbsoluteAvoid`（已有）保留  

### 5.5 可见性

- 异步写成功后 **不强制本回合二次召回**（保持延迟）  
- 下回合 / 下次 warmup 靠 epoch 读到新偏好  
- 可选：写成功发会话 hint「已记住忌口 X」（非阻断）

## 6. 检索与安全降级阶梯

### 6.1 硬约束（不可破）

1. 主料齐全  
2. 临床过敏 + Snapshot.absoluteAvoid + 本轮 absoluteAvoid  
3. 测量禁配餐 → BLOCKED  
4. 有 filter 时向量失败 → fail-closed（不退全库）  

### 6.2 软约束（可降级）

顺序尝试（每次记录 `degradeStep`）：

0. 全量约束（cuisine + kind + tags + conditions + fuzzy）  
1. 去掉本轮 turnHints/preferTags  
2. 去掉 cuisine（保留病情 conditions）  
3. 仅主料 + 绝对忌口（无标量菜系）  
4. 仍空 → EMPTY_GUIDE，不编菜  

**默认**：生产可配置 `nutritionist.recall.degrade.enabled`；门禁测试可关，保持 fail-closed 严格性。  
产品策略：**点名不存在的菜系（XYZ）不降级**，保持 SCALAR_EMPTY（与现 Accept R8 一致）；仅对「有候选语义但过严」的标签/清淡等降级。

### 6.3 emptyReason → 用户话术

维护映射表（Java 模板，非模型）：每种 reason 一句可执行建议。

## 7. 执行与增量（巩固）

- REPLACE / ADD_KIND / MISSING **禁止**全量重跑 RECOMMEND  
- 菜号去重；ADD 不删已有  
- 软确认：仅当 plan 无后续业务任务时因 CONFIRM 停  
- 回复：规则拼接 explanation；可选后续加「模板变量」；不加润色 LLM

## 10. 金标与质量闭环（企业级关键）

### 10.1 金标集结构

每条：

```text
id, utterance, foods?, session_fixture, expect_tasks[], expect_slots,
expect_phase_after, expect_hard_avoid_applied?, notes
```

分桶：问候 / 域外 / 荐菜 / 换菜指代 / 加汤 / 多意图 / 忌口绝对 / 改口 / 确认 / 空结果 / 病情冲突。

规模：v1 **≥80 条**；v2 **≥200 条**。来源：产品用例 + 线上脱敏抽样 + 合成。

### 10.2 两级跑法

| 级 | 方式 | 门禁 |
| --- | --- | --- |
| L1 契约 | mock 模型返回固定 JSON 或跳过模型测 Planner/Executor | PR 必跑 |
| L2 真模型抽检 | 每晚/手动对金标子集打真实 UNDERSTAND | 不挡 PR；回归看板 |

### 10.3 AcceptIT

保留 **10 轮真人 HTTP** 作为冒烟门禁；不替代金标。  
R9/R10 等关键意图可升格为「plan 类型硬断言」可选开关。

### 10.4 Prompt 变更纪律

改理解 prompt 必须：更新金标样例 → L1 绿 → 抽检 L2 对比 OUT_OF_SCOPE/换菜命中率 → 再合入。

## 12. 风险与对策

| 风险 | 对策 |
| --- | --- |
| 真模型仍漏换菜/加汤 | 金标驱动 few-shot；Planner 侧对「换一个」+ 已有菜做薄兜底（可选开关，默认关以保持「理解主路径」） |
| 异步记忆晚到导致下轮才生效 | 产品文案「已记下，下一轮生效」；绝对忌口走同步规则 |
| 降级过宽编出不适菜 | 点名菜系/病情不降级；主料与绝对忌口永不降 |
| 阶段字段拖垮旧客户端 | 仅响应加字段；缺省 phase 由服务端自洽 |
| 金标维护成本 | 分桶业主；改 prompt 强制带金标 diff |
