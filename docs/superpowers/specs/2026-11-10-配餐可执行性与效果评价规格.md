# 配餐可执行性与效果评价规格

日期：2026-11-10

状态：待审。

上位基线：`2026-11-10-慢病与减重食材推荐系统设计.md`

## 1. 目的

本规格解决三个问题：

1. 数学可行的食材克数是否能在现实中执行；
2. 用户如何理解推荐依据和剩余额度；
3. 实际摄入和测量如何形成结构化评价，而不直接修改目标。

## 2. MealPracticalityValidator

`MealPracticalityValidator` 位于求解后、最终营养校验前。它不判断临床安全，也不依赖大模型主观评价。

输入：

- 食材 ID、克数和份量档位；
- 餐次和用户确认的餐次习惯；
- 版本化最小、最大和常见份量规则；
- 版本化食材组合与烹饪兼容规则；
- 家中可用设备、时间和做法限制；
- 库存、预算和偏好；
- 规则和数据版本。

检查：

- 克数是否落在可执行份量档位；
- 是否出现没有实际意义的极小份量；
- 单一食材是否异常占据整餐；
- 食材项是否过度碎片化；
- 主食、蛋白质来源和蔬菜等餐次结构是否满足已发布规则；
- 所选食材是否存在明确的烹饪组合冲突；
- 做法是否需要用户没有的设备或超出明确时间限制；
- 调整后是否仍满足营养、禁忌和库存约束。

输出：

- `PASS`：可以进入最终校验；
- `ADJUSTABLE`：返回结构化可执行性约束，交给求解器最多重算一次；
- `REJECT`：无法在不突破硬约束的情况下形成可执行餐食。

模型不能把 `REJECT` 改成通过，也不能自行添加未经规则支持的“合理搭配”结论。

## 3. 可执行性规则

每条 `MealPracticalityRule` 保存：

- 规则 ID、类型和版本；
- 适用餐次、人群和食材类别；
- 最小份量、最大份量或份量步长；
- 允许或禁止的组合条件；
- 餐次结构要求；
- 设备、时间或做法条件；
- 来源和审核状态；
- 生效失效时间；
- 测试用例。

份量和组合规则必须来源明确。没有规则时保持未知，不由 AI 根据常识写入硬约束。

## 4. RecommendationExplanation

Java 根据已经确定的事实构建 `RecommendationExplanation`：

- `selectedFoods`：为什么这些食材进入方案；
- `portionReasons`：克数对应的餐次额度、份量档位和库存条件；
- `budgetUsage`：本餐使用的能量和关键营养额度；
- `remainingBudget`：当天尚未吃餐次可用范围；
- `activeConstraints`：真正影响结果的安全和营养约束；
- `preferenceTradeoffs`：哪些偏好得到满足，哪些因高优先级约束未满足；
- `dataQualityNotes`：估算值、未知值和限制；
- `confirmationNeeded`：需要用户确认的数量、配料或状态；
- `evidenceRefs`：规则、食物数据和指南引用；
- `limitations`：系统不能保证的部分。

Spring AI 只能把这些字段改写成易懂文字，不能增加新的医学原因、营养数字或安全结论。解释生成失败时仍返回 Java 生成的结构化事实。

## 5. OutcomeEvaluator

`OutcomeEvaluator` 依次生成六类评价：

1. `DataCompletenessAssessment`：摄入、测量、运动、疾病和药物信息是否足够；
2. `AdherenceAssessment`：实际摄入与确认方案的差异，只描述事实，不进行道德评价；
3. `MeasurementQualityAssessment`：单位、时间、设备、餐前餐后语境和异常值；
4. `TargetAchievementAssessment`：实际摄入是否落在当前目标范围；
5. `TrendAssessment`：在已发布规则允许的时间窗内评价体重和血糖趋势；
6. `MeasurementDecision`：复用主方案的 `NEED_MORE_DATA`、`URGENT_REFERRAL`、`KEEP`、`ADJUST_FUTURE_MEALS` 或 `REASSESS_DAILY_TARGET`。

评价必须考虑记录不完整、水分变化、测量时间不一致、运动、急性病和药物变化。单次异常或短期体重不降不能直接生成更大的热量缺口。

`MeasurementDecision` 不是目标修改命令。它必须回到 `安全许可 → NutritionTargetCalculator/ProfessionalTargetLoader → MealBudgetAllocator → 求解器 → MealPracticalityValidator → Java 校验`。专业复核由 `SafetyPermission.HUMAN_REVIEW` 和处置动作表达，不再建立第二套近义状态机。

## 6. 方案和摄入差异

- 确认方案表示计划；
- `intake_event` 表示实际摄入；
- 部分摄入按实际克数复算；
- 未吃、少吃、替换和额外摄入分别记录；
- 系统不得用方案克数自动填充实际摄入；
- 更正通过追加事件完成；
- 效果评价引用实际摄入版本和方案版本。

## 7. 求解器基准体系

建立固定且版本化的 benchmark 数据集：

- 单餐基础求解；
- 全天多餐；
- 减重与控糖共同约束；
- 库存充足和不足；
- 绝对过敏；
- 无解冲突；
- 极端输入；
- 大候选集；
- 并发求解；
- 同输入复现；
- 可执行性重算。

每次基准保存：

- benchmark 版本；
- 规则、食物数据和求解器版本；
- 变量和约束数量；
- 求解状态和耗时；
- 目标函数各层结果；
- 硬约束满足情况；
- 营养汇总；
- 冲突解释；
- 内存和并发资源；
- 最终可执行性状态。

同输入复现不强制食谱文本完全相同，但约束集合、硬约束结果、目标层级、营养结果和可接受的数值误差必须一致。求解器升级必须重跑基准并评审差异。

## 8. SafetyGovernanceService

`SafetyGovernanceService` 的权威边界定义在主方案第 15.3 节。本节只说明它与可执行性、效果评价的衔接；它是运营协调入口，不是新的临床决策引擎。它负责：

- 发布、暂停、回滚规则；
- 发布、下架和恢复食材数据；
- 操作 `EmergencyKillSwitch`；
- 查询受规则或数据版本影响的方案；
- 使受影响未吃餐失效；
- 发起回归、影响分析和恢复审批；
- 保存操作者、原因和审计记录。

它不能编辑临床规则正文、绕过审核、修改历史摄入或直接生成方案。

## 9. 测试合同

至少覆盖：

- 极小份量、份量步长和食材碎片化；
- 餐次结构和明确烹饪冲突；
- 可执行性约束重算一次后通过或拒绝；
- AI 解释编造数字或原因时被拒绝；
- 剩余额度和估算值正确展示；
- 数据不完整时 OutcomeEvaluator 只要求补数据；
- 部分摄入和额外摄入；
- 单次异常不自动修改目标；
- 规则或数据下架后的影响方案定位；
- Kill Switch 和恢复审批；
- 固定 benchmark 的性能和复现性。

## 10. 放行门槛

P2 的确定性 MVP 必须在固定数据集上同时满足营养硬约束、库存约束、可执行性和复现性。P4 的动态调整必须通过专业人员审核的效果评价规则。用户解释必须完全来源于已计算事实，模型表达不是放行依据。
